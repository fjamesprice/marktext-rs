**One dispatch of `soak.yml` costs roughly 2,251 billable minutes against a

The billing page is not readable from this session (the Actions billing API

## 1. Scope

**In:** `crates/mt-doc` and `crates/mt-md`.

- `mt-doc` — the arena, `Text`, `Document`, and `Edit::apply` with its inverse.
  Twenty-five `todo!()`s across five files (`block.rs` 6, `document.rs` 13,

- `mt-md` — `parse`, `serialize`, `dump_state`, `render_to_static_html`. The

- The block-level divergence register (§5 D4) and the conformance re-baseline
  (§5 D5), which is a one-way door.

**Out:**

- **HTML → Markdown (paste).** §4's table lists it under `mt-md`, and nothing
  in M2's exit gate touches it: it is reached only from the clipboard, which is
  M5's, and `htmlToMarkdown.ts` (88 lines) has no fixture in `spec/`. Porting
  it here would add a `html5ever`-shaped dependency question to a milestone
  that already has one about block parsing. Recorded in §10 rather than done.
- **Layout, rendering, highlighting.** M3. `benches/tokenizer.rs` already
  carries two rule-table optimizations M1 deliberately deferred there
  (`html_tag`'s first-byte pre-check, hoisting `tryAutoLinkExtension`'s

- **The renderer half of §10's owed items.** `mt-inline` ships
  `marker_state_of_range` so `header.ts`'s synthetic range is *expressible*;
  whether a renderer uses it is not M2's to answer, because M2 has no renderer.
- **`mt-inline`'s five `debug_assert!`ed branches.** S7 turned four proofs and
  one hang-guard into assertions precisely so that proptest and the soak attack

**Deliberately deferred within M2:** collaborative editing (§5 D9), and any
change to `Edit`'s shape that would foreclose it.

## 3. Three pipelines, not one

This is the reframe M2 needs before any of §4 makes sense, and nothing in the
plan says it. muya converts markdown three different ways, through three
different code paths, and **the M2 exit gate takes one criterion from each of
two of them**:

```
                       ┌─ lexBlock (marked + math/footnote/frontMatter)
markdown ──────────────┤        └─► MarkdownToState.generate() ──► TState[]
                       │                                            ▲
   §11.2 differential ─┘                                            │
   (cargo xtask diff, mt-cli --dump-state) ──────────────────────────┘

markdown ──► getHighlightHtml (marked's OWN renderer + Prism + cjkEmStrong,
             emoji, math, superSubScript) ──► DOMPurify ──► HTML
                       ▲
   §11.1 conformance ──┘   (cargo xtask conformance, renderToStaticHTML)

block text ──► inlineRenderer/lexer.ts ──► Token[] ──► renderer/ ──► DOM
                       ▲
   M1's harness ───────┘   (cargo xtask divergences)
```

Three consequences, each of which becomes a correction below:

1. `renderToStaticHTML` never touches `MarkdownToState`. It calls
   `getHighlightHtml(markdown, …)`, which is `marked.parse()`. So the
   conformance percentage and the differential harness measure **different
   engines**, and the inherited `expected-failures.json` is a property of the
   one the Rust port is *least* going to resemble. → **C3**, **D5**.
2. The differential harness compares `TState[]`, in which a leaf block's text
   is unparsed inline source. Nothing `mt-inline` does is visible to it. →
   **C4**.
3. `mt-inline` — 2 months of M1 — is consumed by neither. It is the editor's
   renderer path, and its first *consumer* is M3. M2 wires the label map into
   it (`collectReferenceDefinitions`) and otherwise leaves it alone.

## 4. Corrections to the plan

### C1 — `pulldown-cmark` for blocks: adopt it, and pay for three things the plan does not name **← measured**

§4 says:

> Markdown → `Document`: `pulldown-cmark` for block structure only; leaf text
> is captured as **raw source slices**, never as parsed inline events. […]
> Using `pulldown-cmark` for blocks only — and never for inlines — is the key
> integration decision.

M1's §4 C1 checked `rules.ts`'s regexes against the `regex` crate's feature set
before adopting it and found the plan's proposal could not work. The same check
here needs a measurement rather than a reading, because the question is not
"can pulldown-cmark parse blocks" (it can, at >99 % CommonMark) but "does it
produce **muya's** blocks", and muya's block parser is `marked`, which is not
CommonMark-conformant and is not going to be ported.

**So it was measured.** `pulldown-cmark 0.13.4` with
`ENABLE_TABLES | ENABLE_STRIKETHROUGH | ENABLE_TASKLISTS`, driven through
`into_offset_iter()`, mapped onto `Block`'s vocabulary by the obvious
correspondence, against `MarkdownToState.generate()` on the same inputs:

| Input set | Options | Count |
|---|---|---:|
| CommonMark 0.31 fixtures | `SPEC` | 652 |
| GFM 0.29-gfm fixtures | `SPEC` | 672 |
| `spec/fixtures/marktext-round-trip/` | `MUYA_DEFAULT` | 11 |
| `bench/corpus/`, the nine files ≤ 300 KB | `MUYA_DEFAULT` | 9 |
| | | **1344** |

**The block-name tree agrees on 1167 of 1344 — 86.8 %.** Per set: CommonMark
567/652 (87.0 %), GFM 585/672 (87.1 %), round-trip fixtures 9/11, corpus 6/9.

**The finding is not the 86.8 %. It is that all 177 disagreements are four
named mechanisms, and none of them is the parser disagreeing about where a
block begins.**

| # | Cause | Cases | Where it lives |
|---:|---|---:|---|
| 1 | **Reference definitions are consumed and not emitted** | **155** | the mapping layer |
| 2 | **Empty containers** — muya's #1735 fix inserts a synthetic empty paragraph | 19 | the mapping layer |
| 3 | **Task lists split a list** — `compatibleTaskList` | 2 | the mapping layer |
| 4 | Block math — `MUYA_DEFAULT` has `math: true`, the spike had no math extension | 1 | options, not a disagreement |

Each in turn, because each is work.

**1 — reference definitions, and the recovery route is lossy.** `[foo]: /url`
produces **no event at all** from `pulldown-cmark`; muya emits a `paragraph`
whose text is the raw line (`markdownToState.ts`'s `def` case, and §2 of the
plan is explicit that reference definitions are not a block type). That single
mechanism is 155 of the 177 — 150 directly, plus 2 where the missing paragraph
shifts a following `block-quote`, 2 where it shifts a following
`setext-heading`, and 1 in `bench/corpus/10kb.md`.

The obvious fix is `parser.reference_definitions()`, whose `LinkDef` carries an
exact `span`. **Measured, it does not survive contact with duplicates:**

```
"[foo]: /a\n[foo]: /b\n\n[foo]\n"   → refdefs: 1   "foo" → "/a"  span 0..9
"[FOO]: /a\n[foo]: /b\n\n[Foo]\n"   → refdefs: 1   "FOO" → "/a"  span 0..9
```

`RefDefs` is a map keyed by Unicode-case-folded label, so a repeated label
**collapses** and the second line exists in neither the event stream nor the
map. muya emits two paragraphs. That is silent data loss on a document the user
typed, and §10 makes lossless round-trip non-negotiable. A third measured
wrinkle: inside a block quote the span is `2..13` for `> [foo]: /url` — the
`> ` is excluded — so the span does not by itself say which container the
definition belonged to.

**So the port scans for definition lines itself** rather than reading
`RefDefs`. That is not extra work invented here: muya already scans
(`InlineRenderer.collectReferenceDefinitions` is a regex over paragraph text),
and the label map the inline tokenizer needs has to be built from the block
tree regardless. → **D3**.

**2 — empty containers.** `>` alone, `-` alone, `-\n\n  foo`. muya pushes an
empty `paragraph` into an otherwise-empty block quote or list item; the code
carries the issue number (#1735). `pulldown-cmark` emits the empty container.
Thirteen list items and six block quotes across the fixtures. Pure mapping.

**3 — a list splits where task-ness changes.** `spec/fixtures/marktext-round-
trip/common/Links.md` has four items — two plain, then two `- [ ]` / `- [x]`.
muya produces a `bullet-list` of two followed by a `task-list` of two;
`pulldown-cmark`, and GFM, produce **one list of four**. This is not a bug in
either: `Block` has `BulletList` and `TaskList` as separate variants and **no
mixed variant**, so muya's `compatibleTaskList` (189 lines) has to split, and
the port has to split identically or the 1:1 mapping stops holding. `gfm#280`
is the nested case.

**Decision: adopt `pulldown-cmark`, and write the mapping layer as a named
deliverable rather than as glue.** The plan's key integration decision survives
the measurement — what it understates is that "for block structure only" is not
the same as "for `Block` directly", and the difference is three mechanisms,
about 155 fixtures, and one lossy API that looks like the answer. → **D1**.

**Two things about the measurement itself, recorded because getting them wrong
inflated the disagreement count by 95 and the first run looked clean.** A
*tight* list item carries its inline events with **no `Paragraph` wrapper**, so
a mapping that only creates nodes for block tags gives every tight item no
children at all — 90 false disagreements. And when a synthetic paragraph is
introduced to fix that, it must be ended by a **block** `Tag` and not by
`Emphasis`, `Link` or `Strikethrough` — ending it on any `Start` splits every
item containing emphasis into several paragraphs, which is 5 more, and which
presented as a plausible `marked`-vs-CommonMark list finding in `10kb.md`
before it was chased down. First run 1062/1333; corrected, 1167/1344. This is
S7's A/B-ordering mistake in another costume: internally consistent, and wrong.

**And what the measurement does not establish.** It compares the tree of block
*names* only — not `meta`, so looseness, list `start`, bullet marker, ordered
delimiter, fence length, heading style and cell alignment are all unchecked,
and every one of them is a field `pulldown-cmark` does not carry in its event
stream and the port must recover by re-reading the source range. §6's S1 gate
is stated over `meta` as well for exactly that reason.

### C2 — "leaf text is captured as raw source slices" is false of the reference engine **← measured**

§4's sentence has two halves and only the second is true. Inline structure is
indeed never parsed — §0's premise holds, and M0 verified it against the
running engine. But a leaf's `text` is **not a slice of the document**. It is
`marked`'s per-token `.text`, which strips block and container markers and, in
four cases, rewrites the content.

Asked of the running engine directly:

| Source | muya's leaf `text` |
|---|---|
| `> hello\n> world` | `"hello\nworld"` — the `> ` prefixes are gone |
| `- foo\n  bar` | `"foo\nbar"` — the marker and the continuation indent are gone |
| `##   Foo   ##` | `"## Foo"` — **reconstructed** as `'#'×level + ' ' + text` |
| `    let a = 1` | `"let a = 1"` — four spaces stripped from every line |
| `Foo\nbar\n===` | `"Foo\nbar"` — the underline is in `meta.underline` |
| `\| a \\\| b \|` | `"a \| b"` — trimmed, and the table `\\\|` escape resolved |
| `$$\n  x^2\n$$` | `"x^2"` — trimmed |
| `  ⇥foo⇥baz` | `"  ⇥foo⇥baz"` — leading indent **kept**, unlike the range |

Measured against the naive reading of §4 — a leaf's text is
`&src[range.start..range.end]` — over the 1167 inputs where the structure
agrees: **4,419 leaves compared, 1,319 differ (29.9 %), in 211 of the 1167
cases.** By leaf kind:

| Kind | Differing | Mechanism |
|---|---:|---|
| `table.cell` | 924 | trim, and `\|` unescaped |
| `code-block` | 263 | indented: the block indent stripped per line |
| `setext-heading` | 51 | the underline moves to `meta` |
| `paragraph` | 50 | container prefixes stripped; own indent kept |
| `atx-heading` | 18 | reconstructed, so runs of spaces collapse |
| `thematic-break` | 11 | `raw` minus trailing newlines, so leading indent kept |
| `html-block` | 2 | container prefixes stripped, then trimmed |

**The correct statement is: a leaf's text is its content with block and
container syntax removed, and inline syntax untouched.** That is a
*reconstruction*, per leaf kind, and it is the second half of the mapping layer
C1 asks for. → **D2**.

Two consequences worth stating now rather than discovering in M3:

- **A leaf's text has no source range.** `mt_inline`'s byte offsets are offsets
  into the block's text — which is M1's D1 as written, so nothing changes
  there — but there is no free mapping from a token's `range` back to a
  document offset. M4's caret needs one and it is not the identity. Recorded in
  §10.
- **This is why C4 is true.** The reason the three registered inline
  divergences are invisible to `cargo xtask diff` is not an accident of the
  harness; it is this correction. A block-state comparison compares strings of
  unparsed inline source.

### C3 — `renderToStaticHTML` is markdown → HTML, not `Document` → HTML

§4's table says:

> | `Document` → HTML | Port `renderToStaticHTML.ts`, sanitize with `ammonia`. |

`renderToStaticHTML.ts` takes a **markdown string**. It calls
`getHighlightHtml(markdown, …)`, which builds a `Marked` instance with
`markedHighlight`, `cjkEmStrong`, `emoji`, and conditionally `math`,
`superSubScript` and `footnote`, and returns `marked.parse(src)`. It never
constructs a `TState[]`, never touches `MarkdownToState`, and never touches the
inline tokenizer M1 ported. The direction in the table is wrong, and so is the
implication that the conformance ratchet measures the same pipeline the
differential harness does.

**The Rust signature is already right**, which is the thing that makes this a
correction to the document rather than to the code:
`mt_md::render_to_static_html(&str, Options, bool)` takes markdown. What has to
be decided is what it does *internally*, and the choice is real:

- **Through `Document`** — one parse, one tree, and the HTML exporter is a
  function of the model the editor actually holds. Architecturally right, and
  it **guarantees** the conformance number differs from muya's, because it is a
  different pipeline: anything `MarkdownToState` normalises away (C2's seven
  mechanisms) is gone before the renderer sees it.
- **A second, direct path** — reproduces the reference's shape and its number,
  and ships a second block parse of every document plus a renderer with no
  consumer inside the application.

**Decided in favour of `Document`** — see D5, which is where it bites, because
it determines what re-baselining `expected-failures.json` is actually
measuring.

### C4 — "the differential test agrees on 100 % of the corpus" is a statement about blocks only

§9's M2 gate and §11.2 both read as though one harness covers the port. It does
not, and C2 is why: `cargo xtask diff` compares `TState[]`, in which a leaf
block's text is **raw markdown source**. Every inline construct in the corpus
is, to that harness, a string.

Concretely: all three entries in `spec/divergences.json` — the nested-emoji
boundary, the unanchored disallowed-tag match, the foster-parented
`getAttributes` element — **cannot appear in `cargo xtask diff` at all**, in
either direction. That is not a gap in the harness; a block-state comparison
has no tokens in it.

So M2.md states which harness is evidence for what, and §6's gates are written
against the right one:

| Claim | Harness | Runs |
|---|---|---|
| Block structure and metadata match muya | `cargo xtask diff` (§11.2) | every commit, 22 files |
| Leaf text matches muya | `cargo xtask diff` — a leaf's `text` **is** the comparison | every commit |
| **Inline tokenization** matches muya | `cargo xtask divergences` (M1 S7) | every commit, 4,264 inputs; 41,009 nightly |
| The HTML matches the CommonMark/GFM spec | `cargo xtask conformance` (§11.1) | every commit, 1,324 examples |
| Round-trip is a fixed point | `mt-md`'s property tests | every commit |

## 5. Decisions to make before writing code

### D1 — adopt `pulldown-cmark`, with the mapping layer as a deliverable **← decided**

C1 measured it. 86.8 % of the block-name tree agrees before any mapping work,
every residual disagreement is one of four named mechanisms, and **not one is
the parser putting a block boundary somewhere `marked` does not**. The
alternative — porting `marked`'s block lexer — is a from-scratch
reimplementation of a third-party library whose behaviour is defined by its own
test suite rather than by muya's, and it is the M2 analogue of the
hand-written-scanners option M1's C1 rejected for the same reason: it makes the
highest-risk component a rewrite on day one.

`pulldown-cmark`, then, and `mt_md::block` is where the four mechanisms live:
refdef recovery (D3), empty-container synthesis, `compatibleTaskList`'s
splitting, and per-leaf text reconstruction (D2). The mapping layer also
recovers every `meta` field `pulldown-cmark` does not carry — heading style,
fence length, bullet marker, ordered delimiter, looseness, cell alignment — by
re-reading the block's source range, which is why S1's gate is stated over
`meta` and not only over names.

*Caveat to check in S1, stated the way M1's C1 stated its own:* the
measurement compared **names**, and the four mechanisms were identified from
the residual. A fifth mechanism hiding inside a case where the names happen to
agree would not have shown up. S1's gate is the same comparison over the full
`TState` JSON, which is what would surface it — and if one appears, it is a
register entry (D4) like any other.

### D2 — where leaf text comes from **← decided**

Not from a source range (C2). Per leaf kind, from the block's source range with
its own syntax removed:

| Kind | Rule |
|---|---|
| `paragraph`, `html-block` | strip each line's container prefix (`>`, list continuation indent); keep the block's own leading indent |
| `atx-heading` | **reconstruct**: `'#' × level`, one space, the heading content with the optional closing sequence removed |
| `setext-heading` | the content lines only; the underline goes to `meta.underline` |
| `code-block`, indented | strip four spaces (or one tab) from every line |
| `code-block`, fenced | the lines between the fences, verbatim |
| `thematic-break` | the source line, minus trailing newlines |
| `table.cell` | trim, and resolve `\|` → `|` |
| `math-block`, `frontmatter` | trim |

Two things this decision is *not* free to get wrong, both from M0:
`CodeBlock::info` is the whole info string and `meta.fenceLength` is **omitted,
not null**, when the fence is three backticks.

**The prefix stripper is the piece with no counterpart in `pulldown-cmark`.**
It is the same operation for a block quote and a list item, it composes (a
paragraph inside a list inside a block quote strips both), and it is the one
part of D2 that is a scanner rather than a rewrite. Write it once, in
`mt_md::block`, and test it against muya directly — S2's gate is exactly that.

### D3 — reference definitions: scan for them, do not read `RefDefs` **← decided**

C1 measured why: `RefDefs` is keyed by case-folded label, so duplicates
collapse and the second definition is unrecoverable from `pulldown-cmark`'s
output entirely. ~~A document containing `[foo]: /a` and `[foo]: /b` would lose
a line, silently, on the first save.~~ — **see the correction below.**

#### Correction at S1 — the reproducer is real and the conclusion drawn from it is not

The measurement in C1 is of `pulldown-cmark`, and it holds: `RefDefs` really
does collapse `[foo]: /a` and `[foo]: /b` into one entry with one span. What
was never checked is the other half of the sentence — *what muya does with the
same input* — and asked directly, it does the same thing:

```text
"[foo]: /a\n[foo]: /b\n\n[foo]\n" → ONE paragraph, "[foo]: /a"
"[FOO]: /a\n[foo]: /b\n\n[Foo]\n" → ONE paragraph, "[FOO]: /a"
```

`marked`'s `def` branch is explicit about it:

```js
} else if (!this.tokens.links[token.tag]) {
    this.tokens.links[token.tag] = { href, title };
    tokens.push(token);          // ← only when the label is new
}
```

So "muya emits two paragraphs" is wrong, there is no data loss to point at,
and **the duplicate collapse is a rule the port must reproduce rather than a
reason to avoid `RefDefs`.** It is reproduced, document-globally — `tokens.links`
belongs to the `Lexer` and a nested `blockTokens` call for a list item shares
it — and `mt_md::block::scan_definitions` carries the two inputs above as
tests.

This is the same failure the milestone has now catalogued five times: a
conclusion that was internally consistent, read plausibly, and had not been
checked against the thing it described. It is recorded rather than quietly
edited, per §0's convention.

**The decision itself survives, on two measured reasons and a third.** They are
about *position*, not about loss:

1. **Tree position.** A definition inside a block quote belongs to the block
   quote (`cm#218`), and `RefDefs`' span for `> [foo]: /url` is `2..13` — the
   `> ` is excluded, so the span does not say which container it came from.
   C1 measured this and it holds unchanged. Scanning per container gets tree
   position for free.
2. **A definition after a paragraph is absorbed into it** — the `marked` branch
   above, first arm: `lastToken.raw += '\n' + token.raw` when the previous
   token at that level is a paragraph or text. So `text\n[foo]: /a` is **one**
   paragraph, and a `RefDefs`-driven port would emit a block muya does not
   have. This one is new at S1 and it is stronger than the duplicate argument
   ever was, because it is a disagreement `RefDefs` *causes* rather than one it
   merely fails to prevent. It also falls out for free from the scan:
   `pulldown-cmark` keeps both lines in one paragraph too, so there is no gap
   for the scanner to find.
3. `RefDefs` is a map. Its iteration order is not document order.

A fourth, minor: `marked` normalises a label with `toLowerCase()` and
`/\s+/g → ' '`; `RefDefs` uses Unicode case folding. The two collapse sets are
not the same one.

So `mt_md::block` recognises a definition line itself and emits the
`Paragraph` muya emits. Two things follow that are worth deciding here rather
than discovering:

- The scan must run **in tree position**, not as a pre-pass over the document,
  because a definition inside a block quote belongs to the block quote
  (`cm#218`). `pulldown-cmark`'s span for that case excludes the `> `, which is
  a second reason not to use it.
- The **label map** the inline tokenizer needs (`mt_inline`'s `labels`) is
  built from these paragraphs, by the same rule muya uses
  (`collectReferenceDefinitions`, a regex over paragraph text) — *not* from
  `RefDefs`, or the two would disagree exactly where the register does.

  **Built at S3, in `mt_md::labels`, and the two scanners disagree on
  purpose.** `scan_definitions` decides where a paragraph *is* and normalises a
  label with `toLowerCase()` **and** `/\s+/g → ' '`, dropping a repeat
  entirely; the label pass decides what a label *points at*, normalises with
  `toLowerCase()` only, and lets the last write win. muya has both and they
  disagree; unifying them is the obvious cleanup and it is the wrong one. The
  module docs put the two side by side, and `[foo bar]: /a` versus
  `[foo  bar]: /a` is the input that separates them.

### D4 — the block-structure divergence register **← decided**

M1 built the mechanism and `spec/README.md` states the rule: *"Three registers,
one shape, on purpose. If you change how one of them decides, change the other
two or write down why not."*

M2 will produce disagreements that are deliberate — anywhere `marked` and
CommonMark differ and the port follows CommonMark. **Those go in
`spec/divergences.json`**, with an added `layer` field (`"inline"` | `"block"`)
so `cargo xtask divergences` and `cargo xtask diff` can each run the entries
that are theirs. One register rather than two, for the reason `spec/README.md`
already gives, and because M1's negative control — *run the register's own
inputs and fail if none of them disagrees* — is the part that makes a green run
mean anything, and it should not have to be built twice.

The four rules carry over unchanged, including rule 3 (an entry with no failing
case is **stale** and fails the build) and rule 2 (every entry names inputs
that become tests). Rule 1 is what makes the M2 gate honest: *a disagreement on
a registered input is expected; a disagreement on anything else is a failure.*

**And the M2 exit gate is restated against it.** §9 says *"differential test vs.
TS engine agrees on 100 % of the corpus"*. Read strictly that forbids the
register, which would mean reproducing `marked`'s block bugs bug-for-bug — the
opposite of what M1's D3 decided for the inline layer, and for weaker reasons,
since here the "bug" is a third-party library's disagreement with the spec the
project is being measured against. **The gate is read as: every corpus file
either agrees or is a registered divergence, and the register is machine-checked
in both directions.** That is the same reading M1 gave its own gate and it is
stated here so it is not a surprise at the end.

### D5 — re-baselining `spec/expected-failures.json` — the one-way door **← decided**

`spec/README.md` step 1: *"Regenerate it from actual results, and read the diff
carefully — you are choosing the floor, and the floor can never be raised
again."* Three things about that instruction have to be settled before it is
followed, because it is written as though the same engine is being measured
twice and it is not.

**1 — the inherited list is a different pipeline's list.** C3: the 78
CommonMark and 90 GFM entries are `getHighlightHtml`'s failures — `marked`'s
renderer plus Prism plus DOMPurify. The Rust engine renders from `Document`,
which was built by `pulldown-cmark` and normalised by D2. **The new list will
differ in both directions and there is no reason to expect an inclusion either
way.** Regenerating is not adjusting a baseline; it is measuring a new engine
for the first time, against fixtures that happen to be the same.

**2 — the slack is two examples, and that is not slack.** `spec/README.md`
records 88.0 % achievable against an 87.7 % floor, and 86.6 % against 86.3 %. A
list two entries longer than the inherited one already fails the gate. Since
the new list is a *different set*, the constraint that actually binds is its
**length**, not its overlap.

So the rule for M2, stated before the numbers exist so it cannot be chosen to
fit them: **the regenerated list may be no longer than the inherited one — 78
and 90 — unless each additional entry is argued individually in the same
commit.** Blanket regeneration to whatever fails is what the ratchet exists to
prevent, and `cargo xtask conformance`'s floor check is a backstop rather than
a review (`spec/README.md` says so).

**3 — `floor_percent()` is raised in the same commit.** The floor is a constant
in `conformance.rs` (87.7 / 86.3) and the list is the thing regenerated; leave
the floor alone and the two drift apart, so that a later regression can eat the
whole margin between the measured rate and the inherited floor without the
backstop firing. After re-baselining, the floor becomes the **measured** rate.
That is what makes "compliance only goes up" true of the number as well as of
the list.

`spec/conformance.md` is rewritten in the same commit, per step 3 — and its
inherited inconsistency (prose says 80 / 92, JSON lists 78 / 90) is fixed then,
since the reason to copy it unchanged expires the moment it stops describing
muya.

### D6 — the three ratchets must not flip on the same day **← decided**

`mt_md::parse`, `serialize`, `render_to_static_html` and `dump_state` all return
`Err(Unimplemented)`. The conformance runner maps that to `Skipped`, the
block-state differential maps `mt-cli`'s exit 3 to `SKIP`, and
`conformance::tests::every_suite_is_skipped_at_m0` is built to fail the day it
changes. **The first `Ok` turns all three on at once**, with no flag and no
code change — which is M0 decision 7 working as intended, and also a lot of red
arriving together with no way to tell which harness is complaining about what.

**Stage it by entry point, in this order**, which S3, S4 and S5 implement:

| Order | Entry point | Harness that wakes up | Why here |
|---:|---|---|---|
| 1 | `parse` + `dump_state` | `cargo xtask diff` | Finest-grained failure message in the repository — `first_difference` reports a JSON path like `[3].children[0].meta.lang`. Wake this one alone, against 22 files, and every disagreement names its own field. |
| 2 | `serialize` | the round-trip property | Needs `parse`; adds `parse ∘ serialize ∘ parse` as a fixed point. Nothing else changes. |
| 3 | `render_to_static_html` | `cargo xtask conformance` | The one-way door (D5). It goes last, when the model underneath it is already agreeing with muya file by file, so a conformance failure is about the renderer rather than about the parse. |

`dump_state` cannot be staged before `parse` — it is `parse` plus a serializer —
so the first row is one step, not two.

### D7 — §4.1's incremental reparse is a shape decision, and it comes before `Edit` **← decided**

§4.1 reads as an optimisation:

> 1. Re-tokenize **only the edited block**, mark it layout-dirty.
> 2. If the edit introduces a block-boundary trigger […] re-run block parsing
>    over the **minimal enclosing region** […] and diff the resulting subtree
>    against the existing one.
> 3. Full document reparse only on load and on external file change.

It is not. Each step is a requirement on types this milestone writes:

- **Step 1 requires that a leaf's text be self-contained**, so that
  re-tokenizing it needs nothing from its neighbours. C2 says it is — a leaf's
  text has its container syntax already removed — so `Edit::SpliceText { node,
  at, remove, insert }` as written is sufficient, and this is the one step that
  costs nothing.
- **Step 2 requires that block parsing be runnable over a sub-region and that
  its output be *diffable* against the existing subtree.** Diffable means nodes
  that survive the reparse keep their `NodeId`, or every cached layout below the
  edit is thrown away on every `#` typed at the start of a line. That is a
  requirement on the arena, not on the parser. → D8.
- **Step 3 is the only one that is free.**

And the dirty set has to distinguish two kinds of staleness, which
`DirtySet::mark(NodeId)` as written cannot: *this leaf's text changed*
(re-tokenize and re-lay-out one block) and *this subtree was replaced*
(everything below is new). `mt-layout` will ask, and adding the distinction
after `Edit::apply` is written means revisiting every call site.

**So D7 is settled before `edit.rs`,** and its concrete outputs are: `DirtySet`
holds `(NodeId, Dirt)` where `Dirt` is `Text | Structure`; `Edit::apply` marks
`Text` for `SpliceText` and `SetMeta` and `Structure` for the other four; and
`mt_md` exposes a reparse entry point that takes a region rather than only a
document. S6 is where the region reparse is written; the *types* it needs land
in S0.

### D8 — the arena, `NodeId`, and `ropey` **← decided**

M0 decision 4 left three placeholders for M2. All three fall due here and D7
decides two of them.

- **`NodeId` becomes generational.** M0 wrote *"whether generational indices
  are needed to catch a `NodeId` used across an undo boundary"* is the open
  question; D7 adds a second and sharper one — an incremental reparse recycles
  slots, and a stale `NodeId` held by `mt-layout`'s cache would then silently
  address a *different block* rather than panicking. A generation counter turns
  that into a `None`. The cost is 4 bytes per handle in a structure with one
  entry per block.
- **Hand-rolled, not `slotmap`.** Insert, remove, get, and a free list with a
  generation counter is a small amount of code with no behaviour of its own,
  and M0 already wrote the shape. The dependency policy is that deps land with
  the milestone that needs them; `ropey` below is a dependency `mt-doc`
  genuinely needs and this is not. Revisit if the arena ever shows up in a
  profile, which it will not — there is one entry per block.
- **`Text::Rope(Rope)` becomes `ropey::Rope`.** The newtype was written so this
  is a body swap with the enum untouched (M0 decision 4), and `ropey` is the
  first real dependency `mt-doc` takes. Promotion threshold stays 8 KiB as
  §2.1 writes it; the demotion direction is deliberately **not** implemented —
  a block that was once large stays a rope, because oscillating at the
  threshold is worse than a few extra ropes.

### D9 — the CRDT deferral **← confirmed at M2 start, as §9 requires**

§2.2: *"muya's `ot-json1` + `ot-text-unicode` layer is not carried forward. The
`Edit` enum is deliberately shaped as discrete invertible ops so a CRDT (`loro`)
can be slid underneath later without redesigning the model. **This is the one
deferred-architecture bet in the plan; make it consciously.**"

**Confirmed: deferred.** The argument, since "make it consciously" asks for one
rather than for agreement:

- **The bet is cheap to hold and expensive to take now.** What keeps the option
  open is that every mutation is a discrete invertible op over `(NodeId,
  offset, len, text)`. That is already what `Edit` is, for undo — §2.2's shape
  is not a concession to a future CRDT, it is what an invertible undo stack
  requires. So holding the option costs **nothing extra** in M2, and this
  confirmation is really a constraint on M3–M5: no edit path may bypass
  `Document::apply`.
- **Taking it now would change the model.** `loro` under the document means
  every leaf's text becomes a CRDT text, which is the `Text` enum's
  representation, which is `mt-layout`'s input, which is M3's whole surface.
  §9's critical path is M2 → M3 → M4 and none of M3/M4/M5 needs it.
- **v1 does not ship collaboration.** §10's ship list has no multi-user
  feature, and §10's *non-negotiable* list is CJK IME, screen readers and
  lossless round-trip — all three of which lose engineering time to this if it
  is taken now.

**What the confirmation costs, stated so it is not free:** if collaboration is
ever taken, the undo stack has to be reconciled with CRDT undo (per-site undo
is not "pop the inverse batch"), and that is a redesign of `history` rather than
of `Edit`. Recorded here so the bet's actual price is on the record rather than
"we kept the option open".

## 6. Stages

Each stage ends with a gate that can be checked by running something. S0–S2 are
sequenced by dependency; S3–S5 are D6's staging order and must not be reordered.

| # | Stage | Gate |

### The two things S3 was asked to settle before any code

#### 1 — what `parse` returns: a `Parsed`, and the ranges live beside the document rather than in it

§10's corrected owed item falls due here. The constraint is hard: `Block` maps
1:1 onto the TypeScript `TState` union,
`block_names_match_typescript_union_one_to_one` is the machine-checked form of
it, and the §11.2 harness depends on it — so a range cannot live on a `Block`.
The three candidates were a side table on `Document`, a second return value, or
nothing again.

**Decided: `parse` returns `mt_md::Parsed { document, labels, source_map }`,
and it is infallible.**

The argument against the side table is the one that decided it, and it is not
about where the field would fit. **A `Document` outlives its parse and no
`Edit` maintains a range.** Hang the map on the document and the first
`SpliceText` makes it lie, silently, with no mechanism that could ever have
kept it true — which is a worse thing to ship than no map at all. Ranges are a
fact about one parse; the return value of the parse is where a fact about the
parse belongs.

The argument against a second entry point ("`parse`, and `parse_with_ranges`
for callers who care") is that it forks the only parse path in the crate so
that the interesting half can be forgotten. `Parsed` costs a caller
`.document` and nothing else.

**And the risk of taking it is the one this milestone keeps recording:** an API
with no caller until M4 is not a check. So the map is checked rather than
merely shipped, in three places —
`tests/source_ranges.rs::every_node_has_a_range_and_the_ranges_nest` walks
every corpus document at both option sets and asserts that every live node
carries a range, that a child's range is inside its parent's, that siblings are
in document order, and that every range is a valid slice;
`the_map_has_exactly_one_entry_per_live_node` pins completeness; and
`block::tests::the_stripper_is_re_runnable_from_src_tree_and_ranges` **runs
S2's argument**. That last one is the point of the whole decision: S2 claimed
the container half of §10's reverse map is not lost, *"because the prefixes are
computable from the ancestors' source ranges"*, and until S3 that was an
argument. It now rebuilds a block quote's `Prefix` from the quote's range
alone and re-derives the inner paragraph's text with `strip_lines`.

What the map does **not** claim is stated on the type: the per-kind half is not
free from it and never will be. An atx heading is rebuilt from scratch, a code
block loses columns after stripping, a table cell is trimmed and unescaped;
each needs its own inverse and each belongs beside its rule.

**One consequence for M4, recorded now because it is cheap now and expensive
later:** the ranges index the string `parse` was given. `mt-cli` normalises
CRLF before calling it (see the traps below), so a range from a file read
through the file layer indexes the *normalised* text, not the bytes on disk.
That is muya's shape too — its file layer normalises and its parser does not —
but a caret that maps back to a file offset has to know it.

#### 2 — where the label map lives: in `mt-md`, run once per parse, typed as `mt_inline::Labels`

muya rebuilds it inside `patch()` — a full depth-first traversal of the
document's state on **every block render**, which is a keystroke. Noticed, not
copied: `parse` builds it once and `mt_md::labels::collect` is public, so an
editor that has just changed a definition can redo it deliberately rather than
on every frame. That is the whole of the difference and it costs nothing to
take.

**The dependency edge is real and it is taken: `mt-inline` stops being a
dev-dependency of `mt-md` and becomes a dependency.** What decided it was not
the `Labels` type but the *regex*.
`beginRules.reference_definition` is already transcribed in `mt-inline`, with
its `\9` backreference and its backtrack limit, because the tokenizer needs it
as a begin rule. The alternative — a `Labels` owned by `mt-md` and converted at
the boundary — buys nothing and costs a **second transcription of that rule**,
which is the "two scanners" mistake §5 D3 spends a section on, in the one
costume where the two really would have to agree.

**What it costs `cargo xtask deps`: nothing measurable, and §1 still holds.**
The runner reports **14 crates** before and after, because `mt-inline` was
already in the workspace graph and the edge is downward —
`mt-doc → mt-inline → mt-md → mt-layout` is §1's own order, and `mt-md`'s crate
doc has said *"on `mt-inline` once inline re-derivation lands"* since M0. §1's
purity constraint is about `src/`, and `mt-inline` is the crate the plan calls
pure. The guard did fire once during this stage, for an unrelated reason and
correctly: a range invariant test that read the corpus was written in
`src/block/tests.rs`, and `deps` failed the build with *"mt-md does no I/O …
move it to an integration test"*. It moved.

**The pass is `getLabelInfo`, not the tokenizer, and the difference is one
line.** `consumeBeginRules` gates the `reference_definition` *token* on
`isLengthEven(def[3])` — an odd run of backslashes escapes the `]` — and
`getLabelInfo` reads the raw capture groups with no such gate. So `[a\]: /x`
produces no token and does define the label `a\`. `mt_inline::label_info` is
the new public function that runs the rule the way muya's label pass runs it,
and every expectation in its tests was measured against the running engine.
Three of them are not what reading the pattern suggests: a parenthesised title
defeats the **whole** rule (`[a]: /u (t)` matches nothing, because `\9` closes
the title with whatever opened it), `^`/`$` are not multi-line so a paragraph
holding a definition *and* anything else defines nothing, and trailing spaces
after a bare href leave muya's `title` as a single space.

### The two things S2 was asked to settle before any code

#### 1 — the stripper subsumes `content_start` and `LogicalText`, and both are re-based on it

The brief's warning was that promoting S1's two detection helpers is the obvious
move and is wrong. It is, and the reason is sharper than "they are approximate":
**they are approximate in the direction that deletes content.** `content_start`
strips *all* leading whitespace and *every* `>` on a line. A reference
definition's own ` {0,3}` indent is part of `Tokenizer.def`'s `cap[0]` and
therefore part of the paragraph muya emits — so `  [foo]: /a` has text
`"  [foo]: /a"`, and the helper that was fine for *finding* the `[` produces the
wrong text by two characters. The same for `> > a` at depth one, where the
second `>` is content.

**They are deleted rather than kept beside the real stripper**, and
`LogicalText` is rebuilt on `strip_lines`. The alternative the brief warns about
— two almost-identical scanners — was never the choice; the choice was between
deleting them and *keeping* them, and keeping them would have meant the def scan
and the leaf text disagreeing about where a line's content starts, in a codebase
where those two answers must be the same or the definition's paragraph has a
range that does not match its own text.

What the detection callers lose by using the exact answer: nothing. Both of them
— `definition_head` and `block_math` — begin by skipping ` {0,3}` themselves,
because `marked`'s rules do.

#### 2 — the reverse offset map: §10's premise does not hold, and the owed item is a different thing

§10 says a per-leaf mapping from block-text offsets back to source offsets
*"has to be built where the reconstruction happens, in `mt_md::block`, because
that is the only place both sides are known."* Having written the
reconstruction, **that is not true, and the useful part is why.**

The stripper does produce the map for free: `StrippedLine` carries
`source_start` per line, and a block-text offset inside line *i* is
`source_start + (offset − line_start)`. But two things fall out of building it:

- **It is only the map for the kinds whose text *is* the stripped lines.**
  An atx heading is `'#'×level + ' ' + content` — a rebuild with no
  correspondence to reconstruct. A code block loses one to four columns per
  line *after* stripping. A table cell is trimmed and unescaped. A task item's
  first paragraph loses a four-character prefix. Each of those needs its own
  inverse, and each inverse belongs with the rule — so the "free by-product" is
  the container half only, and the per-kind half is a second implementation of
  D2 whichever stage writes it.
- **The container half is not lost by deferring it.** `strip_lines` needs two
  things: the source lines, and the ancestor containers' prefixes. The
  ancestors are the tree, which `Document` has. The prefixes are computable
  from the ancestors' *source ranges* — `Prefix::Quote` from the quote's first
  line, `Prefix::Item` from the item's. So the whole stripper is re-runnable
  for one block at a time, lazily, from `(src, tree, ranges)`.

**So what is owed forward is the per-node source ranges, not a per-leaf offset
map**, and that is a smaller and more useful thing: it is one side table rather
than a map per leaf, it is lazily consumable rather than eagerly built for
documents that never see a caret, and it is exactly what an incremental reparse
(D7/S6) wants anyway.

**Deferred, deliberately, and it is not the mistake §10 warns about.** §10's
mistake is the one where a thing becomes unbuildable because the information
that made it cheap is gone. Here the information is `Built::range`, and the
place it is dropped is `to_document` — three lines away from where `parse`'s
signature is decided, at S3. Building a public ranges API *now* would be an API
S3 immediately reshapes, and an API with no caller until M4 is the shape this
milestone has repeatedly found out is not a check. §10 is rewritten below to
say ranges rather than a map, and S3's row carries it.

### `marked`'s source is not minified, and three of S2's rules came from reading it

The brief describes `marked`'s bundle as *"minified, and `node -e` against a
`new Lexer()` is how S1 read its rules when the bundle was unreadable."* The
bundle is minified. **It ships `lib/marked.esm.js.map` with `sourcesContent`**,
so `Tokenizer.ts` (30 KB), `Lexer.ts`, `rules.ts` and `helpers.ts` are all
recoverable in full, in the original TypeScript, for the exact version muya
resolves (18.0.5).

That changed the method for the whole stage. Three rules would have been very
hard to find by probing and are two lines each in the source:

1. **`codeRemoveIndent`'s alternation is ordered.** `/^(?: {1,4}| {0,3}\t)/gm`
   — ` {1,4}` is greedy and tried first, so `"  \tfoo"` loses its two spaces
   and keeps its tab, and the `{0,3}` in the second arm can only ever be zero.
2. **`indentCodeCompensation` requires backticks.** `/^(\s+)(?:```)/` on the
   raw, so an indented `~~~` fence never compensates and an indented ```` ``` ````
   one does.
3. **`Tokenizer.list`'s `indent > 4 ? 1 : indent`**, which is what makes
   `1.      indented code` an indented code block holding `" indented code"`
   with exactly one leading space.

The probing did not stop — every rule here has a measured reproducer, and two
of the readings were wrong until the engine said so. But reading first turned a
search into a transcription. **`node -e` against a `Lexer` is the right tool
for "what does this do"; the sourcemap is the right tool for "why".**

### S2 registers nothing either, and `table.cell` is why that is a result

The brief expected `table.cell` to be *"the biggest class and the likeliest
register entry in the milestone"* — 924 differing leaves, and `marked` resolving
the `\|` escape into a literal `|`. It is not a divergence, and the reason is in
muya's own comment beside the code:

> Store the cell text as marked emits it (with the table `\|` escape already

> escaped `` `\|` `` inside inline code (#4849). `escapeText` re-adds the `\|`
> escape on serialization, keeping the markdown round-trip intact.

That is a **deliberate, documented, round-trip-safe** decision with the issue
number on it, and reproducing it is one `.replace("\\|", "|")`. A register entry
is for where the port *chooses* to disagree with muya (D4 rule 1), and there was
no choice to make: agreeing was cheaper than disagreeing and lossless either

### The fifth mechanism §4 C1's caveat asked about — there were three

D1's caveat: *"the measurement compared **names** … a fifth mechanism hiding
inside a case where the names happen to agree would not have shown up. S1's
gate is the same comparison over the full `TState` JSON, which is what would
surface it."* It surfaced three, all in `meta`, and none of them was
registrable — each is a field the port was simply getting wrong.

**1 — `meta.underline` is the literal run, and `mt_doc::Underline` could not
hold it.** `types.ts:18` declares `underline: string` and comments
`// "==="|"---"`; M0 transcribed the comment. `walkTokens` writes the whole
matched run, so muya's answer for `Hello world\n===========` is
`"==========="`. A two-value enum can only answer `"==="`, which is a
**round-trip data loss** on any underline that is not three characters — and
25 of the 652 CommonMark fixtures and 25 of the 672 GFM ones contain one. §10
marks lossless round-trip non-negotiable, so this is a fix: `Underline` is now
`Equals(u32) | Dashes(u32)`, and the four transcribed spec cases that inherited
the same error are corrected with the reason on them. The TypeScript spec
asserts only `expect(states[0].meta!.underline).toBeTruthy()`, so the
tightening was the transcription's own and so was the error.

**2 — `meta.lang` must be read from the source, not from the event.**
`pulldown-cmark` resolves HTML entities in a fence's info string, so
```` ```f&ouml;&ouml; ```` arrives as `föö`; `marked` keeps the source text and
muya's `meta.lang` is `f&ouml;&ouml;` (`commonmark#34`, `gfm#330`). It does
apply `anyPunctuation` — `/\\([\p{P}\p{S}])/gu → '$1'` — so a backslash escape
*is* resolved (`commonmark#24`, `gfm#320`). Constraint 1 on
`Block::CodeBlock::info` says never to normalise that field and a decoded
entity is a normalisation, so the info string is re-read from the block's first
line and unescaped explicitly.

**3 — looseness has an asymmetry `marked` gets from an ordering accident, and
it is 23 of the 1344.** `Tokenizer.list` sets a flag when an item's raw ends
with a blank line and lets the *next* iteration turn it into `loose`; the last
item has no next iteration, and `marked` then trims that item's raw outright.
So **a trailing blank line after a list's final item does not make the list
loose** — which is the shape of every ordinary document: a list, a blank line,
then a paragraph. `pulldown-cmark` includes that blank line in the last item's
range, so the naive reading says loose and muya says tight, in one direction,
19 times at the top level and 4 more in a nested list.

None of the three is a divergence: all three are the port disagreeing with muya
by accident, and all three are fixed. That is what the caveat was for.

### Three decisions S0 had to take that §5 does not cover

Recorded here rather than in a commit message, because each is a shape later
stages inherit.

**1 — the document root is not a `Block`, and cannot be.** §2 sketches
`Node { parent, block: Block }`. `Block` maps 1:1 onto the TypeScript `TState`
union; `TState` is what an *array* of top-level blocks is made of and has no
root member; and adding a twentieth variant would fail
`block_names_match_typescript_union_one_to_one`, which is the precondition for
the §11.2 harness. So `Node`'s body is `Root { children } | Block(Block)`.

This is not an invention: **muya's own tree is rooted at `ScrollPage`**
(`block/scrollPage.ts`), whose `blockName` is `scrollpage` and which likewise
has no `TState` member. The port models what the reference engine does. M0's
reason for keeping `children` inside `Block`'s container variants survives —
children still live in exactly one place per node kind.

**2 — `Block::meta()` returns `Option<BlockMeta>`.** M0 wrote it as
`-> BlockMeta`, and `BlockMeta` deliberately has no variant for the seven
blocks whose TypeScript interface carries no `meta` object ("there is nothing
to set"). The original signature was unimplementable for seven of nineteen
variants. `Option` also makes `Edit::SetMeta` on a paragraph a clean
`MetaMismatch` rather than a fabricated empty meta.

**3 — `Edit::RemoveNode`'s inverse is `MoveNode`, not `InsertNode`.** Found by
the property test rather than by reading, which is the whole argument for
having written the property test first.

`RemoveNode`'s M0 doc comment says its inverse is `InsertNode` "carrying the
removed block back". That fails in two compounding ways:

- `InsertNode` carries **one** `Block`, and a container `Block` holds
  `Vec<NodeId>`. Restoring a subtree needs those ids still live, so removal
  cannot free the descendants.
- `InsertNode` mints a **new** id. So the batch
  `[SpliceText { node: x }, RemoveNode { node: x }]` inverts to
  `[InsertNode(…), SpliceText { node: x }]`, and by the time the splice is
  undone `x` is stale and the undo fails. That is not a contrived batch: any
  edit that rewrites a block and then merges it away has that shape.

So **`RemoveNode` detaches**: the node and its subtree stay in the arena with
the node's `parent` cleared, and the inverse is `MoveNode` back to the old
`(parent, index)`. The node keeps its id, which makes an apply-then-undo pair
restore the `NodeId`s and not merely the content — a **stronger** guarantee
than §2.2 asks for, and the one `mt-layout`'s cache will want at M3. §2.2's
enum shape is untouched, so D9's bet is intact.

The price is that a detached subtree is reachable only from the undo stack.
`Document::prune_detached()` reclaims it, and its doc comment names the only
legitimate caller — M4's history trimming, the one place that knows an inverse
has been dropped. The property test calls it after every undo and asserts the
arena returns to its pre-batch size, so the cost is bounded by the undo stack
rather than unbounded.

## 10. Owed forward

### Owed to M3/M4 — block text has no document offset

C2's consequence, recorded here because the layer that needs it does not exist.
A leaf's `text` is a reconstruction, so a token's `range` — a byte offset into
that text — does not map to a document offset by addition. Anything that needs
the reverse direction (caret placement from a click, a search hit's position in
the file, an error message with a line number) needs a per-leaf mapping from
block-text offsets back to source offsets, ~~and it has to be built where the
reconstruction happens, in `mt_md::block`, because that is the only place both
sides are known~~ — **see the correction below.** Recorded on `Block::text`'s
docs as well as here.

#### Corrected at S2 — the thing that is owed is the per-node source ranges

Written before the reconstruction existed; having written it, the premise is
wrong in a way that makes the owed item **smaller**. The argument is in §6's
"the two things S2 was asked to settle"; the short form:

- The map is only a free by-product for the leaf kinds whose text *is* the
  container-stripped lines. An atx heading is rebuilt from scratch, a code
  block loses columns *after* stripping, a table cell is trimmed and
  unescaped — each needs its own inverse, and each inverse belongs beside its
  rule wherever it is written. There is no stage at which that half is free.
- The expensive-looking half — the container prefixes, which need the whole
  ancestor chain — is **not** lost. `strip_lines` needs the source lines and
  the ancestors' prefixes; the ancestors are the tree, and their prefixes are
  computable from their **source ranges**. So `(src, tree, ranges)` is enough
  to re-run the stripper for one block, lazily, at any later stage.

So: **keep the per-node source ranges.** They exist as `Built::range` while
`parse_blocks` runs and are dropped by `to_document`, because `mt_doc::Block`
maps 1:1 onto `TState` and has nowhere to put them. **S3 is where that is
decided**, because S3 is where `parse`'s signature is written; a public
ranges-returning API added at S2 would be an API S3 reshapes and M4 is the
first caller. `block::parse_blocks`'s doc comment carries this so it is
findable from the code.

#### Taken at S3 — the ranges survive, on `Parsed` rather than on `Document`

**`mt_md::parse` returns `Parsed { document, labels, source_map }`**, and
`SourceMap` is a `NodeId → Range<usize>` side table handed back *with* the
document rather than stored *in* it. §6's "the two things S3 was asked to
settle" has the argument; the short form is that a `Document` outlives its
parse and no `Edit` maintains a range, so a side table on `Document` would be a
field whose invariant nothing could ever keep. `block::parse_blocks_with_ranges`
is the function; `block::parse_blocks` still exists and drops them, which is
what `cargo xtask blocks` calls.

**The half that is owed is smaller again, and it is now the *only* half.** The
container half is discharged: `block::tests::the_stripper_is_re_runnable_from_src_tree_and_ranges`
rebuilds a block quote's `Prefix` from the quote's range alone and re-derives
the inner paragraph's text with `strip_lines`, so S2's argument is a passing
test rather than an argument. What remains owed to M4 is the **per-kind**
inverse — an atx heading's rebuild, a code block's post-strip columns, a table
cell's trim and unescape, a task item's four-character prefix — and §10 has
said since S2 that there is no stage at which that half is free.

**One thing M4 has to know that S2 could not have said**: the ranges index the
string `parse` was given, and `mt-cli` normalises CRLF before calling it. A
range from a file read through the file layer is an offset into the normalised
text. muya has the same split — file layer normalises, parser does not — but a
caret mapping back to a file offset has to account for it. See §6's "the trap
nobody named".

### Owed by S1 — three narrowings, each with its reproducer

rule 3 makes an entry with no failing differential case stale, and none of the
three is reachable from any of S1's 1344 inputs. Each says what would close it.

1. **`Options::footnote` does nothing in the block pass.** muya's footnotes are
   its own `marked` extension — `[^id]:` with a 4-space de-indent and a
   recursive lex (`utils/marked/extensions/footnote.ts`, 114 lines) — not GFM's,
   so `pulldown-cmark`'s `ENABLE_FOOTNOTES` is not a substitute and is left off.

   emits a plain `paragraph` for `[^a]: note` and so does the port. ~~**Owed to

### Owed by S3 — three cases that fail for a reason of their own

The delist found what neither S1's gate nor S2's could: **`cargo xtask blocks`'
1344 inputs and `cargo xtask diff`'s 22 documents are not the only denominator,
and the transcribed spec suite reaches inputs neither of them contains.** Three
listed cases now fail because the port disagrees with muya rather than because
an entry point is closed, and
`state_specs.rs::the_only_listed_cases_that_fail_for_their_own_reason_are_the_three_m2_names`
asserts that these are all of them — a fourth appearing fails the build.

**1–2. An empty task marker takes a lazy continuation in `marked` and not in
GFM.** `markdownToState`'s
`parses_an_empty_task_marker_with_lazy_continuation_text_as_a_task_item` and
`keeps_lazy_continuation_text_on_the_final_empty_task_marker`.

```text
"- [ ] \ntext\n"
  muya      task-list › task-list-item › paragraph "text"
  the port  task-list › task-list-item › paragraph ""  +  paragraph "text"
```

The mechanism is one line of `marked` and it is upstream of everything the
mapping layer does: to `marked` the item's content is the string `"[ ] "`,
which is **not blank**, so the item's paragraph stays open and `text` is an
ordinary lazy continuation of it — the `[ ] ` prefix comes off afterwards, in
`strip_task_markers`. To GFM the `[ ]` is a *task-list marker* rather than
paragraph content, so `pulldown-cmark` leaves the item empty and `text` starts
a new block at column 0.

Measured, so the next stage inherits the rule and not the symptom — seven of
thirteen probes differ and the six that agree are the boundary:

| Differ | Agree |
|---|---|
| `- [ ] \ntext` | `- [ ] \n\ntext` — a blank line closes the paragraph |
| `- [x] \ntext` | `- [ ] \n# head`, `- [ ] \n> quote` — a block start is not lazy |
| `1. [ ] \ntext` | `- [ ] \n  text` — indented, already inside the item |
| `- [ ] \ntext\nmore` | `- \ntext` — no task marker, nothing to disagree about |
| `> - [ ] \n> text` | `- a\ntext` — an ordinary lazy continuation, already right |
| `- [ ] \ntext\n- [ ] b` | |

**Not registered** (rule 3: no failing differential case) and **not fixed at
S3**: it is a block-structure disagreement, which is S1's layer, and the fix is
a reproduction of `marked`'s lazy continuation for one shape — the kind of work
this milestone has repeatedly found goes wrong when it is done in passing.
`block::tests::an_empty_task_marker_does_not_yet_take_a_lazy_continuation`
characterizes the current behaviour with muya's beside it and the boundary
pinned, so a fix flips one test deliberately and delists two.
**Owed to S4**, which is the next stage to run and whose round-trip property
reaches the same class.

**3. `Options::footnote` has no block extension.**
`markdownToState::converts_block_level_footnote_tokens_into_footnote_states`
asks for a `footnote` state with `footnote: true`, and muya builds one from its
own `marked` extension (`utils/marked/extensions/footnote.ts`, 114 lines) which
is not ported and is not GFM's. This is the *other* half of §10's S1 narrowing
