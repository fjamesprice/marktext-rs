### What M2 owes M3, and it is three items

§10 of M2.md has exactly three headings that name M3, and **none names M3
alone** — every one is *"M3/M4"*, which is itself worth noticing, because two
of the three are really M4's and M3's job is mostly to not make them worse.

1. **"Block text has no document offset"** (M2.md:4277). A leaf's `Text` is a
   *reconstruction*, not a slice of the source, so a token's byte range does
   not map to a document offset by addition. Narrowed three times across S2,
   S3 and S6: the container half is discharged (`block::prefix_chain` rebuilds
   a `Prefix` chain from ancestors' ranges), and what remains owed is the
   **per-kind inverse** — an atx heading's rebuild, a code block's post-strip
   columns, a table cell's trim-and-unescape. §10 has said since S2 that there
   is no stage at which that half is free. **M4 is still the first caller**;
   see §4 C6 below for the reason M3 nonetheless discovers a second offset
   space of its own.
2. **"The reparse divergences are a class"** (M2.md:4898), described in M2's
   own text as *"the most important item in §10, and the reason M2 closed on a
   red soak."* `mt_md::reparse::Incremental` has disagreed with a full parse of
   its own source on **every fuzz dispatch it has been given** — five distinct
   mechanisms, four repaired, one open and uncharacterised. The instruction is
   in as many words: **do not build on `mt_md::reparse` without re-establishing
   it first.** §5 D5 takes this decision at open rather than deferring it.
3. **"Carried from M1 §10, unchanged"** (M2.md:5064). Two renderer behaviours
   that sit above `mt-inline`'s marker-reveal predicate and exist nowhere yet:
   `header.ts`'s **synthetic marker range** for an ATX heading's `#`s, and
   `htmlTag.ts`'s override that a **childless tag is always revealed**. Plus
   `autoLinkEncoding.spec.ts`'s renderer half (marktext #3548) — an
   `auto_link`'s `href` must be emitted verbatim, never re-encoded. These are
   the first items in this project that are owed to a *renderer*, and M3 is the
   first milestone that has one. They are still not M3's: all three describe
   caret-dependent or HTML-emitting behaviour, and M3 has neither a caret nor
   an HTML output. **They stay owed, and §10 restates them so the fourth
   milestone in a row does not lose them.**

### The one mitigating fact, recorded because it bounds the exposure

M2 §10 notes that `normalize_source` — the file-open path's BOM-strip and
CRLF/CR → LF pass — removes the lone-`\r` inputs that three of the five reparse
mechanisms need. A viewer that opens files through that path is not exposed to
those three. This bounds the risk; it does not make the incremental path
trustworthy, and D5 does not lean on it.

## 1. Scope

**In:** `mt-layout`, `mt-render`, `mt-highlight`, and the smallest possible
shell that makes them a program someone can run.

**Out, and each has a milestone that owns it:** the caret, selection, all edit
commands, undo, clipboard, IME and the AccessKit tree (M4); preferences,
keybindings, session import, the file tree and search UI (M5); math rendering,
mermaid diagrams, PDF export and spellcheck (M6). HTML → Markdown on paste is
M5's, per M2 §10.

**The tension this milestone has to resolve, and it is a real one.** §9 puts
`mt-fs`, `mt-ui` and `mt-app` at M5, and R8 requires M3 to *ship publicly as a
standalone previewer*. A previewer needs a window, a file to open, and a theme
— three things whose crates belong to a later milestone. Resolving this by
quietly building M5's crates early would be scope creep dressed as a gate.
§5 D6 takes the decision explicitly.

**What "read-only" buys, and it is more than it sounds.** No caret means no
marker reveal, no IME, no accessibility tree, no undo, and no incremental
reparse. Four of M2's ten open findings and both of M1's owed renderer
behaviours are caret-dependent and therefore out of M3's path entirely. This
milestone is the one place in the project where the hardest inherited debt can
be routed around rather than paid — and §4 C6 is the one place it cannot.

## 2. What is being ported — and the answer is *almost nothing*

**This is the structural break with M1 and M2, and every other section depends
on getting it stated correctly.** M1 ported a tokenizer. M2 ported a parser, a
serializer and a state model. Both had a reference implementation to be
byte-identical to, a differential harness to prove it with, and a spec suite to
count against.

**muya has no layout engine to port, because the browser was the layout
engine.** What MarkText does is build DOM and let Chromium do line breaking,
bidi, font fallback, shaping, and paint. M3 replaces Chromium. There is no
`layout.ts` to read.

### What the reference actually contains, measured

|---|---:|---|

| `inlineRenderer/**/*.ts` — token → VNode → HTML string | 3,977 | **Not ported.** Replaced by token → parley style runs |
| `utils/snabbdom.ts`, `utils/dom.ts` | 139 | **Not ported.** No vdom, no DOM |
| `assets/styles/*.css` — muya's own stylesheets | 2,200 | **This is the port.** The geometry lives here as numbers |
| desktop's 32 theme + 31 Prism-theme CSS files | 11,001 | **The theme model's input**, not a port target — see D4 |

#### Four rows of that table are wrong or incomplete, found by laying them out **← measured at S1**

The table was transcribed by reading CSS. S1 transcribed it into a struct, then
emitted geometry from it and compared the output against the stylesheet again.
Four rows did not survive the second pass, and the first is the one that moves
every number below it:

- **The content column is not the text column.** `blockSyntax.css:17` is
  `box-sizing: border-box`, so the 800px `max-width` at `:18` *contains* the
  `0 50px` padding at `:21`. **The text column is 700px, and 650px under a
  shipped theme** — not 800 and 750. Two independent confirmations: 
  `inlineSyntax.css:197` computes `calc(--editor-area-width - 100px)` itself,
  and C7's user-facing editor-width setting injects `calc(100px + <value>)` for
  exactly this reason. The 800/750 pair is still the right name for the two
  themes, because it is the number a theme file carries; it is not the number
  anything is laid out at.
- **The block-spacing row is wrong about tables.** The figure is excluded from
  the `0.5em` rule; measured clearance is **1.5em above and 1em below**.
- **The line-number gutter is off by default.** `config/index.ts:323` sets
  `codeBlockLineNumbers: false`, and the table lists the `2.5em` gutter
  unconditionally. It is a layout option defaulting to false, not a constant.
  The line after it, `wrapCodeBlocks: false`, matters as much: the base rule is
  `overflow: auto` over the UA's `pre { white-space: pre }`, and the
  `pre-wrap` declaration lives inside `.mu-code-wrap`. **Fenced code does not
  wrap**, which nothing in this document said.
- **The task checkbox's 12×12 is a hit target, not a drawn box.** The `<input>`
  is `appearance: none` with no background: what is *visible* is the
  `::before`, an 18×18 border-box circle with a 2px border at `left: -2px`.
  A renderer draws two rects — the 18×18 ring and its 14×14 interior — and the
  12×12 appears in no display list. It is carried as a theme field anyway,
  because the three outlier themes override it and because **M4 hit-tests
  against it**; S1 is simply not the milestone with a consumer.

### The heading scale is not the browser's, and that is the shape of the whole problem

muya defines `h1 = 1.875em`, not the UA default `2em`; `h2 = 1.5em` matches,
`h3 = 1.375em` does not match `1.17em`. Every such value is a decision someone
made in CSS that a Rust layout engine reproduces only by being told. **There is
no algorithm to port and no test that fails if a number is wrong.** §7 is about
what replaces that.

## 3. One geometry, three consumers

`mt-layout`'s own doc comment states the architecture and M3 does not revisit
it: *"Layout is the single source of truth for geometry, shared by screen
rendering, PDF export, hit-testing, and print. One engine, three consumers —
which is why PDF export matches the screen by construction."*

The pipeline M3 builds, with the milestone that owns each arrow:

```text
  source ──parse (M2)──► Document ──┐
                                     ├──► LayoutTree ──► display list ──► pixels
  theme + available width ──────────┘        (M3)            (M3)          (M3)
                                              │
  per leaf: mt-inline::tokenizer (M1) ────────┤ styled runs + InlineBox
  per fence: mt-highlight (M3) ───────────────┘ highlight spans
```

Three things about this diagram are load-bearing and are asserted here so §6's
stages can be checked against them:

- **`mt-layout` consumes `Document`, never markdown.** `mt_md::parse` returns
  `Parsed { document, labels, source_map }`; the viewer holds all three, and
  §4 C6 is about the third.
- **Inline structure is re-derived per leaf, not stored.** A leaf's `Text` is a
  string; `mt_inline::tokenizer` turns it into a token tree with `Span` byte
  offsets *absolute into that leaf's text*. This is M2 C2's premise seen from
  above, and it is the reason `mt-layout`'s "parley is a direct fit" argument
  holds: inline content really is styled runs over one string.
- **`mt-highlight` sees a code block's text and a language, and nothing else.**
  The language is `Block::highlight_language()` — the **first word** of the
  info string, never the whole string, which round-trips verbatim.

## 4. Corrections to the plan

Eight corrections, ordered by how much they change what M3 builds. Six are
verified against upstream sources fetched on 2026-08-08; two are arguments and
say so.

### C1 — "GPU `vello` vs CPU `tiny-skia`, two backends behind one trait" is a false dichotomy **← verified upstream**

§6's table, §12.2's lever, §13 R7, and `mt-render`'s own doc comment all rest
on the premise that the CPU fallback must come from a different project with a
different imaging model. **It no longer does.** The Vello project ships its own
CPU renderer:

| Crate | Version | Published | What it is |
|---|---|---|---|
| `vello` | 0.9.0 | 2026-05-15 | GPU compute renderer on `wgpu` |
| **`vello_cpu`** | **0.2.0** | **2026-08-07** | CPU renderer, SIMD and multithreaded |
| `vello_hybrid` | 0.2.0 | 2026-08-07 | CPU tiling + GPU fine rasterization |
| `vello_common` | 0.2.0 | 2026-08-07 | Shared foundation for both |

Versions and dates confirmed directly against `crates.io/api/v1/crates/*` on
2026-08-08. The Sparse Strips v0.2.0 release notes call Vello CPU *"broadly
usable, with a reasonably complete imaging model and competitive
performance"*, with **no API stability guarantee**; Vello Hybrid is *"in its
early stages"*. Vello's own README still says the project *"can currently be
considered in an alpha state"* and lists **glyph caching** among its unfinished
work.

**What changes.** The trait in §6 survives; the table under it does not. The
strongest question at S0 is no longer *"GPU or CPU?"* but **"can `vello_cpu`
alone hit 60 fps scroll on the 5 MB corpus?"** If it can, M3 ships one backend,
drops `wgpu` entirely, and §12.2's headline size lever costs zero engineering.
That is a materially different milestone, and it is decided by measurement at
S0 rather than argued here.

**S0's answer, and the question S0 turned out to be unable to ask ← measured.**
The size half is settled: a `vello_cpu` + parley binary is **2,481,664 B** and
adding `vello`/`wgpu` costs **+4,317,696 B — the GPU backend is 2.7× the size
of the entire rest of the program** (`spikes/results/e2-binary-size.md`).

The scroll half is not, and the reason is structural rather than a stage that
ran short. **60 fps scroll cannot be measured before `mt-render` exists, and
`mt-render` is S4.** §6 asked S0 to take D1 from a measurement whose instrument
S0 does not build — an ordering defect in this document, not in the work. D1 is
therefore taken on the evidence that *does* exist and carries an explicit
revisit point; see §5 D1. The honest statement is that the trait stops being
insurance and starts being the thing that makes a late answer affordable.

### C2 — `tiny-skia` cannot draw text at all **← verified upstream**

`tiny-skia` 0.12.0 (2026-02-02, after a ~2-year gap since 0.11.4; the
repository has moved to `github.com/linebender/tiny-skia`). Its README lists
**text rendering under "out of scope"** — *"Text rendering (maybe someday)"* —
along with resource caching, and describes itself as *"not a Skia replacement
and never will be. It's more of a research project."* Its own performance note:
20–100 % slower than Skia on x86-64, 100–300 % on ARM.

The plan treats `tiny-skia` as the cheap option. **On text it is the expensive
one**: choosing it means building outline extraction, rasterization, an atlas,
subpixel positioning and the blend path by hand — precisely the work
`vello_cpu`'s default-on `text` feature already does. `tiny-skia` should be
demoted from *"the CPU backend"* to *"a possible last-resort raster target"*,
and it survives only if S0 says `vello_cpu` cannot.

**Now priced ← measured.** `tiny-skia` adds **+390,144 B** over the `vello_cpu`
baseline — genuinely cheap, and irrelevant, because the 390 KB buys paths and
rects and no glyphs. The demotion stands and the cheapness is the trap: a
backend that is 11× smaller than the GPU one and cannot render a single
character of a text editor's content is not a fallback, and §12.2's lever
sentence ("ship `tiny-skia` only") describes a program that cannot exist.

### C3 — `swash` is not in this stack any more **← verified upstream**

§6 says *"glyph rasterization via `swash`, cached in an atlas keyed by (font,
size, subpixel offset, glyph)"*, and §12.2 bills `parley + swash + fontique +
rustybuzz + ICU segmentation` at 2–3 MB. **Two of those four crates are not in
the graph.** Parley shapes with **HarfRust**, reads fonts with **skrifa**, and
analyses text with **icu4x** (`icu_properties`, `icu_segmenter`,
`icu_normalizer`); neither `swash` nor `rustybuzz` appears in `parley` or
`parley_engine`'s `Cargo.toml`. `swash` itself is alive (0.2.10, 2026-07-17),
so the plan's sentence would still *work* — it would just put a second
font-parsing stack in the binary alongside skrifa.

And the atlas idea fights the renderer: vello and `vello_cpu` draw glyphs as
**vector outlines** through skrifa, not by consuming an externally rasterized
atlas, and vello's README lists glyph caching as work it is doing itself.
**§6's swash atlas should be struck** unless S0 resurrects `tiny-skia`.

### C4 — R2's two "awkward parley cases" are not equal risks, and only one is a research risk **← verified upstream**

§13 R2 names two cases and asks for both in *week 1*. They are in completely
different states.

**Case 1 — inline-widget baseline alignment: solved, but not in a release.**
`linebender/parley` PR **#639** ("Implement `baseline` field on inline boxes")
**merged 2026-07-08**, adding `baseline: Option<f32>` to `InlineBox` and
`PositionedInlineBox` plus `Layout::first_baseline()` / `last_baseline()`.
Parley **0.11.0 published 2026-06-26** — *before* that merge. So the feature R2
calls a week-1 risk exists **only on `main`**. This is a dependency-pinning
decision (D2), not a research problem. Full CSS `vertical-align` remains open
(#291, #325), and tracking issue #208 shows `vertical-align` unchecked with
`[x] Baseline alignment for inline boxes (#639)` and `[ ] Subscript and
superscript` under it — which matters, because MarkText has a
`super_sub_script` option and 26 `TokenKind` variants include
`super_sub_script`.

**Case 2 — nested bidi interacting with inline boxes: not solved, and not
tracked as one thing.** No dedicated issue exists. What exists is a cluster of
open gaps: #208 leaves *"BiDi-direction overrides"*, *"Root-level default BiDi
direction"*, *"Span-level overrides"*, *"Margin/border/padding for inline spans
(should be bidi-aware)"* and *"Bounding boxes for inline spans"* all unchecked;
**#49** (open since 2024-04-29) considers replacing parley's own bidi
implementation with `unicode-bidi`; **#118** (open) reports bidi cursor motion
differing between `Left` and `Ctrl+Left`. The primitives are done — inline
boxes and hit-testing for inline spans are both ticked — but **nobody upstream
has ticked a box that says "an inline box inside an RTL run inside an LTR
paragraph places correctly."**

**R2's mitigation is validated and its ordering is wrong.** #639 is literally
an outside contribution landing the feature the plan feared, which is evidence
for *"Linebender is responsive; budget for upstream contributions."* But case 1
costs a version pin and case 2 is the genuine unknown. **S0's first test matrix
is case 2**, and `bench/corpus/rtl.md` (1,103 bytes, Arabic + Hebrew, mixed
script) plus an inline image is the input that exercises it.

#### What S0 measured, and the paragraph above is wrong about the thing it was most confident of **← measured**

**Case 2 works. On both versions.** `spikes/results/e1-bidi-inline-box.md`
answers M3-R1 **yes** for parley 0.11.0 and for `main` @ `a0752c7b`: an inline
box inside an RTL run inside an LTR paragraph is placed at the byte offset's
**resolved bidi level**, not where a left-to-right sweep of logical bytes would
put it. Both versions split the shaped run at the box's byte index and reorder
the halves with the rest of the line.

The deciding numbers, from an LTR paragraph with the box six bytes into the
Arabic word `مرحبا`: the box lands at **x = 231.96**, with logical bytes 32..51
on its *left* and bytes 26..32 on its *right*. That inversion is the RTL run's
visual order. A logical sweep would have placed it at x ≈ 254.56 — it is 22.6 px
to the left of that, in the correct slot. The harness does not grade parley
against parley: expected visual order is computed independently by
**`unicode-bidi` 0.3.18** with U+FFFC standing in for the box, and parley's
visual neighbours match it character-for-character in all six nested cases,
including level-2 LTR islands inside RTL paragraphs.

**One case fails, identically on both versions, and it is narrow.** An inline
box at **byte 0 of an RTL paragraph** — an image as the first thing in an Arabic
or Hebrew paragraph — is placed at the far left when it belongs at the far
right: x = 0.00..40.00 on a 437 px line where it should occupy 397.00..437.00.
Worse, a box at the *end* of the same paragraph lands at the same coordinates
and is correct there, so leading and trailing boxes are indistinguishable in
the output. The cause is upstream and acknowledged upstream — a box inherits the
preceding run's bidi level, which is right whenever it splits a run and wrong
when there is no preceding run, where the fallback is a hard-coded level 0:

```rust
// parley main, shape/mod.rs — the TODO is upstream's own
// TODO: this lets the inline box take the bidi level of the previous run, but in principle
// inline boxes should be included in bidi analysis as an object replacement character
// (U+FFFC). The box should then take the bidi level of that character.
let prev_bidi_level = if shaped_run_idx > 0 { … } else { BidiLevel::new(0) };
```

`unwrap_or(0)` is the whole bug. **11 of 12 cases pass on each arm.**

**What this does to the risk register.** M3-R1 was written as *"genuinely
unsolved upstream"* and *"not a month-5 discovery."* It was a month-*zero*
discovery, and what it discovered is that the fear was misassigned: the
research risk is a one-line upstream defect with a documented workaround
(an RLM before the box), not an architectural gap. §8 is updated accordingly.
This is also the second time in two milestones that the thing the plan was
most confident about turned out to be the thing that was wrong — M2 §4 C3 was
the first — and the pattern is worth naming rather than enjoying.

**Two upstream facts this turned up that the section above gets wrong.**
#208's *"Root-level default BiDi direction"* is **ticked on `main`** —
`set_base_direction`, PR #708 — and absent from 0.11.0. So case 1 is not the
only unreleased feature M3 needs; there are two, and D2 now turns on both.
And an unlisted silent fix: **0.11.0 breaks Arabic cursive joining at an inline
box** (one glyph changes form, +0.53 px) where `main` does not — a *correctness*
regression in the released version, on the exact construct this milestone's gate
names.

### C5 — §5's incrementality contract is on the wrong axis **← verified upstream**

§5 says *"re-wrapping the whole document happens only on width change — and
even then only for visible blocks plus a viewport margin."* Parley's own crate
documentation says the opposite about which operation is expensive:

> `Layout` supports re-linebreaking and re-aligning many times (in case the
> width at which wrapping should occur changes), **but if the text content or
> the styles applied to that content change then a new `Layout` must be
> created**.

So **a width change is the cheap case** — `break_all_lines(Some(w))` then
`align(…)` on the existing `Layout`, no re-shaping — and **a content change is
a full rebuild** of that block's `Layout`. There is no API to patch a `Layout`
in place, no partial re-shape, no reshape-from-byte-N. The plan's block-granular
dirty model is therefore the *only* available granularity, which is fine
because §0's premise already made blocks the unit — but the caching design
follows the real axis, not the assumed one.

Two supporting facts. `LayoutContext` is documented as *"designed to be a
global resource with only one per-application (or per-thread)"*, so the reuse
it offers is **allocator-level, not shaped-run-level**: rebuilding avoids
malloc traffic, not shaping work. And parley 0.7.0 fixed a bug where laying out
large paragraphs was **non-linear** in length — which is a reason to distrust
any recalled benchmark from before that release.

**Both confirmed ← measured.** Over `5mb.md`, re-breaking every existing
`Layout` at a new width costs **54 ms** against **810 ms** to rebuild them —
a **15.1× ratio** at 800 → 750 px, and **14.8×** at 800 → 1600 px, so the large
jump hides nothing. The documentation's axis is the real axis.

Two consequences the correction did not go far enough on. First, at 54 ms for
the *whole* 5 MB document, **§5's "only for visible blocks plus a viewport
margin" caution is unnecessary for width changes specifically** — a window
resize can re-break everything and stay inside a frame budget's neighbourhood.
Laziness is needed for the *first* layout (D9), not for reflow. Second, the
non-linearity is gone: ns/byte *falls* from 367 to 148 across the corpus's size
range and throughput is flat at 6.5–6.7 MB/s from 250 KB to 5 MB. **The enemy
is block count × a fixed per-`Layout` cost, not document size** — which is
exactly what makes §5's `Code { lines: Vec<Layout> }` sketch the wrong shape
(D9).

### C6 — a read-only viewer lays out a string that is not the block's text, and that is a *third* offset space

**← argument, and the one correction here that is about this port rather than about upstream**

MarkText is WYSIWYG: markdown markers are hidden unless the caret is near them.
`mt-inline::marker` implements exactly that, and its predicate is a pure
function of `(token.range, cursor)` with **no ancestor/descendant propagation
in either direction** — measured against the running engine at M1, which found
§3.1's sketch wrong in two of its three clauses. A read-only viewer has no
caret, so `cursor: None` and **every marker is hidden**.

The consequence the plan does not contain: **the string `mt-layout` hands to
parley is not `Block::text`.** `**bold**` occupies 8 bytes of block text and 4
columns of visible text. So the offset spaces stack three deep:

```text
  source offset  ──(M2's SourceMap, per node; is_exact says which are tight)──►
  block-text offset  ──(M3 must build this)──►  visible-text offset
                                                 └─► parley cluster ──► pixel
```

M2 §10 owes the **first** arrow's inverse to M4, narrowed three times and still
not free. M3 discovers the **second**, and the second is M3's own: nothing can
place a search highlight, a click, or a link hit-region without it. The good
news is that it is cheap where M2's is not — `mt-inline`'s tokens carry both
`range` and `raw` as absolute byte spans into the leaf's text, so the map falls
out of the same walk that builds the style runs, rather than needing a per-kind
inverse. **This is an M3 deliverable and §10 will carry it forward for M4's
caret.**

Related, and recorded so it is not rediscovered: `tokens_to_plain_text` already
performs this stripping, but it is *non-bijective* and exists for
table-of-contents text and HTML anchor slugs. It is the right shape and the
wrong contract — M3 needs the mapping, not just the string.

### C7 — the plan has no theme model, and themes carry geometry **← verified in the reference**

§5 says layout consumes *"a `Document` + theme"* and never says what a theme
is. In MarkText a theme is CSS, and the numbers are not all colours:

- **33 selectable themes**; 32 CSS files on disk plus `light`, which is the
  no-op default. Each file is ~214 lines (dark 220, ulysses 252, graphite 254,
  one-dark 350, material-dark 189).
- **All 32 non-`light` themes override `--editorAreaWidth` from muya's 800px
  default to 750px.** Content column width is a theme property. **← refined at
  S1:** they set `--editorAreaWidth: 750px` *and* carry the alias
  `--editor-area-width: var(--editorAreaWidth)` that muya v2 actually reads. The
  alias exists **only** in those 32 files, so the `light` default is not a no-op
  on this axis — it is the case that gets muya's 800px.
- **← corrected at S1: three** themes, not four — `graphite`, `one-dark` and
  `ulysses`; `dark` is colour-only. They hard-code **non-variable** geometry —
  task-checkbox size, position and rotation, thematic-break styling, and in
  `ulysses` a bullet marker muya does not define at all — replacing
  `blockSyntax.css`'s own rules outright.
- A user-facing **editor-width setting** injects
  `--editorAreaWidth: calc(100px + <value>)` where `<value>` is a free-text
  `ch`/`px`/`%` string; the `+100px` is the container's `0 50px` padding.
- **There is no theme schema.** The contract is implicit in which
  `var(--x, fallback)` names the base stylesheets read. `theme.md` is a
  three-line placeholder for the picker UI.
- Themes reach muya by a build-time `?inline` import concatenated into one
  `<style id="theme-style">` element, and each ships a **paired Prism theme**
  (31 files, `material-dark` reusing `dark`'s).

**M3 cannot consume CSS**, so D4 has to decide what a theme is in Rust and what
the 32 files become. The honest framing: this is a *data-modelling* decision
with 11,001 lines of prior art, not a styling detail.

### C8 — muya does not virtualize, so M3's performance gate is not a parity gate **← verified in the reference**

`ScrollPage.create()` (`block/scrollPage/index.ts:51-63`) maps over the entire
state array and appends **every top-level block** to real DOM at once;
`updateState()` empties and re-appends all of them. The entry point
(`editor/index.ts:282`) calls it once with the complete document. There is no
`IntersectionObserver`, no visible-range concept, no scroll check anywhere in
`block/` or `editor/` — the name `scrollPage` refers to the scrollable
container element, not to a virtualization scheme. MarkText renders the whole
document and relies on the browser's paint culling.

Two consequences, and the second is uncomfortable:

- **If `mt-layout` lazily lays out only visible blocks, that is a new
  capability, not parity.** The plan is right that it is where the 5 MB target
  is won; it should not be described as matching what MarkText does.
- **There is no baseline to compare against.** `bench/corpus/README.md` already
  flags that a `BASELINE.md` capturing real Electron numbers was deliberately
  deferred (it needs a full `pnpm install` and build of the clone). So *"5 MB
  opens ≤ 800 ms"* is an **absolute** target with no reference measurement, on
  unspecified hardware. §8 carries this as a risk, and S0 owes the baseline.

**The baseline now exists, and it retires this bullet ← measured.**
`bench/BASELINE.md` was built at S0 from a **packaged** MarkText — an
`electron-vite build` + `electron-builder --win --x64` artifact at commit
`e52106fd`, run as `dist/win-unpacked/marktext.exe`, not a dev server. On the
same machine every Rust number in this document was taken:

| §12.1 metric | Electron, measured | Target |
|---|---:|---:|
| Cold start → editable caret | **818 ms** (n=8, 809–829) | ≤ 250 ms |
| Warm start | **788 ms** (n=5) | ≤ 120 ms |
| RSS, empty document | **485 MB** (n=3) | ≤ 60 MB |
| RSS, 1 MB document | **920 MB** (n=3) | ≤ 120 MB |
| **Open 5 MB document** | **did not finish — > 150 s, and a second run abandoned at ≈ 5 min** | ≤ 800 ms |
| Keystroke → glyph, p99 | *unmeasured* — no reliable path to real paint timestamps | ≤ 8 ms |
| Idle CPU, focused | **0.04 %** | ~0 % |

The RSS figures sum the whole Electron process tree — main, renderer, GPU,
utility — because a main-process-only number would flatter Electron by an order
of magnitude.

**C8's framing needs strengthening rather than softening.** The correction said
lazy layout is *"a new capability, not parity."* That is now an understatement:
`1mb.md` takes **43.3 s** to open and `5mb.md` never becomes interactive at all,
while staying `Responding = True` and burning CPU — so scaling is superlinear
and the failure is a hang, not a slow load. **The 800 ms gate is not a target
MarkText misses; it is a capability MarkText does not have.** Six of seven §12.1
rows are missed, several by an order of magnitude, and idle CPU is the only row
Electron already passes.

That cuts both ways and the second way is the uncomfortable one: **it removes
"but Electron is slower" as an available defence for the Rust side**, because on
the row that matters most there is no Electron number to be faster than. §6 S6
still has to hit 800 ms on its own terms.

### C9 — three smaller items that would each cost a stage if found late **← verified upstream**

- **`Brush` is parley's own trait**, with a blanket impl for
  `Clone + PartialEq + Default + Debug` and a default type parameter of
  `[u8; 4]`. It is **not** `peniko::Brush` — parley demoted peniko to a
  dev-dependency, replaced `peniko::Font` with
  `linebender_resource_handle::FontData`, and replaced `kurbo::Rect` with its
  own `parley::BoundingBox`. `mt-layout` defines its own brush type, and the
  peniko/kurbo boundary now sits at the `mt-layout` → `mt-render` seam rather
  than inside `mt-layout` — which is what the crate's "no GPU" rule wanted
  anyway.
- **Parley 0.10.0 added a `complex-scripts` feature** for dictionary-based line
  breaking in CJK, Thai, Khmer, Lao and Myanmar. M3's gate says *"CJK renders
  correctly"* and `bench/corpus/cjk.md` includes a long unspaced line for
  UAX #14. The feature is almost certainly required and the plan does not
  mention it.
- **Parley's default feature set is `["system"]`**, which enables system font
  backends — i.e. filesystem enumeration. `mt-layout`'s own doc comment
  commits to **"No I/O"**, and `cargo xtask deps` greps its `src/` for
  `std::fs::` (a deliberately crude check that would *not* catch I/O inside a
  dependency). D7 has to take this explicitly rather than let a default feature
  decide it.

Also worth knowing before pinning: parley's unreleased section **removes
`Glyph::style_index`**, changes `Cluster` to span a full grapheme cluster (a
semantic change to the exact API §5 hit-tests through), and changes line sizing
for mixed inline content. 0.8.0 moved `Glyph::y` from Y-up to **Y-down**.

**All three measured at S0, and the churn was overstated ← measured.**

- **"No I/O" is achievable and cheap.** parley builds and lays out with
  `default-features = false` (plus `std`), which drops the dependency count
  from **61 → 49** crates on 0.11.0 and 62 → 50 on `main`. Fonts register from
  in-memory bytes through
  `Collection::new(CollectionOptions { shared: false, system_fonts: false })`
  followed by `register_fonts(Blob<u8>, None)`. No filesystem enumeration
  anywhere. D7's third option — the one D7 called "the one to beat" — is not
  merely honest, it is the *default* once the feature is off.
- **`complex-scripts` costs nothing in crates and a great deal in bytes.** It
  exists in 0.10, 0.11 and `main`, pulls **0 extra dependencies**, and adds
  **+3.6 MiB** to the binary — dictionary data, and by a wide margin the
  largest single feature-flag cost measured anywhere at S0. C9 called it
  "almost certainly required" for the gate's CJK clause and did not price it.
  It is now the second-largest line item in M3's binary after the GPU backend,
  and it is a flag rather than an architecture, so §12.2 has to carry it.

#### "Almost certainly required" was not required at all, and this is 3.6 MiB **← measured at S1**

S0 priced the feature and inherited C9's judgement that the gate needs it.
Nobody laid the corpus out both ways. S1 did, and **`complex-scripts` changes
nothing this project can observe**: `cjk.md`'s deliberately-long unspaced
Chinese line breaks at byte offsets `[]`, `[]`, `[]`, `[116]`, `[53,110]` at
800/750/700/650/320 px — **byte-identical with the feature on and off**, with
identical advances and identical heights.

The reason is that C9 named the wrong scripts. UAX #14 already permits a break
between ideographs, with no dictionary involved; the dictionary is for **Thai,
Khmer, Lao and Myanmar**, which the corpus does not contain. The control is in
the same experiment so the result cannot be a flag that failed to reach the
code: a Thai string breaks at byte 96 with the feature on and never breaks with
it off.

**M3 ships without it, and the trigger is recorded rather than the conclusion**
— the day a corpus file or a shipped locale acquires Thai, Khmer, Lao or
Myanmar, this is 3.6 MiB that has to be bought. Together with D1 declining the
GPU backend, the two largest line items §12.2 ever named are both now
un-purchased, on measurements taken eight and one stages after the estimate.
- **Porting 0.11.0 → `main` cost 2 lines.** Adding `baseline: None` to two
  `InlineBox` literals, and nothing else. `Glyph::style_index` and the `Cluster`
  grapheme change **were not hit at all**. What *was* hit is the one the plan
  did not emphasise: **#697's line sizing** changed every case — line height
  24.00 → 28.40, baseline 22.00 → 24.00, box y −2.00 → 0.00. So the churn risk
  is real but sits in *geometry*, which goldens catch loudly, rather than in
  *API*, which the plan feared and which cost two lines.

### C10 — §12.2's binary-size table has no provenance **← to measure at S0**

The plan's headline lever is *"drop `wgpu`/`vello`, ship `tiny-skia` only:
−4–6 MB."* **The 4–6 MB figure could not be sourced.** The only public
datapoint found was a small wgpu program at 8.4 MB total with wgpu itself at
~857 KiB per `cargo bloat` — one anecdote, an old wgpu, counting Rust code
only. Vello's docs note that unused pipelines can be disabled to reduce size,
so the shader payload is a knob rather than a fixed cost.

The second lever — *"load tree-sitter grammars on demand: −3–4 MB"* — **is not
a feature flag.** Grammar crates ship generated C compiled by `build.rs` and
**linked statically**; on-demand loading means shipping and `dlopen`-ing
platform dynamic libraries, or embedding a wasm engine. That is a subsystem
with packaging, code-signing and platform-matrix consequences.
`tree-sitter-rust` 0.24.2's published crate is ~360 KB of *compressed source*;
compiled parse-table size is a different and larger number. §12.2's "~4 MB for
core + ~20 grammars" is plausible, unverified, and possibly low.

**S0 replaces the table rather than arguing with it**: four `dist`-profile
builds (`vello_cpu` only · `+ vello`/`wgpu` · `+ tiny-skia` · `+ N grammars`),
`cargo bloat --crates -n 40` on each, deltas recorded. Note the first build may
not have existed when §12.2 was written.

#### The four builds **← measured**

Under the `dist` profile copied verbatim from the root manifest — `lto = "fat"`,
`codegen-units = 1`, `panic = "abort"`, `strip = "symbols"`, `opt-level = "s"`.
Sizes are the stripped artifact; per-crate attribution came from an unstripped
twin profile, because `cargo bloat` cannot attribute what `strip` removed.

| # | Build | Stripped `dist` | Δ over floor | Δ over build 1 |
|---|---|---:|---:|---:|
| 0 | floor (`fn main() {}`) | **98,304 B** | — | — |
| 1 | `vello_cpu` + parley | **2,481,664 B** | +2,383,360 B | — |
| 2 | + `vello`/`wgpu` | **6,799,360 B** | +6,701,056 B | **+4,317,696 B** |
| 3 | + `tiny-skia` | **2,871,808 B** | +2,773,504 B | +390,144 B |
| 4a | + tree-sitter core + **1** grammar | **3,661,312 B** | +3,563,008 B | +1,179,648 B |
| 4b | + tree-sitter core + **20** grammars | **28,388,864 B** | +28,290,560 B | **+25,907,200 B** |

**Lever 1 survives in magnitude and dies in mechanism.** §12.2 claims −4–6 MB
for dropping `wgpu`/`vello`; measured **−4.318 MB**, inside the range at its low
edge. But the plan's stated mechanism — *"ship `tiny-skia` only"* — describes a
program that cannot render text (C2), so the lever is really *"ship `vello_cpu`
only"*, which the plan did not know was an option.

**Lever 2 is understated by 6–8×, and this is the largest single finding of
S0.** §12.2 claims −3–4 MB for on-demand grammars. The measured cost of
bundling 20 is **25.907 MB**, at **~1.301 MB marginal per grammar**. §12.2's
whole *"~17–25 MB default total"* is smaller than one plausible grammar set.

**C10's static-linkage argument is confirmed by reading the code**, not
inferred: `tree-sitter-rust`'s `build.rs` compiles a checked-in **6.5 MB
`parser.c`** through the `cc` crate into a static library. There is no flag that
makes it lazy; "on demand" means dynamic libraries or a wasm engine, exactly as
C10 argued. A C toolchain is required — MSVC was already present here, so this
stage cannot speak to the cost of provisioning one from zero, only to the fact
that one is mandatory.

**A methodological warning for anyone who re-runs this.** `cargo bloat --crates`
**massively under-reports tree-sitter**, because parse tables are `.rdata`
(data) and `cargo bloat` attributes `.text` (code). Per-grammar cost is only
recoverable from whole-binary deltas. A future stage that trusts `cargo bloat`
alone here will conclude grammars are nearly free and be wrong by an order of
magnitude.

### C11 — `mt-highlight`'s stated rationale does not apply at M3 **← argument**

The stub's doc comment says tree-sitter was *"chosen over `syntect` for its
incremental behaviour: an edit inside a fence re-parses the edited region, not
the fence."* **M3 is a read-only previewer. There are no edits inside a fence.**
The benefit is M4's; the costs — static C linkage per grammar, a C toolchain on
every platform, build time, binary size against a 250 ms cold-start budget —
are paid at M3. Meanwhile MarkText's parity baseline is **Prism 1.30 with 298
lazily-loaded grammars**, of which only `latex` and `yaml` are eager, and
highlighting is **synchronous and per-code-block**, falling back to plain
escaped text until a language's dynamic import resolves.

D3 re-opens the choice with three candidates and no winner picked here.
Sourced numbers to decide against, all upstream-verified: `syntect` 5.3.0 loads
its whole binary syntax dump in **~23 ms** with lazy regex compilation, but
highlights 9,200 lines of jQuery in **600 ms** and reaches 50,000 lines/s on
simple syntaxes; its default `regex-onig` feature pulls a C library, while the
pure-Rust `regex-fancy` alternative is *"about half the speed"*; its output is
`Vec<(Style, &str)>`, so `mt-highlight`'s byte-range contract needs an adapter.
`tree-sitter` 0.26.12 (published 2026-08-08) emits
`HighlightStart / Source { start, end } / HighlightEnd` — byte ranges, a direct
fit for the contract. A Prism port is regex-driven and grammar-as-data, so
lazy loading is trivial and binary cost is near zero, at the price of
translating 298 JS grammars' regexes (lookbehind and backreferences need
`fancy-regex`) and owning them as they drift.

#### Four things in the paragraphs above are wrong, and one of them is the load-bearing one **← measured**

`spikes/results/e4-highlight.md` measured all three engines. The costs C11
charges against tree-sitter hold and get worse; the costs it charges against
`syntect` and the Prism port were partly invented.

- **`syntect` needs no adapter.** C11 says its output is `Vec<(Style, &str)>`
  so *"`mt-highlight`'s byte-range contract needs an adapter."* That is true
  only of the `easy::HighlightLines` convenience wrapper. `syntect`'s public
  **`RangedHighlightIterator` already yields `(Style, &str, Range<usize>)`** —
  byte ranges, the contract, no adapter, no cost. A whole objection evaporates.
- **The regex claim names the wrong construct.** C11 says *"lookbehind and
  backreferences need `fancy-regex`."* Native lookbehind appears in **zero of
  the 298 grammar files** — Prism's `lookbehind: true` is a different,
  non-regex mechanism that trims a captured prefix, and C11 conflated the two.
  What actually forces `fancy-regex` is **lookahead**, which C11 does not
  mention and which drives **~73 %** of the files. The conclusion survives
  (`fancy-regex` is needed, and it is already a dependency of `mt-inline`) but
  the reasoning behind it was wrong, which matters because the port's difficulty
  was being estimated from it.
- **It is 297 languages, not 298.** The 298th key is `meta`, which is not a
  language. Every "298" in this document should be read as 297, including §6
  S3's gate and D3's coverage axis.
- **The Prism wiring reference is 405 lines across four files**, not the 397
  in one that §2's table implies.

#### Three of those four corrections are themselves wrong, and one of them threw away a true claim **← measured at S3**

The subsection above was written from **text scans of the grammar files**. S3
loaded all 297 grammars in Node and introspected the **13,725 live `RegExp`
objects** instead, which is the only way to see a pattern that a grammar builds
rather than writes down. Three numbers move, and the pattern is the document's
own: a structure was reasoned about instead of being run.

- **Lookahead drives 89.9 %, not ~73 %.** The measured figure is **267 of 297
  languages**, across **4,211** regexes. ~73 % counted positive lookahead only,
  in file text; `(?!` is as ordinary in these grammars as `(?=`.
- **Backreferences are real, and the correction above deleted a true claim along
  with a false one.** C11 originally wrote *"lookbehind and backreferences need
  `fancy-regex`"*; the subsection struck the whole phrase as one conflation. Only
  the lookbehind half was wrong. **62 regexes across 46 of the 297 languages
  (15.5 %) use a numeric backreference** — `prism-abap.js:3`'s
  ``/(`|')(?:\\.|(?!\1)[^\\\r\n])*\1/`` is the ordinary shape, a quote character
  captured and required to close itself. They force `fancy-regex` independently
  of lookahead, so the dependency now has **two** unrelated justifications where
  the document had recorded none that survived.
- **"Zero native lookbehind" is confirmed, and by the stronger measurement.**
  Zero of 13,725 live regexes contain `(?<=` or `(?<!`; the only textual hits in
  the grammar files are inside comments. C11's mechanism claim is also correct:
  `lookbehind: true` trims a captured prefix from the match and is not a regex
  feature at all.
- **"405 lines across four files" is wrong and it broke a correct number.** §2's
  original **397** was right; the wiring is **five** files, and C11's four-file
  set omits `walkToken.ts` — the token-tree flattener, which is the single most
  S3-relevant file in the reference wiring, since it is where Prism's nested
  `Token` objects become a flat sequence.

**And one measurement nobody asked for, recorded because it removes work rather
than adding it.** Across all 13,725 regexes the only flags in use are **`i`
(1,919) and `m` (604)**. There is **no `s`, no `u`, no `y`** anywhere: Prism
predates dotAll and writes `[\s\S]`, which Rust's regex syntax accepts verbatim,
and it never uses unicode or sticky mode. So the JS→Rust pattern translation is
not a dialect port. It is **`\uNNNN` → `\u{NNNN}` and four `[^]` → `[\s\S]`
sites**, and the residual risk in D3's credit is `fancy-regex`'s **backtracking
throughput**, not its expressiveness — which is what M3-R9 was already pointed at.

**And the measured axes point in different directions, which is why D3 is a
decision and not a lookup.** Cold start to first highlight: `syntect` **≈2.5 ms**
(0.77 ms setup + 1.75 ms first fence) against tree-sitter's **15.3 ms** for one
lazily-built grammar and **80.9 ms** for fourteen eager ones — query compilation
is the whole cost, and 80.9 ms is a third of the 250 ms cold-start budget spent
before a glyph is drawn. Steady-state throughput reverses it: tree-sitter
**41,060–41,394 lines/s** against `syntect`'s **24,344–24,815**, ~1.65× faster.
Coverage over the corpus's own 16 languages is a tie at **42/51 blocks (82.4 %)
each — but they miss different things**: `syntect` has no TypeScript and no TOML
in its default 75-syntax bundle; tree-sitter has no SQL and no diff. Across the
full Prism set `syntect` covers a measured **44 of 297**.

## 5. Decisions to make before writing code

M2's D-list was taken before its first stage and revisited when a stage proved
one wrong. Same discipline. Two are taken at open because scope forces them;
the rest name the stage that must take them, and **S0 exists to take most of
them with numbers rather than arguments**.

### D1 — the renderer set: `vello_cpu` alone, GPU deferred behind the trait **← taken at S0, and taken on incomplete evidence, which is stated rather than hidden**

Options were: `vello_cpu` alone · `vello_cpu` + `vello`/`wgpu` behind the trait ·
the plan's original `vello` + `tiny-skia`.

**Decision: M3 ships `vello_cpu` alone. The §6 trait is built anyway. `wgpu`
does not enter the dependency graph at M3, and `tiny-skia` is struck entirely.**

The numbers it rests on:

| | |
|---|---:|
| `vello_cpu` + parley, `dist`, stripped | **2,481,664 B** |
| cost of adding `vello`/`wgpu` | **+4,317,696 B** — 2.7× the rest of the binary |
| cost of adding `tiny-skia` | +390,144 B, and it renders **no text at all** (C2) |

**The measurement D1 was supposed to turn on was not taken, and could not be.**
§6 asks S0 whether `vello_cpu` hits 60 fps scroll on `5mb.md`. Scroll frame rate
requires `mt-render`, which S4 builds; S0 writes no product code by its own
definition. This is an ordering defect in §6 rather than a stage that ran out of
time, and C1 records it.

So the decision is taken on **cost and risk asymmetry instead of on frame rate**,
and the asymmetry is lopsided. Adding a GPU backend later costs one stage behind
a trait that exists from S4. Carrying `wgpu` from S1 costs 4.3 MB, a second code
path through every pixel golden, `naga`, a shader payload, and the VM-fallback
matrix (R7) for the whole milestone — all to hedge a number nobody has. And the
competitive bar set at S0 is not demanding: the incumbent takes **818 ms** to
show a caret and **never opens `5mb.md` at all**.

**The revisit point is explicit, so this cannot quietly become permanent.**
**S4 measures scroll frame rate on `5mb.md` with `vello_cpu` as its first act.**
If it misses 60 fps, D1 reopens with the number it should have had, the trait
absorbs `vello`/`wgpu`, and §12.2's lever is re-priced. **S4 may not report a
backend as chosen without that number.**

### D2 — parley: track `main`, pinned to one revision **← taken at S0**

C4 case 1's feature (`InlineBox::baseline`) is merged but unreleased, and the
unreleased section also carries breaking changes to `Cluster` — the exact API
hit-testing goes through. Pinning 0.11.0 means no baseline alignment for inline
images and math; tracking git means absorbing semantic churn mid-milestone.

**Decision: track `main`, pinned at rev `a0752c7bdc3ad88dac19fc194d2b8e57e59bea2e`
(2026-08-10). Move the pin deliberately, never by `cargo update`. Re-evaluate
when 0.12.0 ships.**

**This is a correctness-over-performance trade and it costs real performance**,
which is the part neither experiment would have shown alone:

| | 0.11.0 | `main` @ `a0752c7b` |
|---|---:|---:|
| eager layout, `5mb.md` | baseline | **+13.9 % slower** |
| peak RSS | baseline | **+40 %** |
| `break_all_lines` alone | baseline | **+74 %** (points at #697) |
| binary size | baseline | +512 B |
| port cost from 0.11.0 | — | **2 lines** |

Against that, `main` carries **three** things M3's own exit gate requires and
0.11.0 does not have:

1. **`InlineBox::baseline`** (#639) — verified working: `y + baseline` equals the
   line baseline for `Some(24.0)`, `Some(12.0)` and `Some(0.0)`, and
   `first_baseline()` returns sane values. Absent in 0.11.0. Inline images and
   inline math have no baseline to align to without it.
2. **`set_base_direction`** (#708) — root-level default bidi direction, which C4
   discovered is ticked upstream and shipped only on `main`. A document whose
   base direction is RTL cannot be laid out correctly without it.
3. **0.11.0 breaks Arabic cursive joining across an inline box** and `main` does
   not. This one is decisive on its own: the gate says *"Bidi, CJK, emoji,
   ligatures render correctly"*, and the released version renders Arabic
   incorrectly on exactly the construct M3-R1 is about.

The performance gap is recoverable by means M3 is building anyway — laziness is
now load-bearing (D9) and parallel layout returns 2.37×. **A correctness defect
in shaped Arabic is not recoverable at all.** Pinning 0.11.0 would trade a gate
clause for 13.9 %.

**The pin's standing risk**, recorded so a later stage does not rediscover it:
the churn that actually landed was *geometric* (#697 moved line height 24.00 →
28.40 and baseline 22.00 → 24.00), not API. Moving the pin will therefore
invalidate layout goldens rather than fail to compile — **a pin move is a
reviewable event on the same footing as a golden update** (M3-R6).

### D3 — `mt-highlight` ports Prism's grammars. **The M0 decision is overturned** **← taken at S0**

`syntect` · `tree-sitter` · a Prism-grammar port. See C11. The M0 choice was
tree-sitter for a reason that does not apply until M4.

**Decision: port Prism's grammars as data. `tree-sitter` is dropped from M3 and
does not enter the dependency graph. `syntect` is retained as a named fallback
with a measured trigger, below.**

| Axis | `syntect` 5.3.0 | `tree-sitter` 0.26.12 | Prism port |
|---|---:|---:|---:|
| Time to first highlight | **2.5 ms** | 15.3 ms (1 grammar) → 80.9 ms (14 eager) | ~0 (grammars are data, lazily loaded) |
| Steady-state throughput | 24.3k lines/s | **41.1k lines/s** | **unmeasured** |
| Binary delta | +999,936 B | **+1,179,648 B for one grammar; +25,907,200 B for twenty** | est. **< 1.5 MB for all 297** |
| Coverage of Prism's 297 | **44** | 35–50 % (estimate, unverified) | ~~**297 by construction**~~ — **292 register a grammar at all, and coverage is a porting programme, not a construction (D14)** |
| Byte-range contract | direct (`RangedHighlightIterator`) | direct | direct |
| Differential against Prism | weak | weak | **near-exact** |

**Three axes decide it and they are not close.**

**Coverage.** D3's own text says *"language coverage is what users notice."*
`syntect`'s default bundle has **no TypeScript and no TOML**. Shipping a
markdown editor in 2026 that cannot highlight a `ts` fence is a defect users
hit on day one. tree-sitter can reach parity only by linking grammars at
**1.301 MB each** — parity with Prism would be roughly **386 MB**, and even a
40-language subset is +52 MB against a plan whose *entire* budget was 17–25 MB.

**Binary size.** Prism grammars are data, so lazy loading is free rather than
being the dynamic-library subsystem C10 correctly identifies for tree-sitter.
This is the same lever §12.2 wanted, obtained by construction instead of by
engineering. **↑ This sentence is wrong about Prism's source and right about the
port's artifact, and S3 had to build a generator to make it true** — 91 of the
297 grammar files construct their patterns at load time rather than writing them
down. See **D14**, which keeps the conclusion and replaces the mechanism.

**Differential testability, which the plan under-weights and which S0 promotes
to decisive.** §7 states plainly that for the first time in this project
*"does it match MarkText?" cannot be answered by running MarkText* — and that
§6 S3's Prism differential is **the one real differential M3 has left**, the
single place M1 and M2's strongest instrument survives. A port restates Prism's
own rules, so span boundaries can be compared for **exact equality** through the
existing Node harness. `syntect` and tree-sitter use genuinely different
tokenizations and will disagree with Prism constantly while both are "right",
which does not weaken S3's gate so much as delete it. **Choosing either would
mean M3 ships with no differential test at all.**

**What this decision is buying on credit, stated plainly.** Prism's steady-state
throughput in Rust is **unmeasured** — no port exists to measure — and the known
risk is real: ~73 % of grammars need `fancy-regex` for lookahead (C11), and
`syntect`'s own documentation puts its `regex-fancy` backend at *"about half the
speed"* of `regex-onig`. **S3 measures it, and the fallback trigger is named
now so it cannot be argued about later: if the ported engine highlights a
visible fence in more than 16 ms (one frame at 60 fps), `syntect` takes the
top-40 languages and the port continues behind it.**

**Scope, because 297 grammars sounds like a milestone of its own and is not.**
MarkText lazily loads all 297 and eagerly loads **two**. The port is therefore a
ratchet, not a big bang: implement the grammar interpreter once, port languages
in usage order, and let `cargo xtask highlight` count coverage as a number that
only goes up — structurally the same instrument as M2's `PENDING` ratchet, which
delisted 213 of 215 cases stage by stage. **S3's gate is the interpreter plus a
counted, differentially-verified subset — not 297 grammars.**

**The M0 rationale is retired, not merely bypassed.** `mt-highlight`'s stub doc
comment claims tree-sitter was chosen for incremental re-parse inside a fence.
That benefit is M4's; every cost is M3's; and the coverage-per-megabyte number
now says it does not become affordable at M4 either. **M4 re-opens this on
incremental grounds if it wants to, with these numbers in hand.**

### D4 — what a theme *is*: a typed struct with required fields, loaded from TOML **← taken at S1 open**

A typed Rust struct with named fields · a data file with a versioned schema ·
a small subset-of-CSS parser.

**Decision: a typed `Theme` struct whose fields are all required, deserialized
from TOML. No CSS is parsed at runtime; the 32 shipped stylesheets are a
*source* to be transcribed, not a format to be read. S1 delivers two themes,
not 32.**

The variable surface, measured across all 32 `*.theme.css` files and every
stylesheet under `packages/muya/src`:

| | |
|---|---:|
| variables the 32 themes define, union | 122 |
| — kebab-case, the set muya v2 reads | 41 |
| — camelCase, driving desktop chrome and the legacy editor | 81 |
| variables muya's own stylesheets consume | 46 |
| — pure colour | 36 |
| — **pure geometry** | **4** |
| — font family | 2 |
| — compound border/shadow | 4 |
| consumed but defined by no theme, falling back inside muya's CSS | 5 |
| themes overriding a `.mu-*` selector directly | **32 of 32** |
| themes overriding **geometry** | **3 of 32** |

**Three findings, and the first one disqualifies the obvious model.**

**The variable system is a colour system, so a schema that mirrors it cannot
express what themes actually do.** Four of the 46 consumed variables are
geometry — `--editor-area-width`, `--mu-font-size`, `--mu-line-height`,
`--mu-code-font-size` — against 36 pure colours. Everything else geometric that
a theme changes escapes the variable system and lands as a literal rule. **So
the schema's field set is determined by what themes override, not by what the
variable system exposes**, and those are different sets.

**What the three outliers change is shape, not size.** `graphite`, `one-dark`
and `ulysses` replace muya's 12×12 circular checkbox at `-23px` with a 16×16
square at `-24px` carrying a 9×5 checkmark; `graphite` and `ulysses` redraw the
thematic break's `::before` outright, `ulysses` halving its width; `ulysses`
alone hides the native list marker and draws its own 5×2px dash at `-18px`, a
`content: ''` overlay muya does not define at all, and centres every heading.
All literal, all `!important`, no variable involved. The schema therefore
carries checkbox box/ring/check geometry, thematic-break width and inset, a
`ListMarker` enum with a `Dash` variant, and heading alignment — roughly eight
numbers and two enums beyond the variable surface.

**The silent-fallthrough case is the argument against every untyped option, and
it is not hypothetical.** The default `light` theme has **no `.theme.css` file
at all**: it is the base stylesheet plus a two-line patch that bridges **2 of
the 41** variables muya reads. The other 39 are undefined for a
never-touched-preferences install and fall through to CSS initial and inherited
values, which mostly works by luck. Nothing reports it. **A struct whose fields
are required and whose default is a named constant cannot have that failure
mode** — which is the same reasoning D7 applies to `register_fonts` returning
an empty `Vec`, arriving independently at a second layer of the same milestone.

**Two corrections to this document fall out, and both sharpen D4's own test
case.** §2's table and R7 said *at least four* themes override checkbox
geometry; it is **three** — `grep -l "left: -24px"` and
`grep -l "mu-task-list-item > input"` return the same three files, and neither
the export themes nor the legacy `packages/muyajs/themes/` holds a fourth. And
the 800/750 split is not *muya's default versus every shipped theme*: 750px
lives in `--editorAreaWidth`, aliased onto muya's `--editor-area-width` **only
inside the 32 theme files**, so an install that never picks a named theme
silently gets muya's 800px. **The default theme *is* the 800px case.** D4's
test case is therefore two real themes rather than a default and an override,
which is a better test than the one §5 asked for.

**Why not a CSS parser**, stated precisely because it is the option the input
format keeps recommending: the CSS that would have to be parsed is not the
41-declaration variable block, which is flat and trivial. It is the outliers —
`!important`, pseudo-element redefinition, `content: ''` overlays, and a
`transform` composed against the one muya already applies. A parser faithful to
that is a cascade engine, and a cascade engine is the thing M3 exists in order
not to have.

**Why TOML rather than Rust literals**, given that M2's ratchets are Rust
consts for exactly the reason that they have a single consumer: this one does
not. M5 owes an import path that reads a MarkText installation's 32 stylesheets,
and its output has to be *writable*. A const is not an export target.

**The code palette is a field, not a convention.** MarkText ships 31 Prism
stylesheets for 32 themes, pairs them in a hand-written switch statement
(`util/theme.ts:59-198`), has `material-dark` silently reuse `dark`'s, and has
nothing at all checking that a pairing is right. None of the 31 files defines a
single custom property — they are 100 % literal `.token.*` selectors. So the
palette is a second typed struct keyed by Prism token class, and `Theme` names
its palette **by value**.

**Fonts.** No theme file sets `font-family` — zero declarations across all 32.
The two stacks are muya's own, so they are theme fields whose shipped value
happens to be identical everywhere. **S1's owed face list (D7) is therefore a
property of these two fields**, and D7's hard-error-on-empty rule is what makes
a family that resolves to nothing loud instead of subtle.

#### What the schema cost, and the argument for it was right about the wrong thing **← built at S1**

**148 required leaf fields**, no `serde` default anywhere, `deny_unknown_fields`
on every struct, in two themes: `muya-default` and `dark`. D4's central
argument is mechanised rather than asserted — a test deletes each of the 148
fields in turn and requires every deletion to fail the load. Six fields were
added later in the stage when the footnote turned out to be undrawable without
them, and the test simply ran over the larger count.

**The silent-fallthrough argument survives and its stated mechanism does not.**
D4 says the `light` install leaves 39 of the 41 variables muya reads undefined,
so they *"fall through to CSS initial and inherited values, which mostly works
by luck."* They do not. **muya's own `index.css` defines all 41 kebab names** —
verified as an exact set-equality against the 32 themes' 41-name union — so
`light` resolves to a **second, divergent palette** rather than to initial
values, and the two disagree on four names including the one carrying 800/750.
That is a *worse* failure mode than the one D4 described, not a milder one: a
theme that silently works and silently differs is harder to notice than a theme
that silently looks unstyled. The decision is unchanged and better founded.

**Three counts in the section above are wrong.** The colour census is **34
colour + 5 compound + 1 gradient**, not 36 + 4 — `--button-bg-color-hover` is a
`linear-gradient`. The outlier rules carry **zero `!important`**; they win on
source order, and they *do* use variables for colour, so only "literal
geometry" survives of that sentence. And **"3 of 32 themes override geometry"
undercounts badly**: **30 of 32** also set `border: none` on
`pre.mu-code-block`, zeroing muya's 1px code-block border. `dark` is one of
them, so the two S1 themes differ on **two** geometry axes rather than the one
this section designed the test around — and the second one is visible in the
goldens, where `dark`'s first code glyph sits at x = 15.40 against
`muya-default`'s 14.40.

**One thing owed to M6, found while transcribing.** `util/theme.ts:50` wraps
every theme patch in `@media not print`. So PDF export silently reverts to the
base stylesheet's geometry — 800px column, 1px code border — no matter which
theme is selected. §3's *"one engine, three consumers"* promise means M6 has to
decide whether that is a bug to fix or a behaviour to reproduce; either way it
should not be discovered by looking at a PDF.

### D5 — M3 drives full `parse()`, and `mt_md::reparse` stays unproven **← decided at open**

M2 §10's instruction is *do not build on `mt_md::reparse` without
re-establishing it first*, and it offers two acceptable paths: close the class
with a delta-debugging campaign, or drive full `parse()` calls and treat the
incremental path as an unproven optimization. **M3 takes the second, and the
argument is that M3's scope makes it free:** a read-only viewer re-parses on
file open, not on keystroke. Nothing in M3 needs the incremental path, so
adopting it would import an open defect class for no benefit.

Two consequences recorded so this is not read as the debt being paid.
**M4 still owes the re-establishment** — the class is open, and M4 is where an
editor runs it on every keystroke. And **M3 must not quietly grow a dependency
on it** through a "fast reload" convenience; §6's S7 gate asserts the absence.

### D6 — the previewer is a workspace member outside `crates/`, beside `xtask` **← taken at S1 open, and it is a fourth option this section did not list**

§1's tension. The three options offered were a `[[bin]]` in `mt-cli` · a binary
in `mt-app` opened early · a non-member crate outside `crates/` the way `fuzz/`
is a separate workspace.

**Decision: `previewer/`, a root workspace *member* alongside `xtask` — outside
`crates/`, but inside the workspace and inside the lockfile. At M5 its contents
move into `crates/mt-app` and the directory is deleted.**

**Reading the check rather than quoting it changes what the constraint is.**
`xtask/src/deps.rs:126-146` calls `read_dir` on `crates/`, sorts the
subdirectory names, and compares them to a 14-name const — a **directory-name
comparison, not a dependency-graph one**. The forbidden-dependency and no-I/O
scans then iterate only those 14 names and apply the `winit`/`vello`/`wgpu`
prohibitions to the four `HEADLESS` crates. So the purity D6 was trying to
protect is **per-crate, not per-workspace**: `mt-layout` cannot acquire `winit`
no matter where the previewer lives, and a directory that is not under
`crates/` is invisible to the check whether or not it is a workspace member.

**And the precedent §5 reached for is not the closest one.** The root manifest
is `members = ["crates/*", "xtask"]` with no `exclude` key. **`xtask` is already
a workspace member outside `crates/`** — it has been since M0, it is fully
linted and tested, and it is the shape D6 needs. `fuzz/` and `spikes/` are
separate workspace *roots*, which is a different and heavier thing.

Three reasons the member beats the sibling workspace, and the third is the one
that decides it:

- **One lockfile, so D2's pin cannot drift.** A sibling workspace resolves its
  own graph — `spikes/` exploits exactly that to hold two parley revisions at
  once. For a shipped binary that property is a hazard rather than a feature:
  the previewer would be built against a parley revision the goldens never saw,
  and D2's pin is the entire basis on which a golden is reproducible.
- **CI coverage outside the workspace is not free, and `spikes/` is the proof.**
  `cargo test --workspace` and `cargo clippy --workspace -D warnings` resolve
  against `members`, so neither reaches a sibling root. `fuzz/` is covered only
  because someone wrote an explicit `cargo +nightly fuzz build` step
  (`soak.yml:88-90`); **`spikes/` appears in neither workflow — nothing builds,
  tests or lints it today.** Taking the sibling option means owing that step,
  and the repository already contains one instance of that debt going unpaid.
- **A spike is by definition a crate that should not survive.** `spikes/`'s own
  manifest says so. The previewer is R8's public ship and M5's starting point.
  Filing it beside the disposable things is the wrong signal to leave in the
  tree for two milestones.

**The cost, stated rather than elided:** `winit` and `vello_cpu` enter the root
lock graph at S1, so `cargo test --workspace` compiles them. That is a build-time
cost and not a purity one — the check that guarantees `mt-layout` stays headless
reads manifests, not lockfiles, and is unaffected.

**Rejected, with reasons.** `mt-cli` is genuinely close — it has a `[[bin]]`,
it already calls `std::fs::read_to_string`, its own doc comment says *"it is a
program, not a library component,"* and `ci.yml` already builds it. But its
contract is *"argv handling, headless convert, `--dump-state"`*, and it is the
Rust half of the differential harness; giving it a window makes the harness
binary drag a GPU-less-VM matrix behind it. `mt-app` is M5's, with a committed
scope of menus, dialogs, credential storage and session, and opening it early
means M5 refactors around M3's previewer instead of absorbing it.

### D7 — fonts: the collection is built above `mt-layout` and passed in **← taken at S0**

C9: parley's default `system` feature does filesystem I/O, and `mt-layout`
commits to none. MarkText bundles Open Sans and DejaVu Sans Mono as files and
names four fallbacks after each.

**Decision: the third option — `mt-layout` depends on parley with
`default-features = false`, never enumerates anything, and receives a font
collection constructed by the shell. Goldens run against a pinned bundled set
registered from bytes; the shipped previewer adds system fonts on top.**

It was "the one to beat" and nothing beat it, because S0 found it costs less
than the alternatives rather than more:

- `default-features = false` (plus `std`) builds and lays out, and drops the
  dependency count **61 → 49** crates. The purity constraint is cheaper than
  the default.
- In-memory registration is a two-call API:
  `Collection::new(CollectionOptions { shared: false, system_fonts: false })`
  then `register_fonts(Blob<u8>, None)`. No path, no enumeration, no I/O.
- Goldens become reproducible across machines by construction — which §7 needs,
  since textual layout goldens are M3's primary instrument and a golden that
  depends on the developer's installed fonts is not a golden.

**Three measured facts turn the bundled half into concrete work rather than a
checkbox**, and the first is a trap that would have cost a stage to find later:

1. **MarkText's bundled Open Sans cannot be used.** All eight files are `.woff`,
   and skrifa **rejects them silently** — `register_fonts` returns an empty
   `Vec` rather than an error. A font that fails to load without saying so
   produces a layout that is subtly wrong everywhere, with no diagnostic. The
   four DejaVu Sans Mono `.ttf` files (**1,178,216 B**) load fine. **M3 must
   re-source Open Sans as `.ttf`/`.otf`, or decompress at build time, and must
   treat an empty registration result as a hard error.**
2. **The bundled set does not cover the corpus.** DejaVu Sans Mono renders
   Arabic (0/11 tofu) but **not Hebrew (8/9 tofu)** — and `bench/corpus/rtl.md`
   is half Hebrew. The gate says *"Bidi … render correctly"*, so a
   Hebrew-capable face is a **deliverable, not a nicety**. CJK and emoji are the
   same question unanswered: `cjk.md` and `emoji.md` are gate inputs too.
3. **`complex-scripts` costs +3.6 MiB** and 0 extra crates (C9). The gate's CJK
   clause almost certainly requires it, and it is the second-largest line item
   in the binary after the GPU backend that D1 just declined to ship.

**S1 owes the face list**, since D4's theme model names font families and a
family that resolves to nothing is the failure mode above.

#### The face list, and registering a face is not the same as reaching it **← built and measured at S1**

`assets/fonts/` holds **twelve faces, 4,388,460 B**, all OFL 1.1 or Bitstream
Vera, each with an upstream URL, a version and a SHA-256, outside `crates/`
because `mt-layout` opens nothing. `faces.toml` is the artifact, and **its
order is the fallback chain**, so reordering it is a golden-changing event on
the same footing as moving the pin. Corpus coverage went from 145 of 291
distinct non-ASCII codepoints to **291 of 291, zero tofu**, measured by laying
text out through parley rather than by reading a `cmap`.

**M3-R10's Hebrew clause was already discharged by D7's own instruction, at
zero cost.** Re-sourcing Open Sans as `.ttf` fixes the tofu the risk is about:
**upstream Open Sans 3.003 carries 45 Hebrew codepoints**, and MarkText shipped
the *latin-only web subset*. `rtl.md` is 49 of 49 with no `.notdef` and no
Hebrew face is vendored. The risk described a font problem that another line of
the same decision solved.

**Two things D7 does not say, and the second is load-bearing.** Fact 2 above
measured only the *upright* DejaVu faces; the two obliques carry **zero** Arabic
codepoints, so emphasised Arabic had no covering face at all. And **registering
the faces is not enough**: the theme's own stacks taken verbatim leave **249 of
291 as tofu**, because parley resolves emoji through
`GenericFamily::Emoji` and *not* through script fallback — a Noto Emoji
registered as a `Zsye` fallback is never consulted, and 67 of `emoji.md`'s 82
stayed tofu until `append_generic_families` drove it — while with
`system_fonts: false` the stacks' trailing `sans-serif` and `monospace` resolve
to nothing whatsoever. `faces.toml` carries that wiring as data beside each
face, because it is a property of the collection and not of the code.

**CJK is a decision taken with prices, and the artifact is a test fixture.**
Nothing renders `cjk.md` inside a sane repository budget: Noto KR alone is
4.6 MB for 123 of 140, JP+KR 9.2 MB for 128, SC+KR 13.0 MB for 140, and the
single `NotoSansCJKsc-Regular.otf` 16.4 MB for 140. So the goldens get a
**`pyftsubset` of that OTF — 56,268 B, 0.34 % of its input, 140/140 through the
real chain with zero `.notdef` over 726 glyphs.** This is D7's own split
honoured rather than bent: *"goldens run against a pinned bundled set … the
shipped previewer adds system fonts on top"*, so the bundled set exists for
**golden reproducibility** and real-user CJK is S5's. It is labelled a test
fixture everywhere, carries `derived = true`, and the probe prints
`DERIVED-FIXTURE` on every run. Byte-identical across two subsettings, with the
command line, the fontTools version and both hashes recorded.

**The fixture's fragility is a written contract, not a hope.** A subset derived
from the corpus stops covering the corpus the moment the corpus changes, so
`cargo xtask layout` runs `assert_corpus_fully_covered` before it writes or
compares a single golden: every codepoint in every input is resolved against
the collection and the command hard-fails, listing offenders, on glyph id 0. It
fails rather than warns for the reason D7 gives about `register_fonts` — **a
tofu advance makes a perfectly valid-looking golden.** That is now the third
layer of this milestone applying the same rule.

**The pin costs an MSRV bump that nobody priced.** `parley_engine` calls
`icu_properties::PropertyNamesShort::new()` inside a `static`; it became `const`
in `icu_properties` 2.2.0, which declares `rust-version = "1.86"`, and cargo's
MSRV-aware resolver will not select it at 1.85 — so the ICU family is held at
2.1.x and `parley_engine` fails with `E0015`. **There is no version of this
workspace at 1.85 that compiles.** parley's own manifest declares only
`icu_properties = "2.1.1"`, so the bound is under-specified upstream rather than
stated by D2. RUST-REWRITE-PLAN.md §1's floor and `docs/M0.md:289` are both
stale as of S1.

### D8 — a neutral display list `mt-layout` owns, with the font reference as the one named exception **← taken at S1 open**

§5 sketches `BlockContent::Text { layout: parley::Layout<Brush>, … }` — i.e.
`mt-layout`'s public type exposes parley's. The alternative is a neutral display
list of positioned glyph runs and rects with parley confined behind the seam.

**Decision: the neutral list. `parley::Layout` is held per block *inside*
`mt-layout` and appears in no public type. The font reference crosses the seam
as a `FontId` indexing the collection the shell supplied under D7.**

**The seam is far smaller than the sketch implies, and the spikes measure it
rather than estimating it.** The walk a renderer performs is
`Layout → lines() → Line::items() → PositionedLayoutItem::{GlyphRun, InlineBox}`;
a `GlyphRun` bottoms out at a `Run` (font, `font_size`, `is_rtl`, `text_range`)
plus `PositionedGlyph { id, x, y }`, and an `InlineBox` at
`{ id, x, y, width, height, baseline }`
(`spikes/e2-vello-cpu-parley-main/src/main.rs:77-101`,
`spikes/e1-parley-main/src/main.rs:454-497`). **Every field on that walk except
one is already a plain `f32`, `usize`, `bool` or `Range<usize>`.** The neutral
form is very nearly a rename, not a translation — which is why the option §5
framed as the expensive one is not.

**The exception, and it is the whole cost.** `Run::font()` returns
`&FontInstance` whose `.font` is a `FontData` handle, and E2 feeds it straight
into `vello_cpu` with no wrapper at all. D7 is what makes the `FontId` answer
cheap rather than novel: the font collection is already constructed *above*
`mt-layout` and passed in, so the shell that registered the faces is the same
one that resolves an id back to bytes. **No spike has built that mapping, and
this decision does not pretend otherwise.** If resolving parley's handle back to
a registered face turns out not to be cheap, the fallback is to carry the handle
itself across the seam and leave the other dozen-odd fields neutral. The seam
does not collapse in that case; only its purity does.

**What the decision does *not* buy, said first so it cannot be claimed later.
It does not protect the goldens.** The parley churn D2 actually pinned around
was *geometric* — #697 moved line height 24.00 → 28.40 and baseline
22.00 → 24.00 — and a neutral display list carries the new numbers just as
faithfully as parley's own type would. A pin move rewrites goldens either way;
what makes that survivable is D10's header line, not D8.

**What it does buy is the consumers.** `mt-export`'s doc comment commits M6's
PDF writer to computing no geometry of its own, and the display list is its
input; exposing `parley::Layout` would make a milestone two ahead depend on the
internal walk of a git-pinned 0.x crate. The same holds for `mt-render` and for
whatever M4 hit-tests with. C9's sub-question stands unchanged: the list carries
plain `f32` rects, never kurbo or peniko types, and since `Brush` is parley's own
trait rather than `peniko::Brush`, `mt-layout` defines its own brush type in
either design — that part of the seam was always free.

**Hit-testing, which this section assumed and no experiment has touched.**
`mt-layout`'s stub says cursor motion *"must go through parley's cluster API"*
and C9 forecasts `Cluster` changing shape unreleased — but **no spike references
`Cluster`, `hit_test` or cursor motion anywhere**, so the claim that this API
resists a neutral wrapper is an argument, not a measurement, and it is labelled
as one. M3 does not decide M4's hit-testing. It decides the *shape* of the
answer: if M4 needs cluster-level behaviour, `mt-layout` grows a **method** —
point in, offset out — rather than exposing the `Layout`. That keeps `Cluster`
churn inside one file, which is what R4's mitigation already asks for.

**Two consequences elsewhere.** D10's golden serializes a type M3 owns, so a
golden's *shape* changes only when M3 changes it. And D11 needs a block-kind
discriminator on the list so that M6 can replace the math and diagram arm
without re-plumbing layout.

#### The `FontId` mapping is built, not fallen back from **← built at S1**

§9 recorded this as the one part of the seam no spike had exercised, and gave
S1 permission to carry parley's handle across instead. **It did not need to.**
`FontId` keys on `(Blob::id(), FontData::index)`, and `Blob::id()` is an
atomic-counter `u64` that `Clone` **copies** — every hop from `register_fonts`
through `SourceKind::Memory`, `SourceCache::get` and `QueryFont::blob` to
`FontData` is a clone, so the identity holds *by construction* rather than by
pointer luck, which is the failure mode this could have had. Proved by laying
out one line of mixed Latin, Arabic, emoji and Chinese through the theme's own
body stack: zero tofu, four runs, each resolving to the face that covers it —
which exercises named-family, script-fallback and generic-family selection
separately rather than trusting one path to stand for three.

One consequence, recorded because it will bite a later stage: **`Blob::id()` is
process-unique**, so a tree built against one collection and emitted against
another fails every run with an unresolved font. Anything that builds and emits
must thread one collection through.

**Four imprecisions in the section above, all in the direction of the walk
being slightly richer than the sketch.** There is no `PositionedGlyph`; the walk
yields `Glyph { id, x, y, advance }`, a fourth field, dropped losslessly into
the run's own offset and advance. `InlineBox::baseline` is `Option<f32>`, not
`f32`, and the `None` is an instruction rather than a gap.
`PositionedInlineBox::kind` is a **second** parley type on the walk, so *"every
field on that walk except one"* is off by one. And `Brush` came out better than
forecast: it needs **zero** conversion, because `mt-layout`'s own brush type
directly parameterises the stored `parley::Layout<Brush>`.

**The public surface holds.** No public item in `mt-layout` names a parley
type — audited both by source grep and by scraping every rendered rustdoc
signature block. `InlineBox::baseline`, the feature D2 moved the pin for, is
still **untested**, because S1 pushes no inline boxes; S2 should assert it
early rather than at the end.

### D9 — laziness is load-bearing, and S1's data structures must anticipate it **← taken at S0**

§5 says *"never lay out the whole document synchronously"*, C8 says muya does
exactly that, and C5 says a width change is cheap while content is not. S0
measured the honest version.

**Decision: D9 resolves to its second branch. Eager single-threaded layout of
5 MB misses the gate, so laziness is not an optimization with a stage of its
own — S1's data structures have to anticipate it.**

| | |
|---|---:|
| `mt_md::parse`, `5mb.md` | **81 ms** |
| eager layout, one `Layout` per block | **813 ms** (median, 805–829 over 8 launches) |
| **end to end** | **≈ 896 ms — 112 % of the 800 ms gate** |
| blocks / lines | 39,308 leaves / 92,758 lines |
| peak RSS, `1mb.md` | 84.6 MiB (gate ≤ 120 MB) |
| peak RSS, `5mb.md` | 379 MiB |

Hardware: i5-13600K, 64 GB, NVMe, Windows 11, `--release`, warm file cache.
**This is a fast 2022 desktop, so 12 % over is the optimistic reading**, and the
figure is a **lower bound**: it lays out plain text as a single style run, with
no `mt-inline` tokens and no `InlineBox`es. A synthetic styled variant costs
**+10–13 %**.

**Three findings that constrain S1 rather than S6.**

**Laziness must defer shaping, not line-breaking.** The phase split is
**shaping 90.3 %** (720 ms), `break_all_lines` 8.1 %, builder setup 1.5 %,
`align` 0.1 %. A lazy design that defers only line-breaking defers 8 % of the
cost. What must be deferred is `builder.build` itself — which means the data
structure holds *unbuilt* blocks, and "a block that has no `Layout` yet" is a
first-class state in the tree from S1, not a cache miss bolted on at S6.

**§5's `Code { lines: Vec<Layout> }` is refuted.** Against one `Layout` per
fence, one per code line is **1.38× slower and 2.21× the memory** (1,194 ms /
607 MiB vs 863 ms / 275 MiB over 120,000 code lines). The deciding constant:
**a `parley::Layout` costs 3,956 B resident** against a 328 B struct, so a
100,000-line code file would spend **377 MiB and 636 ms** on the split alone.
**S1 builds one `Layout` per fence.** The same constant explains the whole
result — layout cost scales with *block count* × a fixed per-`Layout` price,
not with document size, and ns/byte actually *falls* 367 → 148 as documents
grow (C5). **The lesson generalises: any S1 design decision that multiplies
`Layout` count is the expensive one, whatever it is optimizing.**

**A third option the plan does not consider, and it is cheaper than laziness.**
Layout is embarrassingly parallel — each block's `Layout` depends on its own
text, the theme and the width, nothing else. Measured with `std::thread::scope`
and a byte-balanced split, no `rayon`, no new dependency:

| threads | 1 | 2 | 4 | 8 | 20 |
|---|---:|---:|---:|---:|---:|
| best | 794 ms | 483 ms | 421 ms | 349 ms | **334 ms** |

**Parse + parallel eager layout = 415 ms, inside the gate with no laziness of
any kind.** Scaling plateaus at 2.37×, most likely allocator contention — a
hypothesis S0 did not profile, and it should be labelled as one.

This does not overturn the decision: single-threaded eager misses, which is what
D9 asked. But it is a second lever that needs **no viewport tracking, no
invalidation, no scroll-driven layout queue, and no change to S1's data
structures**, and it composes with laziness rather than competing. **S6 costs
both before committing to the lazy architecture alone** — and S1 should not
assume the lazy path is the only thing standing between M3 and its gate.

#### The phase split measures the layout call and the pipeline is a third longer **← measured at S1**

D9's four phases — shaping 90.3 %, `break_all_lines` 8.1 %, builder setup
1.5 %, `align` 0.1 % — sum to the cost of *building* the `Layout`s. They do not
include producing anything a renderer can consume, because at S0 nothing could.
**Emitting the display list costs 468 ms on `5mb.md`**, which appears in no S0
number. Eager end to end is therefore **≈ 1,297 ms against an 800 ms gate**,
not the 896 ms D9 recorded, and D9's headline arithmetic — *112 % of the gate*
— should be read as **162 %**.

Two consequences, and the first sharpens D9 rather than contradicting it.
**Deferring shaping alone no longer reaches the gate**, because 468 ms of the
remainder is not shaping; S6 has to defer or parallelise emission as well, and
the parallel lever measured above was measured on layout, not on emit. And the
lazy driver's job got easier in exactly the place the eager one got harder:
emission is per-block and viewport-shaped by nature, so a driver that emits
only visible blocks avoids most of the 468 ms without needing an estimator,
whereas the estimator is still required for *placement*.

**S1's structure is sized for this.** `plan()` shapes nothing and costs 6 ms
for `5mb.md`'s 54,896 blocks; `build(i)` touches only block `i`; `build_all` is
a loop over it. What S6 still needs is written down rather than left implied: a
height estimator, a resumable flow cursor, a revision check, and a per-viewport
emit.

### D10 — line-oriented text goldens, one file per corpus file per theme **← taken at S1 open**

§11.3 asks for *"golden images per block type per platform, perceptual-diff
threshold"*. That is a `mt-render` test. `mt-layout` is headless and deserves a
**textual** golden — a stable serialization of the display list — because a
text diff names the block that moved and a pixel diff does not. Two artifacts,
two stages, two thresholds: exact equality for layout, perceptual threshold for
pixels.

**Decision: one line-oriented text file per (corpus file × theme) under
`bench/layout-goldens/`, written and compared only by `cargo xtask layout`,
exact equality, `--update` the sole writer.**

**The finding that shapes it is that there is nothing to copy.** Despite two
milestones of test infrastructure, **no golden file exists anywhere in this
repository.** `diff` and `blocks` generate both sides live and compare in
memory, writing nothing; `conformance` compares against spec fixtures and
ratchets `spec/expected-failures.json`, which holds *failing example numbers*,
not expected output; M2's own harnesses keep expectations as inline Rust
literals beside a `PENDING` const, deliberately, because each has a single
consumer. `insta` is not a dependency and neither is any other snapshot crate.
**D10 is a new instrument rather than an application of an existing one**, so it
should inherit properties from what works here rather than shapes.

Four properties, each borrowed from something already load-bearing:

1. **`--update` is the only writer, and a regeneration is reviewed in the same
   commit as whatever changed the output.** This is `expected-failures.json`'s
   ONE-WAY DOOR rule pointed at a different artifact, and it is what turns
   M3-R6's mitigation from an intention into a mechanism.
2. **Line-oriented custom text — not JSON, and specifically not `insta`.** A
   golden's whole job is to make `git diff` name the block that moved; brace and
   indent noise defeats that. And `insta`'s review flow is an accept-all button,
   which is precisely the rubber-stamp failure mode R6 names — adopting it would
   import the risk the risk register already lists. Hand-rolled over dependency
   is also the house style, for the reason `deps.rs:14-17` gives.
3. **A header line records theme, width and the parley revision.** A pin move
   then appears as a one-line diff at the top of every golden, above the geometry
   changes below it — which makes D2's *"a pin move is a reviewable event on the
   same footing as a golden update"* an artifact rather than an instruction.
4. **Float precision is part of the format, fixed at two decimals.** Goldens are
   produced from a pinned font set (D7) and a pinned parley (D2), so a platform
   that disagrees at 2 dp is a **finding**. Loosening the precision is therefore
   a reviewable event, not a fix — the distinction that keeps a threshold from
   quietly absorbing a real divergence.

**R6's first-review clause, discharged where it can be checked.** The first
golden for each block kind is read by eye once, and §6's S1 record names what
was reviewed. A review that is not written down is indistinguishable at S4 from
one that never happened.

#### The format, and two places the decision needed extending **← built at S1**

**24 goldens, 687,653 B**, under `bench/layout-goldens/`, eleven inputs plus a
twelfth added for the block kinds the corpus could not reach, at two themes
each. `bench/corpus/README.md` is **not** an input: the corpus is generated and
checked by `cargo xtask corpus --check`, and coupling prose edits to golden
churn erodes exactly the review ritual R6 depends on.

**The header records the face set as well as the pin.** D10 asks for theme,
width and parley revision. It gets those plus the **SHA-256 of `faces.toml`**,
because the font set determines geometry exactly as much as the pin does and a
face swap must be as visible as a pin move — the same argument D10 makes for
property 3, applied to the other input it did not name. It also records the
parse options, since one input needs `footnote: true` and a golden must not be
readable as the default configuration when it is not.

**Two large inputs cannot have the golden D10 describes, and the numbers say
so.** A full serialization is 802 KB for `250kb.md`, 3.2 MB for `1mb.md` and
16.7 MB for `5mb.md` at each theme — **41.5 MB of goldens**. A golden a human
cannot open is R6's failure mode with extra steps, so those three take a
**digest** form: the same header, a per-kind census, block count, total height
and a hash of the full serialization, **5.8 KB in total**. Exact equality is
unchanged; a drift still fails, it just fails without a 40 MB diff. `250kb.md`
at 802 KB was openable and went to digest anyway, because the census shows all
three come from one generator and exercise the same six kinds the small full
goldens already carry legibly.

**Granularity is the property D10 left open.** Per-glyph output is roughly
twenty times larger and makes the diff name a glyph where property 2 wants it
to name a block. So the default is per-block and per-item, and every glyph run
carries eight hex of a hash over its `(id, x, y)` sequence — which keeps a
shaping change that preserves count and advance from passing. Per-glyph detail
is available behind a flag for debugging, never in a committed golden.

### D11 — math and diagrams lay out as their own source, in the code-block style **← taken at S1 open**

`MathBlock`, `Diagram` and inline math are real `Block` variants that M2 parses
and M6 renders. A previewer that shows nothing for them looks broken; one that
renders them needs KaTeX and mermaid equivalents that do not exist.

**Decision: lay them out as their own source text in the code-block style, with
the language named. Inline math takes the inline-code style on the same rule.**

**The precedent is not a plan, it is already shipped.** `mt-md`'s static HTML
renderer emits `<pre class="multiple-math" data-math-style="…">` around the
escaped source for `Block::MathBlock` (`crates/mt-md/src/html.rs:270-277`) and
routes `Block::Diagram` through the ordinary code-block path with
`diagram_lang(kind)` (`html.rs:256-258`), under a test named
`math_renders_as_source_because_there_is_no_tex_renderer_yet`
(`crates/mt-md/src/html/tests.rs:224-238`). M2 took this decision for the
identical reason and recorded the two `PENDING` state-spec cases it costs as
*"owed to M6 with `mt-math`"*. **D11 is that same decision restated for a second
consumer** — and the point of stating it rather than re-deriving it is that the
two paths then agree by construction rather than by coincidence.

**One mechanical consequence this section did not anticipate.** §6's S3 names
`Block::highlight_language()` as `mt-highlight`'s only language source, and it
pattern-matches `Block::CodeBlock` alone — returning `None` for every other
variant, enforced by `highlight_language_is_none_for_every_non_code_block`
(`crates/mt-doc/src/block.rs:1044-1057`). **D11 does not change that**, because
the test is right: a math block has no info string. The block → language mapping
belongs to `mt-layout`, which asks `highlight_language()` for a `CodeBlock` and
**reuses `mt-md`'s existing `diagram_lang` for a `Diagram`** rather than
introducing a parallel table. `MathBlock` takes `latex`. A language with no
ported grammar degrades to unhighlighted source, which is S3's coverage number
rather than a defect.

**What the viewer does not do is invent placeholder chrome.** muya keeps the raw
source in the DOM at all times, collapsed off-canvas when the block is inactive,
and on a render failure replaces the *preview* with a sanitized message —
never falling back to showing the source (`diagramPreview.ts:168-207`). A
previewer with no renderer at all is in that failure state permanently, and the
honest presentation of a permanent failure state is the source with its language
labelled, which is what a reader would see in any other editor.

**Owed to M6:** the display list carries a block-kind discriminator (D8), so
`mt-math` and `mt-diagram` replace this arm rather than threading a new path
through layout to reach it.

#### The rule extends to two more kinds, and the table moved rather than being copied **← built at S1**

D11 names `MathBlock`, `Diagram` and inline math. Laying the corpus out found
two more blocks in the same permanent failure state: **`HtmlBlock`** (no HTML
renderer, and there will be none before M5's paste path at the earliest) and
**`Frontmatter`** (no YAML/TOML view). Both take the code-block style with the
language named — `html`, and the front matter's own `lang` — by D11's own
reasoning rather than by a new rule, and muya's own stylesheet already groups
all five constructs, so this is less an extension than a completion.

**The one-table requirement was met by moving the table, not by importing it.**
`diagram_lang` was a private `fn` in `mt-md`'s HTML renderer, and there turned
out to be **four** copies of the mapping across that crate. It now lives on
`mt_doc::DiagramKind` — next to the type it switches on — with `html.rs`,
`serialize.rs` and `state.rs` delegating and no `mt-md` test changed. So
`mt-layout` needs **no dependency edge on `mt-md` at all**, which is a better
outcome than D11 asked for: D5's *"must not reference `mt_md::reparse`"* becomes
true by construction rather than by discipline, and S7's assertion of it becomes
a formality.

**A footnote needs a non-default parse, which is now visible in the golden.**
`Options::MUYA_DEFAULT` sets `footnote: false`, exactly as muya does, so a
`Footnote` block cannot occur in a default document at all. One corpus input
gets footnotes enabled through a table of per-input overrides, and the golden's
header lists every parse option so it cannot be misread as the default
configuration.

### D12 — an inline image is sized from above the seam, and an image with no size is not a number this project invents **← taken at S2 open**

D7 put the font collection above `mt-layout` because the crate opens nothing.
An inline image is the same problem one layer up and S1 left it unnamed: an
`InlineBox` needs a width and a height before parley can place it, and the size
of a PNG is in the PNG.

**Decision: `mt-layout` receives a resolved image-size lookup the way it
receives a font collection — built by the shell, keyed by the token's own `src`,
passed in beside the theme and the width. A `src` with no entry neither guesses
nor errors: it takes the reference's own no-bitmap geometry, which is specified
in CSS and which nobody had read.**

Three ingredients, and the third turns this from a design question into a
transcription.

**The token carries no size, and markdown has nowhere to put one.**
`mt_inline::token::Image` is `{ marker, alt, src_and_title, src, title,
backlash, attrs }` with `ImageAttrs = { src, title, alt }` — no width, no
height, no aspect ratio; `ReferenceImage` carries less. muya's own renderer
reads `token.attrs.width`/`height` (`inlineRenderer/renderer/image.ts:105-106`),
but those arrive from an inline `<img>` tag's attributes, never from `![…](…)`.

**`mt-layout` may not open the file and could not resolve it if it did.**
`./x.png` is relative to the document, and the document's directory is not an
input to layout — nor should it become one, since §3 makes `Document` the whole
input. The shell already does exactly this shape of work for faces: `FaceList`
declares what to read, `xtask`'s `build_collection` reads bytes and verifies a
SHA-256, and a `FontId` crosses the seam. The image table is that idiom with a
smaller payload.

**The reference specifies three boxes for an image with no bitmap.** This
document has quoted `inlineSyntax.css` for two stages and never read past line
352:

| State | Geometry | Source |
|---|---|---|
| `.mu-image-loading` | **400 × 250**, `margin: 0 auto`, **`vertical-align: bottom`** | `inlineSyntax.css:442-448` |
| `.mu-image-fail` | **100 % × 50 px** | `:434-440` |
| `.mu-empty-image` | the same 100 % × 50 px | `:434-440` |
| either box's ground | `--code-block-bg-color`, `border-radius` **2px** — deliberately not inline code's 3 | `:346-352` |
| the icon inside it | **20 × 20** at `top: 15px, left: 15px` | `:396-410` |
| the label inside it | `top: 15px, left: 50px`, `width: calc(100% - 50px)`, 20 px tall, 14 px at line-height 20, weight 600 | `:450-479` |

`100%` there is the *containing block's* width, so a failed inline image is
700 px wide and 50 px tall at `muya-default` and 650 × 50 at `dark` — a box that
cannot share a line with anything, which is a visible and checkable consequence
rather than a subtle one.

**Which of the three states M3 is in, decided rather than assumed.** muya's
`image.ts:170-193` assigns the classes from one variable: `isSuccess` is
`undefined` while `loadImageAsync`'s promise is pending (`mu-image-loading`),
`false` in its `.catch` (`mu-image-fail`), and an empty `src` never starts a load
at all (`mu-empty-image`). **The shell's table is M3's load**, so a miss is a
completed failure and not a pending one: M3 models `mu-image-fail` and
`mu-empty-image`, and `mu-image-loading`'s 400 × 250 is unreachable because
nothing in M3 can report "pending". S5's previewer is the first thing that could,
and it is recorded in §10 rather than pre-built.

**`InlineBox::baseline` gets its answer from the same rules, which is the part
worth noticing.** `.mu-inline-image` is an `inline-block` with `font-size: 0`,
`line-height: 0` and an empty container, so its baseline is its bottom margin
edge — and the loading rule says `vertical-align: bottom` in as many words. That
is exactly what `display.rs` already documents `baseline: None` to mean: *"align
my bottom edge to the text baseline"*, an instruction rather than a missing
value. The feature D2 moved the pin for turns out to have a reference behaviour
to be checked against, not merely a plumbing test.

**What M3 does not draw, stated so it is not read as an omission.** The label is
`content: attr(fail-text)` where the attribute is `i18n.t('Load image failed')`
(`image.ts:89-90`) — a **localized UI string, not document content**. M3 has no
locale and inventing an English one would put chrome inside a display list that
is also PDF export's input. The box, its ground, its radius and the icon's
20 × 20 rect are drawn; the label is owed to S5, which is the first thing in this
project with a UI language.

**The numbers become required theme fields**, on D4's rule and for D4's reason:
they are geometry, they are transcribed from CSS rather than derived, and a
`serde` default would be the silent-fallthrough failure mode D4 exists to
prevent. Both TOMLs change in the same commit, as they did for S1's six footnote
fields.

### D13 — the visible-text map is a run list on the display list, and C6 is wrong about how it falls out **← taken at S2 open**

C6 says the map from visible-text offsets to block-text offsets *"falls out of
the same walk that builds the style runs"* because `mt-inline`'s tokens carry
`range` and `raw` as absolute spans. §10 requires it to be **public API from S2**,
not an internal detail M4 re-derives.

**Decision: a public run list, carried on the display list beside the leaf that
produced it. Visible → block is total; block → visible is partial and says so.
Each run records which of three things happened to it, because two of the three
change length.**

**C6's premise is wrong in one word, and the word matters.** C6 assumes markers
are *deleted*, so that the visible string is a subsequence of the block text and
the map is a list of surviving subranges. **Three token kinds substitute rather
than delete**: `HtmlEscape` renders `&amp;` as one `&` (muya draws it through
`content: attr(data-character)`), a soft or hard line break becomes a space, and
`Emoji` — if S2 follows the reference — renders `:smile:` as one emoji glyph.
A subrange list cannot express any of those, and a map that silently treats them
as deletions puts M4's caret inside a character. So the runs carry a kind —
**copied, substituted, hidden** — and it is stored rather than inferred from the
lengths, because a substituted run whose two sides happen to be the same length
is indistinguishable from a copied one by arithmetic alone.

**The two directions are not symmetric and the API should not pretend they
are.** Every visible offset has a block offset, so that direction is total.
The reverse is not: a hidden marker's bytes have no visible position at all, and
the honest answer is `None` rather than the nearest visible offset. **A clamped
answer is a lie a caller cannot detect** — M5's search will find hits inside
`**` and needs to know that is what happened, not receive the offset of the `b`
next to it. Callers that want snapping can snap; the map does not do it for them.

**What this does not do**, said now because §0's first owed item is the adjacent
one and the two will be confused: this is the **second** arrow of C6's three-deep
stack. Block-text → source is M2's per-kind inverse, still owed to M4, and D13
neither pays nor narrows it.

**The property test the gate names is a test of the walk, not of the
arithmetic.** *"Every visible offset maps back to a block-text offset whose
token contains it"* is only checkable if the run knows which token produced it,
so the walk carries the token's own range into the run rather than accumulating
lengths as it goes. That is a slightly larger structure than C6 implies and it is
the difference between a test that can fail and one that can only agree with
itself.

#### Two of the three substituting kinds are not substitutions, and one of them was a regression **← measured at S2**

D13 was written three commits before anything laid a token out, and it named
three kinds that substitute. **Only one of them does.** Both corrections came out
of S2's cross-check against the reference stylesheet, not out of reading this
document again.

- **A line break is a break, not a space.** `.mu-content` is
  `white-space: pre-wrap` (`blockSyntax.css:948`), so a soft or hard line break
  inside a leaf *breaks the line* — and the reference says so twice, because
  `exportStyle.css:92-105` re-establishes `pre-wrap` on `p` and tight `li` for
  the explicit purpose of making a soft break survive into exported HTML
  (marktext #3676). Substituting a space was **a regression S2 itself
  introduced**: before markers were hidden, the raw `\n` reached parley and broke
  the line correctly. It merged every multi-line paragraph in **9 of 12 corpus
  files** into one wrapped run — `emoji.md`'s first block 76.80 → 102.40 px,
  `100-inline-math.md`'s third 230.40 → 256.00 px.
- **An emoji shortcode is not substituted either**, and the reference is more
  interesting than either option this document offered: `.mu-hide` — which *is*
  the viewer's state — paints the shortcode's text `transparent` while it keeps
  its full advance, and draws the glyph in an absolutely-positioned `::before`
  1 em to its left. So muya reserves the width of `:smile:` and overlays a glyph
  on it. S2 does not do that, for a reason given in §6's S2 record.

**The decision is unchanged and its justification is now thinner and better.**
One substituting kind is enough to refute a subrange list, so nothing about the
run list moves. What does move is the argument for storing the kind rather than
inferring it: with three kinds it read as bookkeeping, and with one it is the
only thing distinguishing a copied run from a substituted run of equal length —
`&lt;` is four visible bytes and one block byte, but `&#60;` and `&#38;` are not
all such tidy cases, and the arithmetic cannot tell.

**The general lesson is the one S1 already recorded, arriving one stage later.**
D13's three kinds were derived by reading `mt-inline`'s token list and asking
what *could* change length — an argument. The stylesheet was not consulted, and
it is the thing that decides. That is the same failure the nine S1 corrections
share: **the document is most wrong where it reasoned from a structure instead of
reading the reference.**

### D14 — the grammars are **generated from a loaded Prism**, not transcribed from its source **← taken at S3 open**

Hand-transcribe each grammar · parse the grammar files as JS and translate them ·
**run Prism once and snapshot the registry it builds**.

**Decision: `mt-highlight`'s grammar tables are generated by loading Prism in
Node, walking `Prism.languages`, and emitting Rust data. The generator is a
committed xtask step; its output is committed Rust, compiled in. No grammar is
read from disk at runtime, and `mt-highlight` opens no files.**

**This decision exists because D3's central claim is false as written, and the
snapshot is what makes it true.** D3 says Prism grammars *"are data, so lazy
loading is free rather than being the dynamic-library subsystem C10 correctly
identifies"*, and that all 297 are covered *"by construction"*. Measured against
the reference clone's `prismjs` 1.30.0:

| | |
|---|---:|
| grammar files that build regexes at load time (`RegExp(…)`, `.source` surgery, or a hook) | **91 of 297 (30.6 %)** |
| …of which call the `RegExp` constructor | 76 |
| …of which do string surgery on another pattern's `.source` | 67 |
| …of which register a tokenizer hook | 21 |
| files that call `extend` / `insertBefore`, so their content depends on another grammar | **130** |
| files that register **no** grammar under their own id — modifier packs only | **5** (`css-extras`, `js-extras`, `js-templates`, `php-extras`, `xml-doc`) |
| languages of the 297 that register a grammar under their own id | **292** |

So roughly a third of the corpus of grammars is a **program**, not a table, and
"297 by construction" was never available. **What rescues the decision is that
every one of those programs runs at load time and none of it survives:** after
loading all 297, the entire registry contains **3 function-valued leaves**.
`extend`, `insertBefore`, constructor-built regexes and `.source` concatenation
have all resolved into ordinary `RegExp` objects by the time the last file is
required. **The expanded registry is data even though the source is not** — so
the port copies the *output* of Prism's load, not its input, and D3's conclusion
(binary cost far below tree-sitter's, lazy loading free) survives on a different
mechanism than the one it named.

**Three consequences that are not obvious and each cost a measurement.**

1. **Load order is load-bearing.** Requiring the 297 in alphabetical order fails
   for four grammars — `jsdoc`, `plsql`, `racket`, `sparql` — because they mutate
   a grammar that has not been defined yet. `components.json`'s `require` field is
   the dependency order and `components/index.js` is the loader that honours it;
   the generator uses it and does not roll its own.
2. **A grammar's content depends on the load set, which makes it a property of
   the differential rather than of the language.** Thirteen files mutate *other*
   grammars globally: `java` is its own definition until `javadoc` loads and 208
   entries afterwards. **Both sides of S3's differential must therefore load the
   same set**, and the generator's set is the definition. A harness that loads one
   language on demand and compares it against a snapshot taken from a full load
   reports mismatches that are its own fault.
3. **The 21 hook grammars cannot be snapshotted and are named rather than
   silently dropped.** Hooks run at tokenize time, not load time, so no expansion
   captures them: `before-tokenize` (14 sites) and `after-tokenize` (38) implement
   the hoisting that templating languages use to embed one grammar in another, and
   `wrap` (6) is HTML presentation with no tokenization content at all. They are
   excluded from the ratchet and listed in it. **The corpus does not need any of
   them**: of its 16 languages only `markup` registers a hook, and it is a `wrap`.

**Why compiled in rather than loaded from disk, since this crate is allowed to
open files.** `cargo xtask deps` names four headless crates — `mt-doc`,
`mt-inline`, `mt-md`, `mt-layout` — and `mt-highlight` is not among them, so
filesystem access here breaks no stated rule. It is still refused, and the reason
is D15's rather than this one's: `mt-layout` **is** headless, it is the consumer,
and a crate that reaches the filesystem on its behalf makes the guarantee depend
on which code path ran. Generated Rust also puts the grammars under the same
review and the same lockfile as everything else, which a data file loaded at
startup would not be. The cost is compile time and binary size, and D3's estimate
of **< 1.5 MB for all 297** is the number S3 must check rather than assume — the
297 grammar source files are 768,444 B before any expansion.

### D15 — highlight spans reach `mt-layout` through `LayoutOptions`, not through a crate edge **← taken at S3 open**

`mt-layout` depends on `mt-highlight` · the shell computes spans and passes them
down · the display list gains a highlight pass after layout.

**Decision: `mt-layout` takes no dependency on `mt-highlight`. Spans arrive as a
caller-supplied table on `LayoutOptions`, beside `images: ImageSizes`, and are
resolved to `StyleRun`s at the one site that already shapes a fence.**

**The check that looks like it decides this cannot.** `cargo xtask deps` is a
line scan over the fourteen manifests plus a substring grep over the headless
crates' `src/`. `mt-highlight` is on neither denylist, so `mt-layout →
mt-highlight` **passes today**; the manifest scan is **not transitive**, so an
`mt-highlight` that opened files would keep passing while §1's actual invariant —
the headless four compile and test with no window and no I/O — was broken. **The
tool would report green on exactly the arrangement it exists to prevent.** So the
edge is refused by construction rather than by the check, and this paragraph is
here because the next stage that reads `deps.rs` for permission will be misled by
it. Whether `deps.rs` should be made transitive is S7's to decide; it is a change
to an instrument, and S3 is not the stage to make one silently.

**The seam is smaller than it looks, and §3's own diagram already drew it.** A
fence is shaped today with literally zero style runs — `flow.rs:783-786` passes
`&[]` and one scalar brush — while the machinery for many runs per line is built,
exercised and visible in the goldens on the heading directly above the first
fence. So the change is three small things: spans in through `LayoutOptions`, one
resolver from token class to `StyleRun` modelled on the existing `style_runs`,
and the `&[]` replaced. **The display-list types, the golden serializer and the
golden format need no change at all**; goldens simply rewrite with more `glyphs`
lines and more than one `fill=`.

Two contracts the resolver inherits rather than invents: runs must be
non-overlapping and ascending, and **a run equal to the block default must not be
pushed**, or every fence pays shaping boundaries for nothing. And one thing that
happens to be free: a code block's visible-text map is
`VisibleTextMap::identity(text.len())`, so `mt-highlight`'s byte ranges are
already ranges into the text `mt-layout` shapes. **There is no offset conversion
at this seam** — the third offset space C6 warns about does not open here.

**`CodePalette` is already built and has never been read.** Its 33 fields — 32
Prism token classes plus `plain` — are deserialized on every theme load and
referenced by nothing outside its own tests. S3 is its first consumer, which
means the palette is a transcription that no artifact has ever checked, and it
must be treated as one.

**One thing the palette's shape forces S3 to decide.** Prism emits
`class="token <type> <alias>…"` and its stylesheets resolve by source order, so
**an alias wins over the type it aliases**. `by_class` takes a single class, so
the resolver must pick a precedence and record it. S3 takes **alias over type,
last alias wins**, because that is what a browser applying muya's own stylesheet
does; the differential compares boundaries and cannot see this choice, so it is
recorded here rather than left to the code.

#### The palette's first artifact, and the transcription was wrong once and incomplete twice **← measured at S3**

D15 says the palette *"is a transcription that no artifact has ever checked, and
it must be treated as one."* The seam's cross-check —
`crates/mt-layout/tests/highlight.rs`, all 32 classes × both themes, every
literal transcribed from the CSS beside it and every number read back out of an
emitted `GlyphRun::brush` — ran **before** a golden was regenerated, and the
33 fields came out as follows.

**What verified.** The class *set* is exactly right: `.token.*` plus
`.namespace` is 32 names in both sheets, set-equal to `TOKEN_CLASSES`, and the
five paint properties those rules use (`color`, `background`, `font-weight`,
`font-style`, `opacity`) are exactly `TokenStyle`'s five fields. All 32 colours
in both palettes match, including the groupings that differ between the two
sheets and the one named colour (`slategray` = `#708090`).

**Divergence 1 — `dark`'s `plain` was `#f8f8f2`, and the rule it came from
matches nothing MarkText builds.** All 31 shipped Prism sheets spell the
container rule `code[class*='language-'], pre.ag-paragraph { color: … }` and
**both** selectors are dead in muya v2: `ag-` is the v1 editor's prefix, and
`codeBlockContent/index.ts:183-188` highlights inside a **detached**
`div.language-<lang>` and assigns only its `innerHTML` back, so no live element
ever carries a `language-` class. Unclassed fence text therefore takes
`.mu-code-block { color: var(--editor-color-50) }` (`blockSyntax.css:207`) in
every theme. `muya-default` had this right by accident — its sheet has no such
rule at all, so the transcriber went to `blockSyntax.css` — and `dark`'s comment
had even noticed that `pre.ag-paragraph`'s *background* was legacy without
carrying the same reading to the *colour* in the same selector group. Fixed:
`plain = #ffffff80`, and asserted as `plain == colors.editor_50` in both themes
so that two transcriptions of one declaration cannot drift apart again. **This
is why the palette is now read rather than merely deserialized.**

**Divergence 2 — `by_class`'s contract said `plain`; a browser says
`inherit`.** *"`None` means paint it as `plain`, which is what the browser does
with a class no rule matches"* is false: an unstyled class inherits. At the top
level of a fence the two are the same number *because* divergence 1 is fixed;
one level in they are not, which is divergence 3. Documentation fixed; the
resolver pushes no run, which is the correct behaviour for the reachable case.

**Divergence 3 — this decision's own precedence loses information when the alias
is *unstyled*, and 15 pattern sites in the ported set are that case.** "Alias
over type" is right whenever the alias is styled, and the confirming half is
measured: the only three patterns in the ported closure where **both** are
styled are `boolean→important`, `builtin→class-name` and `string→url`, and in
both sheets the alias's rule is later in source order, so the alias wins in a
browser too. But Prism also aliases *away from* a styled type, and then the
browser paints the **type** — both classes are on one element, and only one of
them has a rule. In the 16 ported grammars' closure (140 grammars, 877
patterns, 263 aliased):

| type → alias | pattern sites | reached from |
|---|---:|---|
| `punctuation` → `attr-equals` | 3 | `markup`, `java` |
| `entity` → `named-entity` | 4 | `markup`, `java` |
| `keyword` → `control-flow` | 2 | `javascript` and everything embedding it |
| `keyword` → `module` | 2 | `javascript` … |
| `keyword` → `nil` | 4 | `javascript` … |

Across all 297 grammars it is **45 kinds at 231 sites**. Reachable in today's
corpus: **1 span** — the `=` of one HTML attribute — out of 22,259.

**Divergence 4 — `flatten`'s *"innermost wins"* is not what a browser paints
when the innermost class is unstyled, and the differential is green because both
sides share the rule.** `interpreter::flatten` and
`tools/diff/dump-prism-tokens.mjs`'s `flatten` implement the same rule by
construction — that is what makes them comparable — so a defect in the rule is
invisible to the comparison. The rule is right for boundaries and wrong for
colour: a nested token whose class no stylesheet matches inherits its
**enclosing** token's colour in a browser and takes the block default here. In
the ported closure there are **36** such kinds, and the largest is not a corner:
`line inside inserted` and `line inside deleted` are the `diff` grammar, so a
`+`/`-` line's text would be `#22863a` on `#f0fff4` in MarkText and undecorated
block-default here. Others: `unit`/`color inside atrule`,
`n-th`/`pseudo-class`/`combinator`/`id`/`class inside selector`,
`regex-flags`/`regex-delimiter inside regex`, `parameter inside comment`.
Reachable in today's corpus: **0 spans** — the corpus's two `diff` fences are
generated filler with no `+`/`-` line, and its CSS fence uses none of the nested
rules.

**3 and 4 are not fixed at this stage, and the reason is the stage's own
ordering.** Both live in `mt-highlight`'s wire form: the resolved class is
computed by `cargo xtask grammars` at generation time and the flattening rule is
shared with the reference dumper. Correcting either means changing **both sides
of the differential** — which §6 puts before the seam, in a commit that has
already landed — and doing it inside the seam commit would conflate a change to
the instrument with a change to the thing it measures. What the seam does
instead is make them measurable: the corpus emits 14 distinct classes, 2 of them
unstyled, and `by_class` is the single place a future fix would land.

**One number that had never been computed rather than a divergence.**
`.namespace`'s `opacity: 0.7` compounds with the block colour's own alpha. In
`dark` the fence default is `rgba(255,255,255,0.5)`, so a namespace token lands
at alpha **90/255** — an effective 0.35 — where the naive reading is 0.7 of an
opaque colour. In `muya-default` the same declaration over an opaque `#808080`
reads 179/255.

#### What the regenerated goldens showed that the cross-check could not **← read at S3**

The second review, run after `cargo xtask layout --update` and recorded
separately because S2's amendment says the two reviews catch different classes.
**24 goldens, 867,113 → 916,050 B (+5.6 %)**; the seam handed layout **2,506**
code-box blocks and **22,259** spans.

**Nothing moved.** Every `block … bounds=`, every `rect`, every `count` census
line and every `list … height=` is **byte-identical** across all 24 files —
including the three digest goldens, whose heights (`136905.47`, `2680012.00`)
and block counts are unchanged while only the full-serialization hash and its
byte count differ. That is the claim *"a highlight span changes colour, not
metrics"* discharged over the whole corpus rather than argued. Where it could
have failed is measured too: `.token.bold`, `.token.important` and
`.token.italic` do change the **face**, and `tests/highlight.rs` asserts that
DejaVu Sans Mono's four styles leave both the advance and the block height alone
— none of the three is reachable from today's corpus.

**Four things the artifact says and no stylesheet could have.**

1. **The `=` of `class="callout"`.** `block-kinds` block 5, bytes 10..11,
   `fill=#808080ff` between an `attr-name` at `#669900ff` and a `punctuation` at
   `#999999ff`. It is divergence 3's **one reachable instance in the whole
   corpus**, and reading the CSS predicted the shape while only the golden gave
   the location.
2. **The seam feeds D11's non-fence kinds, and `cargo xtask highlight` sees none
   of them.** The differential walks `Block::CodeBlock` only — deliberately, so
   that the gate measures fences — but `mt_layout::code_language` answers for all
   five kinds, so `block-kinds.md`'s **frontmatter** (yaml, 9 spans) and
   **html-block** (markup, 15 spans) are highlighted by code no differential
   covers. Both were therefore checked by hand against a fully-loaded Prism at
   this stage and agree span for span, merges included. The goldens are their
   only standing check.
3. **Three spans become one run, and the golden is where that is visible.**
   `50-code-fences` block 45 is a Go fence whose second line Prism tokenizes as
   **three** adjacent `string` tokens (`` ` ``-delimited, around the line
   ```` ``` not a fence close ``` ````); it draws as a single 25-glyph run at
   `#669900ff`. `mt_highlight::flatten` refuses to merge adjacent same-class
   spans on purpose and `code_style_runs` merges them, and both halves of that
   arrangement are now artifacts. Checked mechanically: **562** code-box glyph
   runs across the full goldens, **zero** adjacent pairs sharing face, size and
   colour, zero runs of zero width or zero glyphs, every same-baseline chain
   tiling in `x` to within 0.02 px and every line seam consuming exactly one
   newline byte.
4. **No class collapses into the block default in either theme.** The 69
   code-box blocks in the full goldens have **identical run boundaries** at
   `muya-default` and at `dark`, which is only true if every styled class
   differs from that theme's fence colour. It is the check that would have
   caught divergence 1 from the other side: with `dark.plain` still `#f8f8f2`
   nothing here would have looked wrong, because `plain` was never read.

**One thing that looked wrong and was right.** A CSS fence draws `3828` as
`number` (`#990055ff`), and stock `Prism.tokenize(code, Prism.languages.css)`
gives only a `punctuation` for the `;`. The port is correct and the check was
not: `css-extras` inserts `number` into the `css` grammar at load time, and
under D14 consequence 2 — *"a grammar's content depends on the load set"* — the
reference is Prism after the **full** 297-file load, which is what the generator
and the differential both use. Re-run that way, Prism agrees exactly.

**Two paths the corpus does not reach**, named rather than assumed covered: the
`TextGround` a `.token.inserted`/`.token.deleted` background produces (the
corpus's three `diff` fences are generated filler with no `+`/`-` line), and the
three weight/style classes. Both are covered by `tests/highlight.rs` and by
nothing in `bench/`.

#### The method that found the defects, and it was not the golden

Before the goldens were written, the emitted geometry was cross-checked against

4. The thematic break sat 1 px low, and **its test asserted the wrong number

5. A nested task list lost a margin the zeroing selector does not name.
6. The bullet cascade counted task-list ancestors the CSS selectors cannot see;

7. The footnote was drawn wrong twice: `opacity: 0.8` applies to the whole

review of the thing it is about to freeze**, and R6's mitigation should be read

#### The method, and this is the stage's most useful finding

S1 closed on the rule that *"a golden's first review is worth less than the
review of the thing it is about to freeze."* S2 ran both reviews deliberately, in
that order, and **they found different classes of defect** — so the rule needs a
second half rather than a repetition.

**The pre-golden cross-check against `inlineSyntax.css` found 14 things**, 12
divergences and 2 instrument defects, 10 fixed and 4 recorded. Every one is of
the form *the stylesheet says X and the code does Y*, and the first was the most
expensive: **marker hiding had turned every line break into a space**, because
`.mu-content` is `white-space: pre-wrap` (`blockSyntax.css:948`) and nobody had
read that line. It merged multi-line paragraphs in 9 of 12 corpus inputs. Two
others were about the instrument itself — the golden carried **no colour at
all**, so every colour decision this stage made was invisible to the thing about
to freeze it, and `GlyphRun::text_range` reported the enclosing shaped run's
range rather than the style run's, which was right by accident until markers were
hidden.

**The golden review then found two more, and neither was reachable by reading CSS
against code.** Both are of the form *the artifact contains something
impossible*:

1. **Inline horizontal padding was painted and never advanced.** The ground rect
   for `padding: 0.2em 0.4em` was drawn around text that had not moved. The tell
   was not a wrong number, it was a **rect at negative x** — `[-5.12 …]`, a
   ground 5.12 px left of the content column — which no amount of reading the
   padding rule against the padding code would have produced. 177 grounds across
   eight goldens. CSS is asymmetric here in a way that is easy to over-fix:
   horizontal padding on a non-replaced inline advances the line, vertical
   padding does **not** affect line box height (CSS 2.1 §10.6.1, §10.8.1), so the
   fix had to leave every height alone. It did.
2. **parley has no strut, and hiding `## ` exposed it.** CSS 2.1 §10.8 gives
   every line box a zero-width phantom in the *block's own* font; parley says in
   its own note that it has none, so a line whose runs all resolve to a fallback
   face is sized only by that face. `rtl.md` block 2 fell 35.60 → 33.60 — Open
   Sans Bold's 26.00/7.60 replaced by Noto Sans Arabic's 24.00/9.60 — the moment
   the only Latin text in the line stopped being drawn. Nine blocks. Fixed in
   `mt-layout`, which owns block geometry, by unioning the strut's
   half-leading-adjusted extent with every inline box's:
   `max(26, 24) + max(7.60, 9.60) = 35.60`.

**So the amendment is that the two reviews are not the same review at different
times.** The cross-check finds what the reference says and the code does not; the
golden review finds what the code emits and nothing could have said. **A stage
that runs only one of them ships the other's class of defect** — and the ordering
still matters, because had the cross-check not gone first, twelve divergences
would have been frozen and the two the golden caught would have been
indistinguishable from them in the diff.

**One finding was wrong and was withdrawn**, recorded because the correction cost
less than the claim would have. The ligature clause was first reported as *"Noto
Sans Arabic does not form lam-alef"* — a claim that implies our Arabic shaping is
misconfigured on the exact construct D2 moved the pin for. It was a misreading of
`is_ligature_start`, which is a **many-to-one** detector and reads `false`
whenever a font implements a ligature as a many-to-many chain-context
substitution, as Noto does. The control that settled it needs no font-table
parsing at all: **U+FEFB *is* the lam-alef ligature by definition, so equal
advances prove formation** — `لا` measures 9.31 against U+FEFB's 9.31 in Noto and
9.63 against 9.63 in DejaVu, where the unligated pair would be 14.93. The
corpus's Arabic **is** ligated. `fi`/`fl`/`ff` ligate at the body stack: two
graphemes, one glyph.

### S3 is open. Two decisions, and the stage's reference can be run rather than read

S3 opens on **two** open decisions — D14 (how a grammar becomes Rust) and D15
(where spans meet the display list) — both taken above, both from measuring the
reference rather than from §5, which names neither. §5 did not anticipate them
because it never asked what a Prism grammar file *is*, and never asked what
`deps.rs` actually enforces.

**What makes this stage different from every other stage in M3.** §7's
uncomfortable sentence is that *"does it match MarkText?" cannot be answered by
running MarkText* — and S3 is the exception it names. The reference here is
Prism's own tokenization, Prism is a Node module in the reference clone, and the
harness that runs it already exists in two working instances. **So S1's and S2's
"check the emitted thing against the reference before the artifact freezes it"
is available on every fence rather than by reading a stylesheet.** The first half
of R6's method stops being a manual cross-check and becomes the gate itself.
That is a strengthening, and it carries one hazard worth naming at open: a
differential that runs is indistinguishable in a summary from a differential that
was skipped, and both look like a passing stage. **S3's record states what was
compared, how many cases, and against what — or it has not discharged the gate.**

**Where S3 expects the plan to be wrong, written before finding out.** §4 C11 and
§5 D3 are the two sections this stage builds on, and both were written from
argument and text-scanning rather than from running Prism. Opening the stage by
re-measuring them found **five** wrong numbers, three of them in the subsection
C11 added at S0 to correct itself — including one that struck a *true* claim about
backreferences while removing a false one about lookbehind. **A correction is not
evidence that the thing is now right**, which is the shape of the finding rather
than a complaint about it, and it is why D14 exists at all: the load-bearing
sentence in D3 — *"grammars are data"* — is false of the thing D3 was looking at.

**Two numbers this stage inherits and must not quietly restate.** The gate says
the differential runs *"over every fence in the corpus"*, and that is **2,512**
fences, of which **2,458 (97.8 %) are generated `rust` filler** of the form
`let value_N = NNNN;`. The number the rest of the plan reasons about is **51 code
blocks in 16 languages**, which is `50-code-fences.md` alone — 50 fences plus one
indented block — and it reproduces exactly against S0's `e4-highlight.md`. S3
runs the gate as written, over all of them, because narrowing a gate on the
grounds that it is slow is the move this project's method exists to prevent;
**and it reports the distinct-input count beside the total**, because "2,512
fences agree" claims coverage that 54 distinct inputs did not buy.

**The order of work, which is S2's amendment applied to a stage that can run its
reference.** S2 established that the pre-artifact cross-check and the artifact
review catch different classes and that neither substitutes for the other. S3 has
both, in an unusual arrangement: the cross-check is *automated* (the differential)
and the artifact review is the goldens. So the stage runs **harness → interpreter
→ differential green → seam into `mt-layout` → regenerate goldens → read them**,
in that order and in separate commits, with the tree deliberately carrying stale
goldens in between. Building the harness before the interpreter is the whole
point: an interpreter written first is an interpreter whose first check is the
thing it was written to satisfy.

## 7. Test inventory — and the finding is that there is not one

M1 transcribed **49** spec cases. M2 transcribed **215** of the 221 its §7
inventories, tracked them in a `PENDING` ratchet, and delisted them stage by
stage until 2 remained — both M6's. Both milestones could also run a **differential** against the TypeScript
engine on every commit, which §11.2 correctly calls the highest-value test
asset in the project.

**M3 has zero transcribed cases, and for most of it no differential is
possible.** There is no muya spec suite for rendering, because the thing being
tested was Chromium. `cargo xtask diff` compares state JSON; there is nothing
to compare a glyph position to. This is the largest methodological change in
the project so far and it deserves stating plainly rather than discovering at
S4.

What replaces it, in descending order of strength:

| Instrument | Covers | Strength |
|---|---|---|
| **`xtask highlight --require-ts`** (S3) | code-fence tokenization vs Prism | A **real differential** — same shape as `blocks`/`diff`, same Node harness. The one place M3 keeps M1/M2's strongest tool |
| **Textual layout goldens** (S1, S2) | the display list, exactly | Strong but *self-referential*: it proves nothing changed, not that anything is right. First goldens must be reviewed by eye, once, deliberately |
| **The §2 CSS table as constants** (S1) | the geometry numbers | The closest thing to a spec M3 has. A stylesheet is a fixed reference even if it is not runnable |
| **Pixel goldens + perceptual threshold** (S4) | rasterization | §11.3's instrument; platform-dependent and threshold-dependent by nature |
| **Corpus-driven property tests** (S2, S7) | bidi/CJK/emoji invariants, determinism, no-panic | Generated input, which M2 S7 proved finds what fixed corpora do not |
| **The Electron baseline** (S0) | the performance claim | Owed since M0 and still not built. Without it, "≤ 800 ms" has no comparison |

**The uncomfortable sentence, written here so no later section can soften it:
for the first time in this project, "does it match MarkText?" cannot be
answered by running MarkText.** It can be answered for code highlighting, and
approximated for geometry by reading a stylesheet. For everything else, M3's
answer is a golden file that someone looked at once.

## 10. Owed forward

Restated at open so the list starts complete rather than accreting.

### Owed to M4 — everything M2 §10 owed to "M3/M4", unchanged

All three items in §0 above are carried without modification. M3 pays none of
them and is not expected to: the per-kind source-offset inverse needs a caret
to have a caller, the reparse class needs an editor to be dangerous, and both
of M1's renderer behaviours are caret-dependent. **The risk is that a fourth
milestone passes them along and the list becomes furniture.** They are restated
here in full rather than referenced, which is the same discipline M2 §10 used
for M1's.

### Owed by M3 to M4 — the visible-text offset map (C6)

New, and M3's own. The map from visible-text offsets to block-text offsets
falls out of S2's style-run walk. M4 needs it for caret placement from a click;
M5 needs it for search-hit positioning. **It should be public API from S2, not
an internal detail M4 has to re-derive** — which is the mistake M2 §10 records
having nearly made with `SourceMap`.

**Delivered at S2 and it is public.** `VisibleTextMap` hangs off the display
list beside the leaf that produced it; M4 re-derives nothing. The property test
the gate named runs over 2,210 corpus leaves and checks the thing that makes it
more than arithmetic agreeing with itself — that the block offset lands inside
the range of the **token** that produced the run.

**Shaped at S2 open by D13**, which also corrects C6's premise: the visible
string is not a subsequence of the block text, because three token kinds
substitute rather than delete, so the artifact M4 inherits is a **run list with
a kind per run** rather than the subrange list C6 describes. The reverse
direction returns `Option` rather than snapping, for the reason D13 gives — M5's
search will find hits inside hidden markers and must be able to tell.

### Owed by M3 to M6 — the display list is PDF export's input too

`mt-layout`'s doc comment commits to *"one engine, three consumers"* and names
PDF export as one of them. M3 has no PDF writer and will not check the claim.
D8's decision — whether the display list exposes `parley::Layout` or a neutral
form — is the one that determines whether that promise is keepable, so **D8 is
recorded as an M6-facing decision taken at M3** rather than a local one.

**Taken at S1: the neutral form.** M6 therefore consumes a type `mt-layout`
owns rather than a git-pinned 0.x crate's internal walk, and the promise is
keepable on M3's side. Two things M6 still has to check that M3 cannot: that the
list carries enough to *embed* fonts rather than merely position glyphs — PDF
needs bytes where the screen needs a handle, and D8's `FontId` is the seam both
go through — and that the block-kind discriminator D11 requires is where
`mt-math` and `mt-diagram` can reach it. **`mt-export`'s own doc comment is
stale** (it predates §4's corrections); M6 rewrites it, and until then it should
not be read as a specification.

**One more thing M3 cannot check, found at S1 and belonging squarely to M6.**
`util/theme.ts:50` wraps every theme's CSS in `@media not print`, so
**MarkText's own PDF export silently ignores the selected theme's geometry** and
falls back to the base stylesheet's 800px column and 1px code border. §3's
promise is that PDF matches the screen *by construction*; the reference's
promise is the opposite by construction. M6 has to decide whether that is a
defect to fix or a behaviour to reproduce, and it should not discover the
question by looking at a PDF.

### Owed by M3 to M5 — the theme model's second half

D4 decides what a theme is. What M3 will *not* build is the preference UI, the
picker, or the import of an existing MarkText install's theme choice — all M5's
per §9. The obligation M3 incurs is that the model must be **expressible from
the 32 shipped CSS files**, since M5's import path has to read them.

**Sharpened at S1, because D4 measured what "expressible" costs.** 29 of the 32
themes are colour-only and import cleanly. **Three do not** — they override
geometry with literal rules on pseudo-elements, and one of them (`ulysses`)
draws a list marker muya does not define at all. D4's schema carries named
fields for every such case found, which means the import path is a
transcription for 32 of 32 files *today*. **The obligation M5 inherits is what
happens on the 33rd**: a theme carrying a drawing primitive the schema has no
field for must **fail loudly at import**, never silently drop the rule. This is
the same failure mode D7 found in `register_fonts` returning an empty `Vec`, and
the same rule applies for the same reason — a subtly wrong result with no
diagnostic is worse than a refusal.

M5 also inherits the **metadata** MarkText never had: its manifest is
`ThemeDescriptor { name: string }`, with display names title-cased at render
time, dark/light membership kept as two frozen arrays in a *different* file, and
window background colours in a fourth hand-maintained map — none of them linked
by any type. D4's struct is where those become fields.

### Owed by M3 to upstream — one small parley patch, and it is already specified

New at S0. M3-R1's residual is a bidi level assigned by `unwrap_or(0)` where an
inline box has no preceding run, sitting under parley's own TODO saying the box
should instead take the level of a U+FFFC standing in for it. E1's harness
already contains the failing case, the expected coordinates, and an independent
`unicode-bidi` oracle that produces them — which is most of a regression test.

§13 R2's mitigation reads *"Linebender is responsive; budget for upstream
contributions."* **This is that budget falling due, and it is the cheapest
version of it the project could have got**: a one-line fix with a ready test,
rather than the feature-scale contribution R2 imagined. M3 carries the
workaround (an RLM before the box) either way, so **this is owed but not
blocking**, and it should not be allowed to become the reason a stage slips.

### Owed to the plan itself — two statements S1 made false

New at S1, and listed here because a stale sentence in a closed document is the
same hazard as a stale doc comment: it is the first thing a reader believes.

- **RUST-REWRITE-PLAN.md §1's `rust-version = "1.85"`** and **`docs/M0.md:289`**
  (*"the floor stays 1.85"*) are both false as of S1. D2's parley pin forces
  1.86 through an under-specified upstream ICU bound, and there is no version of
  this workspace at 1.85 that compiles. The workspace manifest now says 1.86 and
  records the whole chain; neither closed document has been edited, because
  they are the record of what was decided when. **A milestone that raises the
  floor again should add to this list rather than replace it.**
- **§12.2's binary-size levers are now both un-purchased for reasons §12.2 did
  not anticipate.** D1 declined the GPU backend (−4.318 MB) and S1 declined
  `complex-scripts` (−3.6 MiB) — the two largest line items the section ever
  named, one on risk asymmetry and one because the feature turned out to change
  nothing measurable. Whatever replaces that table at S6 should start from the
  measurements, not from the section.
