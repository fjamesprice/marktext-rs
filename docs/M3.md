**Status: OPEN, S0 closed 2026-08-10** — opened 2026-08-08. · **Predecessor:**
[`M2.md`](M2.md), closed the same day on its deliverables with its soak clause
red.

RUST-REWRITE-PLAN.md §9 M3: *"`mt-layout` + `mt-render` + `mt-highlight` —
read-only viewer."* Exit gate: *"**5 MB doc opens ≤ 800 ms. 60 fps scroll.
Bidi, CJK, emoji, ligatures render correctly. CPU fallback works in a VM. Ships
publicly as a standalone fast previewer.**"* Budgeted at 5 months, and §13 R8
makes the public ship a risk mitigation rather than a nice-to-have: it is the
plan's answer to *"25 months with nothing shipped; momentum dies."*

This document is the working plan for that milestone. Where it disagrees with
§§5–7 and §12 of RUST-REWRITE-PLAN.md, the disagreement is called out in §4
rather than applied silently. The plan remains the contract; this is the
reading of it after the crates it names were actually looked up.

**On the tags in §4.** M1 and M2 used **← measured** to mean *this project ran
something and recorded the number*. Most of §4 below cannot earn that tag on
day one, because the claims are about upstream crates rather than about this
port. So M3 uses two tags and does not blur them:

- **← verified upstream** — a page was fetched on 2026-08-08 that states it,
  and the URL is given. This is a fact about someone else's repository.
- **← to measure at S0** — nobody has run it. The number in the plan, if there

### What M2 owes M3, and it is three items

§10 of M2.md has exactly three headings that name M3, and **none names M3
alone** — every one is *"M3/M4"*, which is itself worth noticing, because two
of the three are really M4's and M3's job is mostly to not make them worse.

1. **"Block text has no document offset"** (M2.md:4277). A leaf's `Text` is a
   *reconstruction*, not a slice of the source, so a token's byte range does
   not map to a document offset by addition. Narrowed three times across S2,
   S3 and S6: the container half is discharged (`block::prefix_chain` rebuilds
   a `Prefix` chain from ancestors' ranges), and what remains owed is the
   **per-kind inverse** — an atx heading's rebuild, a code block's post-strip
   columns, a table cell's trim-and-unescape. §10 has said since S2 that there
   is no stage at which that half is free. **M4 is still the first caller**;
   see §4 C6 below for the reason M3 nonetheless discovers a second offset
   space of its own.
2. **"The reparse divergences are a class"** (M2.md:4898), described in M2's
   own text as *"the most important item in §10, and the reason M2 closed on a
   red soak."* `mt_md::reparse::Incremental` has disagreed with a full parse of
   its own source on **every fuzz dispatch it has been given** — five distinct
   mechanisms, four repaired, one open and uncharacterised. The instruction is
   in as many words: **do not build on `mt_md::reparse` without re-establishing
   it first.** §5 D5 takes this decision at open rather than deferring it.
3. **"Carried from M1 §10, unchanged"** (M2.md:5064). Two renderer behaviours
   that sit above `mt-inline`'s marker-reveal predicate and exist nowhere yet:
   `header.ts`'s **synthetic marker range** for an ATX heading's `#`s, and
   `htmlTag.ts`'s override that a **childless tag is always revealed**. Plus
   `autoLinkEncoding.spec.ts`'s renderer half (marktext #3548) — an
   `auto_link`'s `href` must be emitted verbatim, never re-encoded. These are
   the first items in this project that are owed to a *renderer*, and M3 is the
   first milestone that has one. They are still not M3's: all three describe
   caret-dependent or HTML-emitting behaviour, and M3 has neither a caret nor
   an HTML output. **They stay owed, and §10 restates them so the fourth
   milestone in a row does not lose them.**

### The one mitigating fact, recorded because it bounds the exposure

M2 §10 notes that `normalize_source` — the file-open path's BOM-strip and
CRLF/CR → LF pass — removes the lone-`\r` inputs that three of the five reparse
mechanisms need. A viewer that opens files through that path is not exposed to
those three. This bounds the risk; it does not make the incremental path
trustworthy, and D5 does not lean on it.

## 1. Scope

**In:** `mt-layout`, `mt-render`, `mt-highlight`, and the smallest possible
shell that makes them a program someone can run.

**Out, and each has a milestone that owns it:** the caret, selection, all edit
commands, undo, clipboard, IME and the AccessKit tree (M4); preferences,
keybindings, session import, the file tree and search UI (M5); math rendering,
mermaid diagrams, PDF export and spellcheck (M6). HTML → Markdown on paste is
M5's, per M2 §10.

**The tension this milestone has to resolve, and it is a real one.** §9 puts
`mt-fs`, `mt-ui` and `mt-app` at M5, and R8 requires M3 to *ship publicly as a
standalone previewer*. A previewer needs a window, a file to open, and a theme
— three things whose crates belong to a later milestone. Resolving this by
quietly building M5's crates early would be scope creep dressed as a gate.
§5 D6 takes the decision explicitly.

**What "read-only" buys, and it is more than it sounds.** No caret means no
marker reveal, no IME, no accessibility tree, no undo, and no incremental
reparse. Four of M2's ten open findings and both of M1's owed renderer
behaviours are caret-dependent and therefore out of M3's path entirely. This
milestone is the one place in the project where the hardest inherited debt can
be routed around rather than paid — and §4 C6 is the one place it cannot.

## 2. What is being ported — and the answer is *almost nothing*

**This is the structural break with M1 and M2, and every other section depends
on getting it stated correctly.** M1 ported a tokenizer. M2 ported a parser, a
serializer and a state model. Both had a reference implementation to be
byte-identical to, a differential harness to prove it with, and a spec suite to
count against.

**muya has no layout engine to port, because the browser was the layout
engine.** What MarkText does is build DOM and let Chromium do line breaking,
bidi, font fallback, shaping, and paint. M3 replaces Chromium. There is no
`layout.ts` to read.

### The heading scale is not the browser's, and that is the shape of the whole problem

muya defines `h1 = 1.875em`, not the UA default `2em`; `h2 = 1.5em` matches,
`h3 = 1.375em` does not match `1.17em`. Every such value is a decision someone
made in CSS that a Rust layout engine reproduces only by being told. **There is
no algorithm to port and no test that fails if a number is wrong.** §7 is about
what replaces that.

## 3. One geometry, three consumers

`mt-layout`'s own doc comment states the architecture and M3 does not revisit
it: *"Layout is the single source of truth for geometry, shared by screen
rendering, PDF export, hit-testing, and print. One engine, three consumers —
which is why PDF export matches the screen by construction."*

The pipeline M3 builds, with the milestone that owns each arrow:

```text
  source ──parse (M2)──► Document ──┐
                                     ├──► LayoutTree ──► display list ──► pixels
  theme + available width ──────────┘        (M3)            (M3)          (M3)
                                              │
  per leaf: mt-inline::tokenizer (M1) ────────┤ styled runs + InlineBox
  per fence: mt-highlight (M3) ───────────────┘ highlight spans
```

Three things about this diagram are load-bearing and are asserted here so §6's
stages can be checked against them:

- **`mt-layout` consumes `Document`, never markdown.** `mt_md::parse` returns
  `Parsed { document, labels, source_map }`; the viewer holds all three, and
  §4 C6 is about the third.
- **Inline structure is re-derived per leaf, not stored.** A leaf's `Text` is a
  string; `mt_inline::tokenizer` turns it into a token tree with `Span` byte
  offsets *absolute into that leaf's text*. This is M2 C2's premise seen from
  above, and it is the reason `mt-layout`'s "parley is a direct fit" argument
  holds: inline content really is styled runs over one string.
- **`mt-highlight` sees a code block's text and a language, and nothing else.**
  The language is `Block::highlight_language()` — the **first word** of the
  info string, never the whole string, which round-trips verbatim.

## 4. Corrections to the plan

Eight corrections, ordered by how much they change what M3 builds. Six are
verified against upstream sources fetched on 2026-08-08; two are arguments and
say so.

### C1 — "GPU `vello` vs CPU `tiny-skia`, two backends behind one trait" is a false dichotomy **← verified upstream**

§6's table, §12.2's lever, §13 R7, and `mt-render`'s own doc comment all rest
on the premise that the CPU fallback must come from a different project with a
different imaging model. **It no longer does.** The Vello project ships its own
CPU renderer:

| Crate | Version | Published | What it is |
|---|---|---|---|
| `vello` | 0.9.0 | 2026-05-15 | GPU compute renderer on `wgpu` |
| **`vello_cpu`** | **0.2.0** | **2026-08-07** | CPU renderer, SIMD and multithreaded |
| `vello_hybrid` | 0.2.0 | 2026-08-07 | CPU tiling + GPU fine rasterization |
| `vello_common` | 0.2.0 | 2026-08-07 | Shared foundation for both |

Versions and dates confirmed directly against `crates.io/api/v1/crates/*` on
2026-08-08. The Sparse Strips v0.2.0 release notes call Vello CPU *"broadly
usable, with a reasonably complete imaging model and competitive
performance"*, with **no API stability guarantee**; Vello Hybrid is *"in its
early stages"*. Vello's own README still says the project *"can currently be
considered in an alpha state"* and lists **glyph caching** among its unfinished
work.

**What changes.** The trait in §6 survives; the table under it does not. The
strongest question at S0 is no longer *"GPU or CPU?"* but **"can `vello_cpu`
alone hit 60 fps scroll on the 5 MB corpus?"** If it can, M3 ships one backend,
drops `wgpu` entirely, and §12.2's headline size lever costs zero engineering.
That is a materially different milestone, and it is decided by measurement at
S0 rather than argued here.

**S0's answer, and the question S0 turned out to be unable to ask ← measured.**
The size half is settled: a `vello_cpu` + parley binary is **2,481,664 B** and
adding `vello`/`wgpu` costs **+4,317,696 B — the GPU backend is 2.7× the size
of the entire rest of the program** (`spikes/results/e2-binary-size.md`).

The scroll half is not, and the reason is structural rather than a stage that
ran short. **60 fps scroll cannot be measured before `mt-render` exists, and
`mt-render` is S4.** §6 asked S0 to take D1 from a measurement whose instrument
S0 does not build — an ordering defect in this document, not in the work. D1 is
therefore taken on the evidence that *does* exist and carries an explicit
revisit point; see §5 D1. The honest statement is that the trait stops being
insurance and starts being the thing that makes a late answer affordable.

### C2 — `tiny-skia` cannot draw text at all **← verified upstream**

`tiny-skia` 0.12.0 (2026-02-02, after a ~2-year gap since 0.11.4; the
repository has moved to `github.com/linebender/tiny-skia`). Its README lists
**text rendering under "out of scope"** — *"Text rendering (maybe someday)"* —
along with resource caching, and describes itself as *"not a Skia replacement
and never will be. It's more of a research project."* Its own performance note:
20–100 % slower than Skia on x86-64, 100–300 % on ARM.

The plan treats `tiny-skia` as the cheap option. **On text it is the expensive
one**: choosing it means building outline extraction, rasterization, an atlas,
subpixel positioning and the blend path by hand — precisely the work
`vello_cpu`'s default-on `text` feature already does. `tiny-skia` should be
demoted from *"the CPU backend"* to *"a possible last-resort raster target"*,
and it survives only if S0 says `vello_cpu` cannot.

**Now priced ← measured.** `tiny-skia` adds **+390,144 B** over the `vello_cpu`
baseline — genuinely cheap, and irrelevant, because the 390 KB buys paths and
rects and no glyphs. The demotion stands and the cheapness is the trap: a
backend that is 11× smaller than the GPU one and cannot render a single
character of a text editor's content is not a fallback, and §12.2's lever
sentence ("ship `tiny-skia` only") describes a program that cannot exist.

### C3 — `swash` is not in this stack any more **← verified upstream**

§6 says *"glyph rasterization via `swash`, cached in an atlas keyed by (font,
size, subpixel offset, glyph)"*, and §12.2 bills `parley + swash + fontique +
rustybuzz + ICU segmentation` at 2–3 MB. **Two of those four crates are not in
the graph.** Parley shapes with **HarfRust**, reads fonts with **skrifa**, and
analyses text with **icu4x** (`icu_properties`, `icu_segmenter`,
`icu_normalizer`); neither `swash` nor `rustybuzz` appears in `parley` or
`parley_engine`'s `Cargo.toml`. `swash` itself is alive (0.2.10, 2026-07-17),
so the plan's sentence would still *work* — it would just put a second
font-parsing stack in the binary alongside skrifa.

And the atlas idea fights the renderer: vello and `vello_cpu` draw glyphs as
**vector outlines** through skrifa, not by consuming an externally rasterized
atlas, and vello's README lists glyph caching as work it is doing itself.
**§6's swash atlas should be struck** unless S0 resurrects `tiny-skia`.

### C4 — R2's two "awkward parley cases" are not equal risks, and only one is a research risk **← verified upstream**

§13 R2 names two cases and asks for both in *week 1*. They are in completely
different states.

**Case 1 — inline-widget baseline alignment: solved, but not in a release.**
`linebender/parley` PR **#639** ("Implement `baseline` field on inline boxes")
**merged 2026-07-08**, adding `baseline: Option<f32>` to `InlineBox` and
`PositionedInlineBox` plus `Layout::first_baseline()` / `last_baseline()`.
Parley **0.11.0 published 2026-06-26** — *before* that merge. So the feature R2
calls a week-1 risk exists **only on `main`**. This is a dependency-pinning
decision (D2), not a research problem. Full CSS `vertical-align` remains open
(#291, #325), and tracking issue #208 shows `vertical-align` unchecked with
`[x] Baseline alignment for inline boxes (#639)` and `[ ] Subscript and
superscript` under it — which matters, because MarkText has a
`super_sub_script` option and 26 `TokenKind` variants include
`super_sub_script`.

**Case 2 — nested bidi interacting with inline boxes: not solved, and not
tracked as one thing.** No dedicated issue exists. What exists is a cluster of
open gaps: #208 leaves *"BiDi-direction overrides"*, *"Root-level default BiDi
direction"*, *"Span-level overrides"*, *"Margin/border/padding for inline spans
(should be bidi-aware)"* and *"Bounding boxes for inline spans"* all unchecked;
**#49** (open since 2024-04-29) considers replacing parley's own bidi
implementation with `unicode-bidi`; **#118** (open) reports bidi cursor motion
differing between `Left` and `Ctrl+Left`. The primitives are done — inline
boxes and hit-testing for inline spans are both ticked — but **nobody upstream
has ticked a box that says "an inline box inside an RTL run inside an LTR
paragraph places correctly."**

**R2's mitigation is validated and its ordering is wrong.** #639 is literally
an outside contribution landing the feature the plan feared, which is evidence
for *"Linebender is responsive; budget for upstream contributions."* But case 1
costs a version pin and case 2 is the genuine unknown. **S0's first test matrix
is case 2**, and `bench/corpus/rtl.md` (1,103 bytes, Arabic + Hebrew, mixed
script) plus an inline image is the input that exercises it.

#### What S0 measured, and the paragraph above is wrong about the thing it was most confident of **← measured**

**Case 2 works. On both versions.** `spikes/results/e1-bidi-inline-box.md`
answers M3-R1 **yes** for parley 0.11.0 and for `main` @ `a0752c7b`: an inline
box inside an RTL run inside an LTR paragraph is placed at the byte offset's
**resolved bidi level**, not where a left-to-right sweep of logical bytes would
put it. Both versions split the shaped run at the box's byte index and reorder
the halves with the rest of the line.

The deciding numbers, from an LTR paragraph with the box six bytes into the
Arabic word `مرحبا`: the box lands at **x = 231.96**, with logical bytes 32..51
on its *left* and bytes 26..32 on its *right*. That inversion is the RTL run's
visual order. A logical sweep would have placed it at x ≈ 254.56 — it is 22.6 px
to the left of that, in the correct slot. The harness does not grade parley
against parley: expected visual order is computed independently by
**`unicode-bidi` 0.3.18** with U+FFFC standing in for the box, and parley's
visual neighbours match it character-for-character in all six nested cases,
including level-2 LTR islands inside RTL paragraphs.

**One case fails, identically on both versions, and it is narrow.** An inline
box at **byte 0 of an RTL paragraph** — an image as the first thing in an Arabic
or Hebrew paragraph — is placed at the far left when it belongs at the far
right: x = 0.00..40.00 on a 437 px line where it should occupy 397.00..437.00.
Worse, a box at the *end* of the same paragraph lands at the same coordinates
and is correct there, so leading and trailing boxes are indistinguishable in
the output. The cause is upstream and acknowledged upstream — a box inherits the
preceding run's bidi level, which is right whenever it splits a run and wrong
when there is no preceding run, where the fallback is a hard-coded level 0:

```rust
// parley main, shape/mod.rs — the TODO is upstream's own
// TODO: this lets the inline box take the bidi level of the previous run, but in principle
// inline boxes should be included in bidi analysis as an object replacement character
// (U+FFFC). The box should then take the bidi level of that character.
let prev_bidi_level = if shaped_run_idx > 0 { … } else { BidiLevel::new(0) };
```

`unwrap_or(0)` is the whole bug. **11 of 12 cases pass on each arm.**

**What this does to the risk register.** M3-R1 was written as *"genuinely
unsolved upstream"* and *"not a month-5 discovery."* It was a month-*zero*
discovery, and what it discovered is that the fear was misassigned: the
research risk is a one-line upstream defect with a documented workaround
(an RLM before the box), not an architectural gap. §8 is updated accordingly.
This is also the second time in two milestones that the thing the plan was
most confident about turned out to be the thing that was wrong — M2 §4 C3 was
the first — and the pattern is worth naming rather than enjoying.

**Two upstream facts this turned up that the section above gets wrong.**
#208's *"Root-level default BiDi direction"* is **ticked on `main`** —
`set_base_direction`, PR #708 — and absent from 0.11.0. So case 1 is not the
only unreleased feature M3 needs; there are two, and D2 now turns on both.
And an unlisted silent fix: **0.11.0 breaks Arabic cursive joining at an inline
box** (one glyph changes form, +0.53 px) where `main` does not — a *correctness*
regression in the released version, on the exact construct this milestone's gate
names.

### C5 — §5's incrementality contract is on the wrong axis **← verified upstream**

§5 says *"re-wrapping the whole document happens only on width change — and
even then only for visible blocks plus a viewport margin."* Parley's own crate
documentation says the opposite about which operation is expensive:

> `Layout` supports re-linebreaking and re-aligning many times (in case the
> width at which wrapping should occur changes), **but if the text content or
> the styles applied to that content change then a new `Layout` must be
> created**.

So **a width change is the cheap case** — `break_all_lines(Some(w))` then
`align(…)` on the existing `Layout`, no re-shaping — and **a content change is
a full rebuild** of that block's `Layout`. There is no API to patch a `Layout`
in place, no partial re-shape, no reshape-from-byte-N. The plan's block-granular
dirty model is therefore the *only* available granularity, which is fine
because §0's premise already made blocks the unit — but the caching design
follows the real axis, not the assumed one.

Two supporting facts. `LayoutContext` is documented as *"designed to be a
global resource with only one per-application (or per-thread)"*, so the reuse
it offers is **allocator-level, not shaped-run-level**: rebuilding avoids
malloc traffic, not shaping work. And parley 0.7.0 fixed a bug where laying out
large paragraphs was **non-linear** in length — which is a reason to distrust
any recalled benchmark from before that release.

**Both confirmed ← measured.** Over `5mb.md`, re-breaking every existing
`Layout` at a new width costs **54 ms** against **810 ms** to rebuild them —
a **15.1× ratio** at 800 → 750 px, and **14.8×** at 800 → 1600 px, so the large
jump hides nothing. The documentation's axis is the real axis.

Two consequences the correction did not go far enough on. First, at 54 ms for
the *whole* 5 MB document, **§5's "only for visible blocks plus a viewport
margin" caution is unnecessary for width changes specifically** — a window
resize can re-break everything and stay inside a frame budget's neighbourhood.
Laziness is needed for the *first* layout (D9), not for reflow. Second, the
non-linearity is gone: ns/byte *falls* from 367 to 148 across the corpus's size
range and throughput is flat at 6.5–6.7 MB/s from 250 KB to 5 MB. **The enemy
is block count × a fixed per-`Layout` cost, not document size** — which is
exactly what makes §5's `Code { lines: Vec<Layout> }` sketch the wrong shape
(D9).

### C6 — a read-only viewer lays out a string that is not the block's text, and that is a *third* offset space

**← argument, and the one correction here that is about this port rather than about upstream**

MarkText is WYSIWYG: markdown markers are hidden unless the caret is near them.
`mt-inline::marker` implements exactly that, and its predicate is a pure
function of `(token.range, cursor)` with **no ancestor/descendant propagation
in either direction** — measured against the running engine at M1, which found
§3.1's sketch wrong in two of its three clauses. A read-only viewer has no
caret, so `cursor: None` and **every marker is hidden**.

The consequence the plan does not contain: **the string `mt-layout` hands to
parley is not `Block::text`.** `**bold**` occupies 8 bytes of block text and 4
columns of visible text. So the offset spaces stack three deep:

```text
  source offset  ──(M2's SourceMap, per node; is_exact says which are tight)──►
  block-text offset  ──(M3 must build this)──►  visible-text offset
                                                 └─► parley cluster ──► pixel
```

M2 §10 owes the **first** arrow's inverse to M4, narrowed three times and still
not free. M3 discovers the **second**, and the second is M3's own: nothing can
place a search highlight, a click, or a link hit-region without it. The good
news is that it is cheap where M2's is not — `mt-inline`'s tokens carry both
`range` and `raw` as absolute byte spans into the leaf's text, so the map falls
out of the same walk that builds the style runs, rather than needing a per-kind
inverse. **This is an M3 deliverable and §10 will carry it forward for M4's
caret.**

Related, and recorded so it is not rediscovered: `tokens_to_plain_text` already
performs this stripping, but it is *non-bijective* and exists for
table-of-contents text and HTML anchor slugs. It is the right shape and the
wrong contract — M3 needs the mapping, not just the string.

### C7 — the plan has no theme model, and themes carry geometry **← verified in the reference**

§5 says layout consumes *"a `Document` + theme"* and never says what a theme
is. In MarkText a theme is CSS, and the numbers are not all colours:

- **33 selectable themes**; 32 CSS files on disk plus `light`, which is the
  no-op default. Each file is ~214 lines (dark 220, ulysses 252, graphite 254,
  one-dark 350, material-dark 189).
- **All 32 non-`light` themes override `--editorAreaWidth` from muya's 800px
  default to 750px.** Content column width is a theme property.
- At least four themes (`graphite`, `dark`, `one-dark`, `ulysses`) hard-code
  **non-variable** geometry — task-checkbox size, position and rotation, and
  thematic-break styling — replacing `blockSyntax.css`'s own rules outright.
- A user-facing **editor-width setting** injects
  `--editorAreaWidth: calc(100px + <value>)` where `<value>` is a free-text
  `ch`/`px`/`%` string; the `+100px` is the container's `0 50px` padding.
- **There is no theme schema.** The contract is implicit in which
  `var(--x, fallback)` names the base stylesheets read. `theme.md` is a
  three-line placeholder for the picker UI.
- Themes reach muya by a build-time `?inline` import concatenated into one
  `<style id="theme-style">` element, and each ships a **paired Prism theme**
  (31 files, `material-dark` reusing `dark`'s).

**M3 cannot consume CSS**, so D4 has to decide what a theme is in Rust and what
the 32 files become. The honest framing: this is a *data-modelling* decision
with 11,001 lines of prior art, not a styling detail.

### C8 — muya does not virtualize, so M3's performance gate is not a parity gate **← verified in the reference**

`ScrollPage.create()` (`block/scrollPage/index.ts:51-63`) maps over the entire
state array and appends **every top-level block** to real DOM at once;
`updateState()` empties and re-appends all of them. The entry point
(`editor/index.ts:282`) calls it once with the complete document. There is no
`IntersectionObserver`, no visible-range concept, no scroll check anywhere in
`block/` or `editor/` — the name `scrollPage` refers to the scrollable
container element, not to a virtualization scheme. MarkText renders the whole
document and relies on the browser's paint culling.

Two consequences, and the second is uncomfortable:

- **If `mt-layout` lazily lays out only visible blocks, that is a new
  capability, not parity.** The plan is right that it is where the 5 MB target
  is won; it should not be described as matching what MarkText does.
- **There is no baseline to compare against.** `bench/corpus/README.md` already
  flags that a `BASELINE.md` capturing real Electron numbers was deliberately
  deferred (it needs a full `pnpm install` and build of the clone). So *"5 MB
  opens ≤ 800 ms"* is an **absolute** target with no reference measurement, on
  unspecified hardware. §8 carries this as a risk, and S0 owes the baseline.

**The baseline now exists, and it retires this bullet ← measured.**
`bench/BASELINE.md` was built at S0 from a **packaged** MarkText — an
`electron-vite build` + `electron-builder --win --x64` artifact at commit
`e52106fd`, run as `dist/win-unpacked/marktext.exe`, not a dev server. On the
same machine every Rust number in this document was taken:

| §12.1 metric | Electron, measured | Target |
|---|---:|---:|
| Cold start → editable caret | **818 ms** (n=8, 809–829) | ≤ 250 ms |
| Warm start | **788 ms** (n=5) | ≤ 120 ms |
| RSS, empty document | **485 MB** (n=3) | ≤ 60 MB |
| RSS, 1 MB document | **920 MB** (n=3) | ≤ 120 MB |
| **Open 5 MB document** | **did not finish — > 150 s, and a second run abandoned at ≈ 5 min** | ≤ 800 ms |
| Keystroke → glyph, p99 | *unmeasured* — no reliable path to real paint timestamps | ≤ 8 ms |
| Idle CPU, focused | **0.04 %** | ~0 % |

The RSS figures sum the whole Electron process tree — main, renderer, GPU,
utility — because a main-process-only number would flatter Electron by an order
of magnitude.

**C8's framing needs strengthening rather than softening.** The correction said
lazy layout is *"a new capability, not parity."* That is now an understatement:
`1mb.md` takes **43.3 s** to open and `5mb.md` never becomes interactive at all,
while staying `Responding = True` and burning CPU — so scaling is superlinear
and the failure is a hang, not a slow load. **The 800 ms gate is not a target
MarkText misses; it is a capability MarkText does not have.** Six of seven §12.1
rows are missed, several by an order of magnitude, and idle CPU is the only row
Electron already passes.

That cuts both ways and the second way is the uncomfortable one: **it removes
"but Electron is slower" as an available defence for the Rust side**, because on
the row that matters most there is no Electron number to be faster than. §6 S6
still has to hit 800 ms on its own terms.

### C9 — three smaller items that would each cost a stage if found late **← verified upstream**

- **`Brush` is parley's own trait**, with a blanket impl for
  `Clone + PartialEq + Default + Debug` and a default type parameter of
  `[u8; 4]`. It is **not** `peniko::Brush` — parley demoted peniko to a
  dev-dependency, replaced `peniko::Font` with
  `linebender_resource_handle::FontData`, and replaced `kurbo::Rect` with its
  own `parley::BoundingBox`. `mt-layout` defines its own brush type, and the
  peniko/kurbo boundary now sits at the `mt-layout` → `mt-render` seam rather
  than inside `mt-layout` — which is what the crate's "no GPU" rule wanted
  anyway.
- **Parley 0.10.0 added a `complex-scripts` feature** for dictionary-based line
  breaking in CJK, Thai, Khmer, Lao and Myanmar. M3's gate says *"CJK renders
  correctly"* and `bench/corpus/cjk.md` includes a long unspaced line for
  UAX #14. The feature is almost certainly required and the plan does not
  mention it.
- **Parley's default feature set is `["system"]`**, which enables system font
  backends — i.e. filesystem enumeration. `mt-layout`'s own doc comment
  commits to **"No I/O"**, and `cargo xtask deps` greps its `src/` for
  `std::fs::` (a deliberately crude check that would *not* catch I/O inside a
  dependency). D7 has to take this explicitly rather than let a default feature
  decide it.

Also worth knowing before pinning: parley's unreleased section **removes
`Glyph::style_index`**, changes `Cluster` to span a full grapheme cluster (a
semantic change to the exact API §5 hit-tests through), and changes line sizing
for mixed inline content. 0.8.0 moved `Glyph::y` from Y-up to **Y-down**.

**All three measured at S0, and the churn was overstated ← measured.**

- **"No I/O" is achievable and cheap.** parley builds and lays out with
  `default-features = false` (plus `std`), which drops the dependency count
  from **61 → 49** crates on 0.11.0 and 62 → 50 on `main`. Fonts register from
  in-memory bytes through
  `Collection::new(CollectionOptions { shared: false, system_fonts: false })`
  followed by `register_fonts(Blob<u8>, None)`. No filesystem enumeration
  anywhere. D7's third option — the one D7 called "the one to beat" — is not
  merely honest, it is the *default* once the feature is off.
- **`complex-scripts` costs nothing in crates and a great deal in bytes.** It
  exists in 0.10, 0.11 and `main`, pulls **0 extra dependencies**, and adds
  **+3.6 MiB** to the binary — dictionary data, and by a wide margin the
  largest single feature-flag cost measured anywhere at S0. C9 called it
  "almost certainly required" for the gate's CJK clause and did not price it.
  It is now the second-largest line item in M3's binary after the GPU backend,
  and it is a flag rather than an architecture, so §12.2 has to carry it.
- **Porting 0.11.0 → `main` cost 2 lines.** Adding `baseline: None` to two
  `InlineBox` literals, and nothing else. `Glyph::style_index` and the `Cluster`
  grapheme change **were not hit at all**. What *was* hit is the one the plan
  did not emphasise: **#697's line sizing** changed every case — line height
  24.00 → 28.40, baseline 22.00 → 24.00, box y −2.00 → 0.00. So the churn risk
  is real but sits in *geometry*, which goldens catch loudly, rather than in
  *API*, which the plan feared and which cost two lines.

### C10 — §12.2's binary-size table has no provenance **← to measure at S0**

The plan's headline lever is *"drop `wgpu`/`vello`, ship `tiny-skia` only:
−4–6 MB."* **The 4–6 MB figure could not be sourced.** The only public
datapoint found was a small wgpu program at 8.4 MB total with wgpu itself at
~857 KiB per `cargo bloat` — one anecdote, an old wgpu, counting Rust code
only. Vello's docs note that unused pipelines can be disabled to reduce size,
so the shader payload is a knob rather than a fixed cost.

The second lever — *"load tree-sitter grammars on demand: −3–4 MB"* — **is not
a feature flag.** Grammar crates ship generated C compiled by `build.rs` and
**linked statically**; on-demand loading means shipping and `dlopen`-ing
platform dynamic libraries, or embedding a wasm engine. That is a subsystem
with packaging, code-signing and platform-matrix consequences.
`tree-sitter-rust` 0.24.2's published crate is ~360 KB of *compressed source*;
compiled parse-table size is a different and larger number. §12.2's "~4 MB for
core + ~20 grammars" is plausible, unverified, and possibly low.

**S0 replaces the table rather than arguing with it**: four `dist`-profile
builds (`vello_cpu` only · `+ vello`/`wgpu` · `+ tiny-skia` · `+ N grammars`),
`cargo bloat --crates -n 40` on each, deltas recorded. Note the first build may
not have existed when §12.2 was written.

#### The four builds **← measured**

Under the `dist` profile copied verbatim from the root manifest — `lto = "fat"`,
`codegen-units = 1`, `panic = "abort"`, `strip = "symbols"`, `opt-level = "s"`.
Sizes are the stripped artifact; per-crate attribution came from an unstripped
twin profile, because `cargo bloat` cannot attribute what `strip` removed.

| # | Build | Stripped `dist` | Δ over floor | Δ over build 1 |
|---|---|---:|---:|---:|
| 0 | floor (`fn main() {}`) | **98,304 B** | — | — |
| 1 | `vello_cpu` + parley | **2,481,664 B** | +2,383,360 B | — |
| 2 | + `vello`/`wgpu` | **6,799,360 B** | +6,701,056 B | **+4,317,696 B** |
| 3 | + `tiny-skia` | **2,871,808 B** | +2,773,504 B | +390,144 B |
| 4a | + tree-sitter core + **1** grammar | **3,661,312 B** | +3,563,008 B | +1,179,648 B |
| 4b | + tree-sitter core + **20** grammars | **28,388,864 B** | +28,290,560 B | **+25,907,200 B** |

**Lever 1 survives in magnitude and dies in mechanism.** §12.2 claims −4–6 MB
for dropping `wgpu`/`vello`; measured **−4.318 MB**, inside the range at its low
edge. But the plan's stated mechanism — *"ship `tiny-skia` only"* — describes a
program that cannot render text (C2), so the lever is really *"ship `vello_cpu`
only"*, which the plan did not know was an option.

**Lever 2 is understated by 6–8×, and this is the largest single finding of
S0.** §12.2 claims −3–4 MB for on-demand grammars. The measured cost of
bundling 20 is **25.907 MB**, at **~1.301 MB marginal per grammar**. §12.2's
whole *"~17–25 MB default total"* is smaller than one plausible grammar set.

**C10's static-linkage argument is confirmed by reading the code**, not
inferred: `tree-sitter-rust`'s `build.rs` compiles a checked-in **6.5 MB
`parser.c`** through the `cc` crate into a static library. There is no flag that
makes it lazy; "on demand" means dynamic libraries or a wasm engine, exactly as
C10 argued. A C toolchain is required — MSVC was already present here, so this
stage cannot speak to the cost of provisioning one from zero, only to the fact
that one is mandatory.

**A methodological warning for anyone who re-runs this.** `cargo bloat --crates`
**massively under-reports tree-sitter**, because parse tables are `.rdata`
(data) and `cargo bloat` attributes `.text` (code). Per-grammar cost is only
recoverable from whole-binary deltas. A future stage that trusts `cargo bloat`
alone here will conclude grammars are nearly free and be wrong by an order of
magnitude.

### C11 — `mt-highlight`'s stated rationale does not apply at M3 **← argument**

The stub's doc comment says tree-sitter was *"chosen over `syntect` for its
incremental behaviour: an edit inside a fence re-parses the edited region, not
the fence."* **M3 is a read-only previewer. There are no edits inside a fence.**
The benefit is M4's; the costs — static C linkage per grammar, a C toolchain on
every platform, build time, binary size against a 250 ms cold-start budget —
are paid at M3. Meanwhile MarkText's parity baseline is **Prism 1.30 with 298
lazily-loaded grammars**, of which only `latex` and `yaml` are eager, and
highlighting is **synchronous and per-code-block**, falling back to plain
escaped text until a language's dynamic import resolves.

D3 re-opens the choice with three candidates and no winner picked here.
Sourced numbers to decide against, all upstream-verified: `syntect` 5.3.0 loads
its whole binary syntax dump in **~23 ms** with lazy regex compilation, but
highlights 9,200 lines of jQuery in **600 ms** and reaches 50,000 lines/s on
simple syntaxes; its default `regex-onig` feature pulls a C library, while the
pure-Rust `regex-fancy` alternative is *"about half the speed"*; its output is
`Vec<(Style, &str)>`, so `mt-highlight`'s byte-range contract needs an adapter.
`tree-sitter` 0.26.12 (published 2026-08-08) emits
`HighlightStart / Source { start, end } / HighlightEnd` — byte ranges, a direct
fit for the contract. A Prism port is regex-driven and grammar-as-data, so
lazy loading is trivial and binary cost is near zero, at the price of
translating 298 JS grammars' regexes (lookbehind and backreferences need
`fancy-regex`) and owning them as they drift.

#### Four things in the paragraphs above are wrong, and one of them is the load-bearing one **← measured**

`spikes/results/e4-highlight.md` measured all three engines. The costs C11
charges against tree-sitter hold and get worse; the costs it charges against
`syntect` and the Prism port were partly invented.

- **`syntect` needs no adapter.** C11 says its output is `Vec<(Style, &str)>`
  so *"`mt-highlight`'s byte-range contract needs an adapter."* That is true
  only of the `easy::HighlightLines` convenience wrapper. `syntect`'s public
  **`RangedHighlightIterator` already yields `(Style, &str, Range<usize>)`** —
  byte ranges, the contract, no adapter, no cost. A whole objection evaporates.
- **The regex claim names the wrong construct.** C11 says *"lookbehind and
  backreferences need `fancy-regex`."* Native lookbehind appears in **zero of
  the 298 grammar files** — Prism's `lookbehind: true` is a different,
  non-regex mechanism that trims a captured prefix, and C11 conflated the two.
  What actually forces `fancy-regex` is **lookahead**, which C11 does not
  mention and which drives **~73 %** of the files. The conclusion survives
  (`fancy-regex` is needed, and it is already a dependency of `mt-inline`) but
  the reasoning behind it was wrong, which matters because the port's difficulty
  was being estimated from it.
- **It is 297 languages, not 298.** The 298th key is `meta`, which is not a
  language. Every "298" in this document should be read as 297, including §6
  S3's gate and D3's coverage axis.
- **The Prism wiring reference is 405 lines across four files**, not the 397
  in one that §2's table implies.

**And the measured axes point in different directions, which is why D3 is a
decision and not a lookup.** Cold start to first highlight: `syntect` **≈2.5 ms**
(0.77 ms setup + 1.75 ms first fence) against tree-sitter's **15.3 ms** for one
lazily-built grammar and **80.9 ms** for fourteen eager ones — query compilation
is the whole cost, and 80.9 ms is a third of the 250 ms cold-start budget spent
before a glyph is drawn. Steady-state throughput reverses it: tree-sitter
**41,060–41,394 lines/s** against `syntect`'s **24,344–24,815**, ~1.65× faster.
Coverage over the corpus's own 16 languages is a tie at **42/51 blocks (82.4 %)
each — but they miss different things**: `syntect` has no TypeScript and no TOML
in its default 75-syntax bundle; tree-sitter has no SQL and no diff. Across the
full Prism set `syntect` covers a measured **44 of 297**.

## 5. Decisions to make before writing code

M2's D-list was taken before its first stage and revisited when a stage proved
one wrong. Same discipline. Two are taken at open because scope forces them;
the rest name the stage that must take them, and **S0 exists to take most of
them with numbers rather than arguments**.

### D1 — the renderer set: `vello_cpu` alone, GPU deferred behind the trait **← taken at S0, and taken on incomplete evidence, which is stated rather than hidden**

Options were: `vello_cpu` alone · `vello_cpu` + `vello`/`wgpu` behind the trait ·
the plan's original `vello` + `tiny-skia`.

**Decision: M3 ships `vello_cpu` alone. The §6 trait is built anyway. `wgpu`
does not enter the dependency graph at M3, and `tiny-skia` is struck entirely.**

The numbers it rests on:

| | |
|---|---:|
| `vello_cpu` + parley, `dist`, stripped | **2,481,664 B** |
| cost of adding `vello`/`wgpu` | **+4,317,696 B** — 2.7× the rest of the binary |
| cost of adding `tiny-skia` | +390,144 B, and it renders **no text at all** (C2) |

**The measurement D1 was supposed to turn on was not taken, and could not be.**
§6 asks S0 whether `vello_cpu` hits 60 fps scroll on `5mb.md`. Scroll frame rate
requires `mt-render`, which S4 builds; S0 writes no product code by its own
definition. This is an ordering defect in §6 rather than a stage that ran out of
time, and C1 records it.

So the decision is taken on **cost and risk asymmetry instead of on frame rate**,
and the asymmetry is lopsided. Adding a GPU backend later costs one stage behind
a trait that exists from S4. Carrying `wgpu` from S1 costs 4.3 MB, a second code
path through every pixel golden, `naga`, a shader payload, and the VM-fallback
matrix (R7) for the whole milestone — all to hedge a number nobody has. And the
competitive bar set at S0 is not demanding: the incumbent takes **818 ms** to
show a caret and **never opens `5mb.md` at all**.

**The revisit point is explicit, so this cannot quietly become permanent.**
**S4 measures scroll frame rate on `5mb.md` with `vello_cpu` as its first act.**
If it misses 60 fps, D1 reopens with the number it should have had, the trait
absorbs `vello`/`wgpu`, and §12.2's lever is re-priced. **S4 may not report a
backend as chosen without that number.**

### D2 — parley: track `main`, pinned to one revision **← taken at S0**

C4 case 1's feature (`InlineBox::baseline`) is merged but unreleased, and the
unreleased section also carries breaking changes to `Cluster` — the exact API
hit-testing goes through. Pinning 0.11.0 means no baseline alignment for inline
images and math; tracking git means absorbing semantic churn mid-milestone.

**Decision: track `main`, pinned at rev `a0752c7bdc3ad88dac19fc194d2b8e57e59bea2e`
(2026-08-10). Move the pin deliberately, never by `cargo update`. Re-evaluate
when 0.12.0 ships.**

**This is a correctness-over-performance trade and it costs real performance**,
which is the part neither experiment would have shown alone:

| | 0.11.0 | `main` @ `a0752c7b` |
|---|---:|---:|
| eager layout, `5mb.md` | baseline | **+13.9 % slower** |
| peak RSS | baseline | **+40 %** |
| `break_all_lines` alone | baseline | **+74 %** (points at #697) |
| binary size | baseline | +512 B |
| port cost from 0.11.0 | — | **2 lines** |

Against that, `main` carries **three** things M3's own exit gate requires and
0.11.0 does not have:

1. **`InlineBox::baseline`** (#639) — verified working: `y + baseline` equals the
   line baseline for `Some(24.0)`, `Some(12.0)` and `Some(0.0)`, and
   `first_baseline()` returns sane values. Absent in 0.11.0. Inline images and
   inline math have no baseline to align to without it.
2. **`set_base_direction`** (#708) — root-level default bidi direction, which C4
   discovered is ticked upstream and shipped only on `main`. A document whose
   base direction is RTL cannot be laid out correctly without it.
3. **0.11.0 breaks Arabic cursive joining across an inline box** and `main` does
   not. This one is decisive on its own: the gate says *"Bidi, CJK, emoji,
   ligatures render correctly"*, and the released version renders Arabic
   incorrectly on exactly the construct M3-R1 is about.

The performance gap is recoverable by means M3 is building anyway — laziness is
now load-bearing (D9) and parallel layout returns 2.37×. **A correctness defect
in shaped Arabic is not recoverable at all.** Pinning 0.11.0 would trade a gate
clause for 13.9 %.

**The pin's standing risk**, recorded so a later stage does not rediscover it:
the churn that actually landed was *geometric* (#697 moved line height 24.00 →
28.40 and baseline 22.00 → 24.00), not API. Moving the pin will therefore
invalidate layout goldens rather than fail to compile — **a pin move is a
reviewable event on the same footing as a golden update** (M3-R6).

### D3 — `mt-highlight` ports Prism's grammars. **The M0 decision is overturned** **← taken at S0**

`syntect` · `tree-sitter` · a Prism-grammar port. See C11. The M0 choice was
tree-sitter for a reason that does not apply until M4.

**Decision: port Prism's grammars as data. `tree-sitter` is dropped from M3 and
does not enter the dependency graph. `syntect` is retained as a named fallback
with a measured trigger, below.**

| Axis | `syntect` 5.3.0 | `tree-sitter` 0.26.12 | Prism port |
|---|---:|---:|---:|
| Time to first highlight | **2.5 ms** | 15.3 ms (1 grammar) → 80.9 ms (14 eager) | ~0 (grammars are data, lazily loaded) |
| Steady-state throughput | 24.3k lines/s | **41.1k lines/s** | **unmeasured** |
| Binary delta | +999,936 B | **+1,179,648 B for one grammar; +25,907,200 B for twenty** | est. **< 1.5 MB for all 297** |
| Coverage of Prism's 297 | **44** | 35–50 % (estimate, unverified) | **297 by construction** |
| Byte-range contract | direct (`RangedHighlightIterator`) | direct | direct |
| Differential against Prism | weak | weak | **near-exact** |

**Three axes decide it and they are not close.**

**Coverage.** D3's own text says *"language coverage is what users notice."*
`syntect`'s default bundle has **no TypeScript and no TOML**. Shipping a
markdown editor in 2026 that cannot highlight a `ts` fence is a defect users
hit on day one. tree-sitter can reach parity only by linking grammars at
**1.301 MB each** — parity with Prism would be roughly **386 MB**, and even a
40-language subset is +52 MB against a plan whose *entire* budget was 17–25 MB.

**Binary size.** Prism grammars are data, so lazy loading is free rather than
being the dynamic-library subsystem C10 correctly identifies for tree-sitter.
This is the same lever §12.2 wanted, obtained by construction instead of by
engineering.

**Differential testability, which the plan under-weights and which S0 promotes
to decisive.** §7 states plainly that for the first time in this project
*"does it match MarkText?" cannot be answered by running MarkText* — and that
§6 S3's Prism differential is **the one real differential M3 has left**, the
single place M1 and M2's strongest instrument survives. A port restates Prism's
own rules, so span boundaries can be compared for **exact equality** through the
existing Node harness. `syntect` and tree-sitter use genuinely different
tokenizations and will disagree with Prism constantly while both are "right",
which does not weaken S3's gate so much as delete it. **Choosing either would
mean M3 ships with no differential test at all.**

**What this decision is buying on credit, stated plainly.** Prism's steady-state
throughput in Rust is **unmeasured** — no port exists to measure — and the known
risk is real: ~73 % of grammars need `fancy-regex` for lookahead (C11), and
`syntect`'s own documentation puts its `regex-fancy` backend at *"about half the
speed"* of `regex-onig`. **S3 measures it, and the fallback trigger is named
now so it cannot be argued about later: if the ported engine highlights a
visible fence in more than 16 ms (one frame at 60 fps), `syntect` takes the
top-40 languages and the port continues behind it.**

**Scope, because 297 grammars sounds like a milestone of its own and is not.**
MarkText lazily loads all 297 and eagerly loads **two**. The port is therefore a
ratchet, not a big bang: implement the grammar interpreter once, port languages
in usage order, and let `cargo xtask highlight` count coverage as a number that
only goes up — structurally the same instrument as M2's `PENDING` ratchet, which
delisted 213 of 215 cases stage by stage. **S3's gate is the interpreter plus a
counted, differentially-verified subset — not 297 grammars.**

**The M0 rationale is retired, not merely bypassed.** `mt-highlight`'s stub doc
comment claims tree-sitter was chosen for incremental re-parse inside a fence.
That benefit is M4's; every cost is M3's; and the coverage-per-megabyte number
now says it does not become affordable at M4 either. **M4 re-opens this on
incremental grounds if it wants to, with these numbers in hand.**

### D4 — what a theme *is* **← decide at S1**

C7 says a theme carries geometry, colour, and a paired code-highlight palette,
with no schema and 11,001 lines of prior art in CSS. M3 must decide: a typed
Rust struct with named fields · a data file (TOML/JSON) with a versioned schema
· a small subset-of-CSS parser. The decision constrains D8's display list and
every golden test in §7, because a golden layout is only reproducible if the
theme that produced it is. **The 800px-vs-750px split is the test case**: the
model must express that muya's default and every shipped theme disagree.

### D5 — M3 drives full `parse()`, and `mt_md::reparse` stays unproven **← decided at open**

M2 §10's instruction is *do not build on `mt_md::reparse` without
re-establishing it first*, and it offers two acceptable paths: close the class
with a delta-debugging campaign, or drive full `parse()` calls and treat the
incremental path as an unproven optimization. **M3 takes the second, and the
argument is that M3's scope makes it free:** a read-only viewer re-parses on
file open, not on keystroke. Nothing in M3 needs the incremental path, so
adopting it would import an open defect class for no benefit.

Two consequences recorded so this is not read as the debt being paid.
**M4 still owes the re-establishment** — the class is open, and M4 is where an
editor runs it on every keystroke. And **M3 must not quietly grow a dependency
on it** through a "fast reload" convenience; §6's S7 gate asserts the absence.

### D6 — where the previewer binary lives **← decide at S1**

§1's tension. Options: a `[[bin]]` in `mt-cli` (which exists, is M0's, and
already reads files) · a new binary in `mt-app` (M5's crate, opened early) · a
non-member crate outside `crates/` the way `fuzz/` is a separate workspace.
The constraint is hard and mechanical: **`cargo xtask deps` requires
`crates/` to contain exactly the 14 named crates** — no more, no fewer — so a
fifteenth crate is a check failure, not a style preference. The
outside-the-workspace option is the one with precedent (`fuzz/`), and it also
keeps `winit` out of the main dependency graph until M4 wants it.

### D7 — fonts: the collection is built above `mt-layout` and passed in **← taken at S0**

C9: parley's default `system` feature does filesystem I/O, and `mt-layout`
commits to none. MarkText bundles Open Sans and DejaVu Sans Mono as files and
names four fallbacks after each.

**Decision: the third option — `mt-layout` depends on parley with
`default-features = false`, never enumerates anything, and receives a font
collection constructed by the shell. Goldens run against a pinned bundled set
registered from bytes; the shipped previewer adds system fonts on top.**

It was "the one to beat" and nothing beat it, because S0 found it costs less
than the alternatives rather than more:

- `default-features = false` (plus `std`) builds and lays out, and drops the
  dependency count **61 → 49** crates. The purity constraint is cheaper than
  the default.
- In-memory registration is a two-call API:
  `Collection::new(CollectionOptions { shared: false, system_fonts: false })`
  then `register_fonts(Blob<u8>, None)`. No path, no enumeration, no I/O.
- Goldens become reproducible across machines by construction — which §7 needs,
  since textual layout goldens are M3's primary instrument and a golden that
  depends on the developer's installed fonts is not a golden.

**Three measured facts turn the bundled half into concrete work rather than a
checkbox**, and the first is a trap that would have cost a stage to find later:

1. **MarkText's bundled Open Sans cannot be used.** All eight files are `.woff`,
   and skrifa **rejects them silently** — `register_fonts` returns an empty
   `Vec` rather than an error. A font that fails to load without saying so
   produces a layout that is subtly wrong everywhere, with no diagnostic. The
   four DejaVu Sans Mono `.ttf` files (**1,178,216 B**) load fine. **M3 must
   re-source Open Sans as `.ttf`/`.otf`, or decompress at build time, and must
   treat an empty registration result as a hard error.**
2. **The bundled set does not cover the corpus.** DejaVu Sans Mono renders
   Arabic (0/11 tofu) but **not Hebrew (8/9 tofu)** — and `bench/corpus/rtl.md`
   is half Hebrew. The gate says *"Bidi … render correctly"*, so a
   Hebrew-capable face is a **deliverable, not a nicety**. CJK and emoji are the
   same question unanswered: `cjk.md` and `emoji.md` are gate inputs too.
3. **`complex-scripts` costs +3.6 MiB** and 0 extra crates (C9). The gate's CJK
   clause almost certainly requires it, and it is the second-largest line item
   in the binary after the GPU backend that D1 just declined to ship.

**S1 owes the face list**, since D4's theme model names font families and a
family that resolves to nothing is the failure mode above.

### D8 — what the display list carries **← decide at S1**

§5 sketches `BlockContent::Text { layout: parley::Layout<Brush>, … }` — i.e.
`mt-layout`'s public type exposes parley's. Alternative: a neutral display list
of positioned glyph runs and rects, with parley confined behind the seam. The
first is cheaper and matches the sketch; the second keeps `mt-render`, PDF
export and hit-testing from all depending on a 0.x crate with churn like
C9's. C9 also settles a sub-question: whichever is chosen, the list carries
`parley::BoundingBox` or plain `f32` rects, **not** kurbo/peniko types.

### D9 — laziness is load-bearing, and S1's data structures must anticipate it **← taken at S0**

§5 says *"never lay out the whole document synchronously"*, C8 says muya does
exactly that, and C5 says a width change is cheap while content is not. S0
measured the honest version.

**Decision: D9 resolves to its second branch. Eager single-threaded layout of
5 MB misses the gate, so laziness is not an optimization with a stage of its
own — S1's data structures have to anticipate it.**

| | |
|---|---:|
| `mt_md::parse`, `5mb.md` | **81 ms** |
| eager layout, one `Layout` per block | **813 ms** (median, 805–829 over 8 launches) |
| **end to end** | **≈ 896 ms — 112 % of the 800 ms gate** |
| blocks / lines | 39,308 leaves / 92,758 lines |
| peak RSS, `1mb.md` | 84.6 MiB (gate ≤ 120 MB) |
| peak RSS, `5mb.md` | 379 MiB |

Hardware: i5-13600K, 64 GB, NVMe, Windows 11, `--release`, warm file cache.
**This is a fast 2022 desktop, so 12 % over is the optimistic reading**, and the
figure is a **lower bound**: it lays out plain text as a single style run, with
no `mt-inline` tokens and no `InlineBox`es. A synthetic styled variant costs
**+10–13 %**.

**Three findings that constrain S1 rather than S6.**

**Laziness must defer shaping, not line-breaking.** The phase split is
**shaping 90.3 %** (720 ms), `break_all_lines` 8.1 %, builder setup 1.5 %,
`align` 0.1 %. A lazy design that defers only line-breaking defers 8 % of the
cost. What must be deferred is `builder.build` itself — which means the data
structure holds *unbuilt* blocks, and "a block that has no `Layout` yet" is a
first-class state in the tree from S1, not a cache miss bolted on at S6.

**§5's `Code { lines: Vec<Layout> }` is refuted.** Against one `Layout` per
fence, one per code line is **1.38× slower and 2.21× the memory** (1,194 ms /
607 MiB vs 863 ms / 275 MiB over 120,000 code lines). The deciding constant:
**a `parley::Layout` costs 3,956 B resident** against a 328 B struct, so a
100,000-line code file would spend **377 MiB and 636 ms** on the split alone.
**S1 builds one `Layout` per fence.** The same constant explains the whole
result — layout cost scales with *block count* × a fixed per-`Layout` price,
not with document size, and ns/byte actually *falls* 367 → 148 as documents
grow (C5). **The lesson generalises: any S1 design decision that multiplies
`Layout` count is the expensive one, whatever it is optimizing.**

**A third option the plan does not consider, and it is cheaper than laziness.**
Layout is embarrassingly parallel — each block's `Layout` depends on its own
text, the theme and the width, nothing else. Measured with `std::thread::scope`
and a byte-balanced split, no `rayon`, no new dependency:

| threads | 1 | 2 | 4 | 8 | 20 |
|---|---:|---:|---:|---:|---:|
| best | 794 ms | 483 ms | 421 ms | 349 ms | **334 ms** |

**Parse + parallel eager layout = 415 ms, inside the gate with no laziness of
any kind.** Scaling plateaus at 2.37×, most likely allocator contention — a
hypothesis S0 did not profile, and it should be labelled as one.

This does not overturn the decision: single-threaded eager misses, which is what
D9 asked. But it is a second lever that needs **no viewport tracking, no
invalidation, no scroll-driven layout queue, and no change to S1's data
structures**, and it composes with laziness rather than competing. **S6 costs
both before committing to the lazy architecture alone** — and S1 should not
assume the lazy path is the only thing standing between M3 and its gate.

### D10 — the golden-data format **← decide at S1**

§11.3 asks for *"golden images per block type per platform, perceptual-diff
threshold"*. That is a `mt-render` test. `mt-layout` is headless and deserves a
**textual** golden — a stable serialization of the display list — because a
text diff names the block that moved and a pixel diff does not. Two artifacts,
two stages, two thresholds: exact equality for layout, perceptual threshold for
pixels.

### D11 — what the viewer does with M6's block kinds **← decide at S1**

`MathBlock`, `Diagram` and inline math are real `Block` variants that M2 parses
and M6 renders. A previewer that shows nothing for them looks broken; one that
renders them needs KaTeX and mermaid equivalents that do not exist. The cheap
honest answer is to lay them out as their **source text in the code-block
style**, which is what muya's own `Options::SPEC` path effectively produces and
what M2's port already emits for `multiple-math`. Decide it explicitly so it is
a choice rather than a gap.

**On S0 being a whole stage.** M2 spent S7 discovering that a check which gets
raised rather than reasoned about is worth more than an argument, and closed on
a red soak because three rounds of new defects is a rate rather than a tail.
M3 opens with ten corrections to a plan, two of which are *"this number has no
source."* Building on those would be the same mistake in the other direction.

**On what S0 must not become.** A measurement stage with no product code is
also the easiest stage in this project to let run long. Its gate is a list of
decisions with numbers attached, not a report.

### S0 is closed. Where the evidence lives, and what it did not answer

Five experiments, all committed as running code rather than as claims. The
spikes are a **separate cargo workspace at `spikes/`**, following `fuzz/`'s
precedent for the reason D6 gives: `crates/` must hold exactly 14 crates, and a
spike is by definition a crate that should not survive. `cargo xtask deps`
reports **14**.

| Evidence | Takes |
|---|---|
| `spikes/results/e1-bidi-inline-box.md` | M3-R1, D2, part of D7 |
| `spikes/results/e2-binary-size.md` | §12.2's table, D1, part of D3 |
| `spikes/results/e3-layout-scale.md` | D9, confirms C5 |
| `spikes/results/e4-highlight.md` | D3 |
| `bench/BASELINE.md` | M3-R3, C8 — owed since M0, now paid |

**The gate is met on its own terms**: D1, D2, D3, D7 and D9 are each taken with

**Two things S0 did not answer, recorded here rather than left to be noticed

fallback trigger S3 must check.

**One methodological note for later stages.** Two decisions moved only because
two experiments were read *together*: E1 said track parley `main` for
correctness, E3 said `main` costs 13.9 % and +40 % RSS, and D2 is the trade
between them — neither experiment alone contains the decision. **A stage that
reports experiments separately and never crosses them will miss this class of
finding.**

## 7. Test inventory — and the finding is that there is not one

M1 transcribed **49** spec cases. M2 transcribed **215** of the 221 its §7
inventories, tracked them in a `PENDING` ratchet, and delisted them stage by
stage until 2 remained — both M6's. Both milestones could also run a **differential** against the TypeScript
engine on every commit, which §11.2 correctly calls the highest-value test
asset in the project.

**M3 has zero transcribed cases, and for most of it no differential is
possible.** There is no muya spec suite for rendering, because the thing being
tested was Chromium. `cargo xtask diff` compares state JSON; there is nothing
to compare a glyph position to. This is the largest methodological change in
the project so far and it deserves stating plainly rather than discovering at
S4.

What replaces it, in descending order of strength:

| Instrument | Covers | Strength |
|---|---|---|
| **`xtask highlight --require-ts`** (S3) | code-fence tokenization vs Prism | A **real differential** — same shape as `blocks`/`diff`, same Node harness. The one place M3 keeps M1/M2's strongest tool |
| **Textual layout goldens** (S1, S2) | the display list, exactly | Strong but *self-referential*: it proves nothing changed, not that anything is right. First goldens must be reviewed by eye, once, deliberately |
| **The §2 CSS table as constants** (S1) | the geometry numbers | The closest thing to a spec M3 has. A stylesheet is a fixed reference even if it is not runnable |
| **Pixel goldens + perceptual threshold** (S4) | rasterization | §11.3's instrument; platform-dependent and threshold-dependent by nature |
| **Corpus-driven property tests** (S2, S7) | bidi/CJK/emoji invariants, determinism, no-panic | Generated input, which M2 S7 proved finds what fixed corpora do not |
| **The Electron baseline** (S0) | the performance claim | Owed since M0 and still not built. Without it, "≤ 800 ms" has no comparison |

**The uncomfortable sentence, written here so no later section can soften it:
for the first time in this project, "does it match MarkText?" cannot be
answered by running MarkText.** It can be answered for code highlighting, and
approximated for geometry by reading a stylesheet. For everything else, M3's
answer is a golden file that someone looked at once.

## 9. Open decisions carried forward

From M2 §9:

- **GPU vs CPU default (§12.2)** — carried, reshaped by C1, and **closed at S0
  by D1: CPU only.** `wgpu` does not enter M3's dependency graph. It is closed
  on binary size and risk asymmetry rather than on the frame-rate measurement
  §6 asked for, because that measurement needs `mt-render`; **S4 owes the
  number and may reopen this.** The decision is therefore closed with a date on
  it, which is what §14's open-decisions list asked for, and not closed for
  good.
- **`Arena` demotion policy** — `Text` promotes `Inline → Rope` at 8 KiB and
  never demotes. Unchanged and untriggered; M3 is the first milestone to hold
  thousands of blocks live at once, so if a profile ever shows it, S6 is where
  it would show.

New at M3: D1–D11 above. **D5 was taken at open; D1, D2, D3, D7 and D9 were
taken at S0 with numbers attached. Five remain, and all five are S1's: D4 (what
a theme is), D6 (where the previewer binary lives), D8 (what the display list
carries), D10 (the golden-data format), D11 (M6's block kinds).**

Two of those five are now constrained by S0's numbers rather than open on their
own terms. **D8 inherits D2's pin**: tracking parley `main` means #697-class
geometry churn invalidates goldens, so whether the display list exposes
`parley::Layout` decides how far that churn propagates. And **D4 inherits D7's
face-list obligation**, since a theme names font families and a family that
resolves to nothing fails silently.

## 10. Owed forward

Restated at open so the list starts complete rather than accreting.

### Owed to M4 — everything M2 §10 owed to "M3/M4", unchanged

All three items in §0 above are carried without modification. M3 pays none of
them and is not expected to: the per-kind source-offset inverse needs a caret
to have a caller, the reparse class needs an editor to be dangerous, and both
of M1's renderer behaviours are caret-dependent. **The risk is that a fourth
milestone passes them along and the list becomes furniture.** They are restated
here in full rather than referenced, which is the same discipline M2 §10 used
for M1's.

### Owed by M3 to M4 — the visible-text offset map (C6)

New, and M3's own. The map from visible-text offsets to block-text offsets
falls out of S2's style-run walk. M4 needs it for caret placement from a click;
M5 needs it for search-hit positioning. **It should be public API from S2, not
an internal detail M4 has to re-derive** — which is the mistake M2 §10 records
having nearly made with `SourceMap`.

### Owed by M3 to M6 — the display list is PDF export's input too

`mt-layout`'s doc comment commits to *"one engine, three consumers"* and names
PDF export as one of them. M3 has no PDF writer and will not check the claim.
D8's decision — whether the display list exposes `parley::Layout` or a neutral
form — is the one that determines whether that promise is keepable, so **D8 is
recorded as an M6-facing decision taken at M3** rather than a local one.

### Owed by M3 to M5 — the theme model's second half

D4 decides what a theme is. What M3 will *not* build is the preference UI, the
picker, or the import of an existing MarkText install's theme choice — all M5's
per §9. The obligation M3 incurs is that the model must be **expressible from
the 32 shipped CSS files**, since M5's import path has to read them.

### Owed by M3 to upstream — one small parley patch, and it is already specified

New at S0. M3-R1's residual is a bidi level assigned by `unwrap_or(0)` where an
inline box has no preceding run, sitting under parley's own TODO saying the box
should instead take the level of a U+FFFC standing in for it. E1's harness
already contains the failing case, the expected coordinates, and an independent
`unicode-bidi` oracle that produces them — which is most of a regression test.

§13 R2's mitigation reads *"Linebender is responsive; budget for upstream
contributions."* **This is that budget falling due, and it is the cheapest
version of it the project could have got**: a one-line fix with a ready test,
rather than the feature-scale contribution R2 imagined. M3 carries the
workaround (an RLM before the box) either way, so **this is owed but not
blocking**, and it should not be allowed to become the reason a stage slips.
