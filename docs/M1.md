# M1 — `mt-inline`, the tokenizer port

**Status:** working plan · **Opened:** 2026-08-01 · **Predecessor:** [`M0.md`](M0.md)

RUST-REWRITE-PLAN.md §9 M1: *"`mt-inline` — full tokenizer port."* Exit gate:
*"Every `inlineRenderer/__tests__` spec passes. Tiling invariant holds on the
whole corpus. Fuzzer runs 24 h without a panic."* Budgeted at 2 months.

This document is the working plan for that milestone. Where it disagrees with
§3 of RUST-REWRITE-PLAN.md, the disagreement is called out explicitly below
(§"Corrections to §3") rather than applied silently — §3 remains the contract;
this is the reading of it after the source was actually read.

---

## 1. Scope

**In:** `crates/mt-inline` — the token types, the rule set, the tokenizer loop,
the emphasis-validation helpers, `generator`, `tokensToPlainText`, and the
marker-reveal predicate from §3.1.

**Out:** everything downstream. `mt-inline` takes `&str` and returns
`Vec<Token>`. It does not know about blocks, documents, layout, or rendering.
The §1 dependency constraint (no `mt-ui`, no `mt-app`, no I/O, no windowing, no
GPU) is machine-checked by `cargo xtask deps` and must stay green.

**Deliberately deferred to M2:** wiring the tokenizer into `mt-md`. M1 ends with
a tokenizer that is correct in isolation and proven so. Nothing consumes it yet.

**The handler precedence list is the contract.** `INLINE_HANDLERS`
(`lexer.ts:792`) is a fixed, ordered array; the loop takes the first handler
that returns `true`. Port it as an ordered array too, not as a match on the
next character — the order *is* the spec, and it carries a comment in the
TypeScript saying so.

## 3. Reconciling §3's `TokenKind` with `types.ts`

§3's `TokenKind` is a sketch and is incomplete in ways that matter. `types.ts`
is authoritative. Differences to resolve when writing the Rust enum:

| §3 sketch | `types.ts` reality |
|---|---|
| `Link { href, title, children }` | also `marker`, `hrefAndTitle`, `anchor`, `backlash: {first, second}` |
| `Image { attrs, backslash }` | also `marker`, `srcAndTitle`, `src`, `title`, `alt`; `attrs` is `{src, title, alt, ...}` with `src`/`alt` **URI-encoded**, unlike the bare fields |
| `ReferenceDefinition { /* … */ }` | 11 distinct fields, one per capture group |
| `HtmlTag { tag, attrs, children }` | also `openTag`, `closeTag`, `content` |
| `Text` | carries `content` (equal to `raw`) |
| `Backslash { marker }` | also `content`, which is **always** `''` |
| — | every token has `parent: Token[]`, a back-reference |
| `SuperSubScript` | one variant covering both `^` and `~`; the marker distinguishes them |
| `Emoji`, `InlineCode`, `InlineMath` | one TS variant, `CodeEmojiMathToken`, three `type` values |

Two naming points:

- muya spells it **`backlash`**, not `backslash` — in the token type name, the
  field name, and the rule name. It is a typo that is load-bearing: the
  differential harness compares `type` strings. Keep muya's spelling wherever it
  crosses the wire; a Rust-side `Backslash` variant is fine only if it
  serializes as `backlash`.
- `parent` is a renderer navigation aid, not data. **Drop it.** Rust has no
  cheap cyclic back-reference and nothing in the tokenizer reads it. If a
  consumer needs a parent later, it gets an index path.

## 4. Corrections to §3

### C1 — the `regex` crate cannot express these rules

§3 says: *"`rules.ts` is regex-driven; use `regex` with pre-compiled
`LazyLock<Regex>`."* That does not work. The `regex` crate has no
backreferences and no lookaround, by design. **16 of the 26 rules need one or
both:**

| Feature | Rules |
|---|---|
| Backreference | `strong` `em` `inline_code` `del` `emoji` `inline_math` `superscript` `subscript` `html_tag` (`\3`) `reference_definition` (`\9`) |
| Lookahead | `strong` `em` `del` `link` `reference_link` `soft_line_break` `hard_line_break` `auto_link_extension` `inline_math` `superscript` `subscript` |
| Lookbehind | `superscript` `subscript` `footnote_identifier` |

Only 10 rules — `hr` `code_fence` `header` `multiple_math` `tail_header`
`image` `reference_image` `html_escape` `backlash` `auto_link` — are plain
enough for `regex`.

**Recommendation: `fancy-regex`.** It wraps `regex`, supports backreferences
and lookaround, and delegates to the underlying non-backtracking engine when a
pattern does not need the extra power — so the 10 plain rules stay fast. It
keeps §3's "port the regexes verbatim first, hand-optimize later, with the
suite as the guard" strategy intact, which is the whole reason §3 chose regexes.

Hand-writing 16 scanners up front is the alternative, and it inverts §3's
sequencing: it makes the highest-fidelity-risk component a from-scratch
reimplementation on day one. Reject it for M1. Individual scanners can replace
individual regexes later, one at a time, once the suite is green — exactly as
§3 prescribes.

*Caveat to check in S1:* `fancy-regex` is a backtracking engine, so the
ReDoS-class patterns `rules.ts` disables lint rules for (`no-super-linear-
backtracking` appears 7 times) are genuinely super-linear here too. Input is
the user's own block text, not network data, so this is a latency question and
not a security one — but it is what the M1 fuzzing gate should be pointed at
first. `fancy-regex` has a backtrack limit; set it explicitly and decide what
exceeding it means (recommend: treat as "rule did not match", never panic).

### C2 — JavaScript and Rust regex classes are not the same

Faithful-port traps that will not show up as compile errors:

| Class | JavaScript | Rust `regex`/`fancy-regex` | Fix |
|---|---|---|---|
| `\w` | ASCII `[A-Za-z0-9_]` | Unicode-aware | write `(?-u:\w)` or the literal class |
| `\s` | includes U+FEFF, excludes U+0085 | `\p{White_Space}`: excludes U+FEFF, includes U+0085 | define the class explicitly |
| `.` | excludes `\n \r \u2028 \u2029` | excludes `\n` only | use an explicit negated class |
| `(?i)` | simple folding | full Unicode folding | only `auto_link` and `html_tag` use it; verify |

`\w` matters immediately: it is the emoji word-boundary check (`lexer.ts:206`),
and under Rust's default a Cyrillic or CJK character before a `:` would suppress
an emoji that muya emits. `\s` matters because `UNICODE_WHITESPACE_REG` drives
the entire emphasis-flanking decision, and the corpus has a BOM case.

### C3 — the tiling invariant holds *per level*, not globally

§3 rule 1 says concatenating every token's `raw` reproduces the source. True,
but only within one `tokenizerFac` call. Children are tokenized from a
**substring** with an absolute base offset, so:

- concatenating a level's tokens reproduces that level's input exactly;
- a child level's concatenation reproduces the parent's capture group, which is
  a sub-slice of the parent's `raw`.

Assert both, and assert that every child range is contained in its parent's
range. State the invariant that way in the debug assertion, or it will fire
spuriously on the first nested `**bold**`.

Three handlers need care because their `raw` is not their consumed length:

- `tryBacklash` — `raw` is only the `\`; the escaped character is pushed into
  `pending` and surfaces in the *next* text token. Consumed length is 2.
- `tryTailHeader` — `raw` and consumption are both `tailTo[1]`, not `tailTo[0]`;
  the trailing whitespace group is left in the input.
- `tryAutoLinkExtension` — `raw` is the *trimmed* extent; consumption matches
  the trim, so the trimmed tail re-enters the loop as text.

## 5. Decisions to make before writing code

### D1 — offset units: UTF-16 or UTF-8 bytes? **← decide first**

muya's `range.start`/`range.end` are JavaScript string indices, i.e. **UTF-16
code units**. §3 says "byte offsets into the block's text". These differ for
every non-ASCII character, and the corpus deliberately contains CJK, emoji
(including ZWJ sequences and regional-indicator flags), and RTL files.

This is not cosmetic. Ranges are what §3.1's marker-reveal predicate compares
the caret against, what `highlights` intersect with, and what M2's differential
harness would compare if ranges ever reach the state dump.

**Recommendation:** store UTF-8 byte offsets internally — anything else fights
`&str` — and put the UTF-16 conversion in *one* place, at the boundary where a
token is serialized for comparison against TypeScript. Transcribed tests that
assert a numeric range must then either assert byte offsets (recompute by hand,
document the input's encoding) or go through the converter. Pick one convention
in S0 and write it into the test module header; mixing them silently is the
failure mode.

Note this also *removes* code: `lastCodePointChar` and `codePointCharAt`
(`utils.ts:104-130`) exist purely to reassemble surrogate pairs that JavaScript
splits. Rust's `char` iteration gives that for free. Port their *callers*
faithfully; do not port the functions.

### D2 — `getAttributes` needs an HTML parser

`getAttributes` (`utils.ts:172`) calls `DOMParser` — which is why every one of
the seven spec files carries `// @vitest-environment happy-dom`. `mt-inline`
cannot have a DOM.

It parses the full match, takes `body.firstElementChild`, keeps only the 25
whitelisted attribute names, seeds `{title, src, alt}` to `''` for `IMG`, and
coerces `width`/`height` through a digits-only check. Returning `null` (no
element) makes `tryHtmlTag` fail; returning `{}` does **not** — an empty object
is truthy in JavaScript. Get that distinction right: `None` fails, `Some(empty)`
passes.

**Recommendation:** hand-write a scanner over the open tag implementing the
HTML5 attribute-tokenization states. It is a small, well-specified state
machine, and it keeps `mt-inline` dependency-free. The risk is malformed input,
where DOMParser does error recovery — so pair it with a differential check
against happy-dom via the existing harness. `html5ever` is the fallback if the
scanner diverges on real corpus content; it is pure (no I/O) and so permitted by
§1, but it is a large dependency for one function.

### D3 — reproduce muya's emoji-in-children bug, or fix it?

`tryChunks` tests `state.originSrc[state.pos - 1]` for the emoji word boundary.
In a nested call `originSrc` is the **child** substring while `pos` is an
**absolute** offset, so the check reads the wrong character — or off the end.

Verified against the running engine:

```
":smile:"            → emoji: [":smile:"]     top level, correct
"lunch :100: today"  → emoji: [":100:"]       top level, correct
"**a :smile:**"      → emoji: []              nested — emoji swallowed
"**:smile:**"        → emoji: []              nested — emoji swallowed
"*x :smile:*"        → emoji: [":smile:"]     nested — survives by luck
"[a :smile:](u)"     → emoji: [":smile:"]     nested — survives by luck
```

Whether an emoji inside emphasis survives depends on what character happens to
sit at the absolute offset within the child string. `tryAutoLinkExtension` reads
`originSrc` the same way but is gated on `state.top`, so it is safe.

**Recommendation: reproduce it in M1, fix it in M2.** M1's whole verification
strategy is agreement with the TypeScript engine; diverging on day one gives up
the one signal that says the port is faithful. Port it bug-for-bug with a
`// MUYA-BUG(emoji-nested-boundary)` marker and a test asserting the current
behaviour, then fix it at M2 as a deliberate, tested divergence — at which point
`expected-failures.json` and the differential harness can absorb one known
difference. **Raise it upstream as a marktext issue either way.**

Grep for that marker at M2 to find every such site. Others found so far:

- `lexer.ts:135` — `state.pending += state.pending + backTo[2]` reads as a
  doubling bug, but `pushPending` clears `pending` immediately above it, so it
  is inert. Port it as a plain assignment and note why.
- `disallowedHtmlTag` (`lexer.ts:21`) is unanchored, so `<mytitle>` matches
  `title` and is rejected. Substring semantics — keep them.

### D4 — `state.src.substring(n)` is O(n²)

The TypeScript loop reslices the remaining input on every token *and every
unmatched character*. Rust should advance an index into the original `&str` and
match anchored at that index. This is a pure win — same semantics, no allocation
— but it changes what "the input to a rule" means, so decide it before writing
the loop rather than retrofitting.

Anchoring: every rule is `^`-anchored and JavaScript `exec` is called on a fresh
substring. In Rust, match against `&src[pos..]` with the same `^` anchor, or use
an explicitly anchored search. Do not use an unanchored search and check the
match start — that silently changes `lowerPriority`'s meaning.

### D5 — where `lowerPriority` gets its rule set

Two different sets are passed, and the difference is load-bearing (there is a
14-line comment in `rules.ts:118-125` explaining why, referencing issue #4671):

- `validateRules` — all rules except `em`, `strong`, `tail_header`, `backlash`,
  `superscript`, `subscript`, `footnote_identifier` — used by emphasis
  validation and the emoji check.
- `linkValidateRules` — only `inline_code`, `html_tag`, `auto_link` — used by
  `tryLink` and `tryReferenceLink`.

Model these as two explicit const slices. Do not derive one from the other at
runtime; the exclusion list is a `const` in TypeScript for the same reason.

Note `lowerPriority` iterates every position up to `offset` and runs every rule
in the set at each one. It is O(offset × |rules|) regex executions. Correct
first, per §3; but it is the obvious hot spot and worth a benchmark before M1
closes so M3 is not surprised.

### D6 — fuzzing on Windows

The exit gate is 24 hours without a panic. `cargo-fuzz`/libFuzzer support on
Windows MSVC is thin. **Recommendation:** run the 24 h libFuzzer soak on Linux
in CI, and run `proptest` on all three platforms in the normal test job. The
corpus already contains the awkward inputs to seed from. Panic-freedom is a
property of the code, not the platform — but the *platform-specific* risk here
is UTF-8 boundary slicing, so make sure the proptest generator produces
multi-byte and lone-surrogate-adjacent input.

### D7 — what `highlights` costs

`tokenizer()` takes `highlights` and runs a post-pass intersecting every token
range with every highlight. §3 puts `highlights: SmallVec<[Highlight; 2]>` on
every token. The TypeScript makes it optional and only allocates on
intersection. Keep it optional/empty-by-default; a `SmallVec` inline capacity of
2 on every token in a 5 MB document is a measurable memory cost for a field
that is empty except during a search.

S6's round-trip property is the strongest single check in the milestone and it
is nearly free — `generator` is a concatenation of `raw` fields. Build it as
soon as S1 lands rather than waiting for S6; it will catch tiling errors in
every stage after it.

## 8. Risks

| Risk | Mitigation |
|---|---|
| `fancy-regex` backtracking blows up on a pathological input | Explicit backtrack limit from S1; treat exceeding it as no-match; point the fuzzer at it first |
| D1 decided late, or decided twice | Gate S0 on it; write the convention into the test module header |
| The attribute scanner (D2) diverges from DOMParser on malformed HTML | Differential check against happy-dom in S4; `html5ever` as the escape hatch |
| Bug-for-bug fidelity (D3) accumulates without a record | `// MUYA-BUG(...)` marker convention, grepped at M2 |
| `lowerPriority` is O(n²) and becomes an M3 problem | Benchmark before M1 closes, so the number is known rather than discovered |
| The 24 h fuzz gate is unrunnable on the dev platform | Linux CI for the soak, proptest everywhere (D6) |
