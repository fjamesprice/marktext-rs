# M1 — `mt-inline`, the tokenizer port

**Status:** working plan · **Opened:** 2026-08-01 · **Predecessor:** [`M0.md`](M0.md)

RUST-REWRITE-PLAN.md §9 M1: *"`mt-inline` — full tokenizer port."* Exit gate:
*"Every `inlineRenderer/__tests__` spec passes. Tiling invariant holds on the
whole corpus. Fuzzer runs 24 h without a panic."* Budgeted at 2 months.

This document is the working plan for that milestone. Where it disagrees with
§3 of RUST-REWRITE-PLAN.md, the disagreement is called out explicitly below
(§"Corrections to §3") rather than applied silently — §3 remains the contract;
this is the reading of it after the source was actually read.

---

## 1. Scope

**In:** `crates/mt-inline` — the token types, the rule set, the tokenizer loop,
the emphasis-validation helpers, `generator`, `tokensToPlainText`, and the
marker-reveal predicate from §3.1.

**Out:** everything downstream. `mt-inline` takes `&str` and returns
`Vec<Token>`. It does not know about blocks, documents, layout, or rendering.
The §1 dependency constraint (no `mt-ui`, no `mt-app`, no I/O, no windowing, no
GPU) is machine-checked by `cargo xtask deps` and must stay green.

**Deliberately deferred to M2:** wiring the tokenizer into `mt-md`. M1 ends with
a tokenizer that is correct in isolation and proven so. Nothing consumes it yet.

## 2. What is being ported

Real line counts, measured today — §3 quotes 898 + 112 from an earlier revision:

| Source | Lines | Contains |
|---|---:|---|
| `inlineRenderer/lexer.ts` | 1003 | 16 rule handlers, the tokenizer loop, `generator`, `tokensToPlainText` |
| `inlineRenderer/utils.ts` | 360 | `validateEmphasize`, `lowerPriority`, `getAttributes`, `parseSrcAndTitle`, `correctUrl`, the CJK/punctuation tables |
| `inlineRenderer/rules.ts` | 130 | 26 regexes across 5 rule groups |
| `inlineRenderer/types.ts` | 246 | 20 token variants |
| `config/escapeCharacter.ts` | 553 | ~~538~~ **269** HTML entity ↔ character pairs, of which 252 are distinct — see below |
| `utils/marked/utils.ts` | — | `findClosingBracket` (23 lines, needed by `correctUrl`) |
| `utils/index.ts` | — | `isLengthEven`, `union` (highlight intersection) |

≈1750 lines of behaviour. Small enough to port line by line, as §3 requires.

**Corrected at S6, which is the stage that built the map.** "538 pairs" was the
file's line count read as a count of pairs. It is two arrays of **269**, so 269
pairs — and `escapeCharactersMap` is a `reduce` over both, so a repeated key is
overwritten by its last occurrence and the *decode map* holds **252**. Twelve
keys repeat; every repeat pairs with the same character, so the resolution order
is unobservable. S1 needed only the keys and transcribed all 269 verbatim,
because that list **is** the `html_escape` rule (`rules.ts:45` joins it into an
alternation). S6 needed the values. `crates/mt-inline/src/escape.rs` holds both
and its header carries the enumeration.

**The handler precedence list is the contract.** `INLINE_HANDLERS`
(`lexer.ts:792`) is a fixed, ordered array; the loop takes the first handler
that returns `true`. Port it as an ordered array too, not as a match on the
next character — the order *is* the spec, and it carries a comment in the
TypeScript saying so.

## 3. Reconciling §3's `TokenKind` with `types.ts`

§3's `TokenKind` is a sketch and is incomplete in ways that matter. `types.ts`
is authoritative. Differences to resolve when writing the Rust enum:

| §3 sketch | `types.ts` reality |
|---|---|
| `Link { href, title, children }` | also `marker`, `hrefAndTitle`, `anchor`, `backlash: {first, second}` |
| `Image { attrs, backslash }` | also `marker`, `srcAndTitle`, `src`, `title`, `alt`; `attrs` is `{src, title, alt, ...}` with `src`/`alt` **URI-encoded**, unlike the bare fields |
| `ReferenceDefinition { /* … */ }` | 11 distinct fields, one per capture group |
| `HtmlTag { tag, attrs, children }` | also `openTag`, `closeTag`, `content` |
| `Text` | carries `content` (equal to `raw`) |
| `Backslash { marker }` | also `content`, which is **always** `''` |
| — | every token has `parent: Token[]`, a back-reference |
| `SuperSubScript` | one variant covering both `^` and `~`; the marker distinguishes them |
| `Emoji`, `InlineCode`, `InlineMath` | one TS variant, `CodeEmojiMathToken`, three `type` values |

Two naming points:

- muya spells it **`backlash`**, not `backslash` — in the token type name, the
  field name, and the rule name. It is a typo that is load-bearing: the
  differential harness compares `type` strings. Keep muya's spelling wherever it
  crosses the wire; a Rust-side `Backslash` variant is fine only if it
  serializes as `backlash`.
- `parent` is a renderer navigation aid, not data. **Drop it.** Rust has no
  cheap cyclic back-reference and nothing in the tokenizer reads it. If a
  consumer needs a parent later, it gets an index path.

## 4. Corrections to §3

### C1 — the `regex` crate cannot express these rules **← actioned in S1**

§3 says: *"`rules.ts` is regex-driven; use `regex` with pre-compiled
`LazyLock<Regex>`."* That does not work. The `regex` crate has no
backreferences and no lookaround, by design. **16 of the 26 rules need one or
both:**

| Feature | Rules |
|---|---|
| Backreference | `strong` `em` `inline_code` `del` `emoji` `inline_math` `superscript` `subscript` `html_tag` (`\3`) `reference_definition` (`\9`) |
| Lookahead | `strong` `em` `del` `link` `reference_link` `soft_line_break` `hard_line_break` `auto_link_extension` `inline_math` `superscript` `subscript` |
| Lookbehind | `superscript` `subscript` `footnote_identifier` |

Only 10 rules — `hr` `code_fence` `header` `multiple_math` `tail_header`
`image` `reference_image` `html_escape` `backlash` `auto_link` — are plain
enough for `regex`.

**Recommendation: `fancy-regex`.** It wraps `regex`, supports backreferences
and lookaround, and delegates to the underlying non-backtracking engine when a
pattern does not need the extra power — so the 10 plain rules stay fast. It
keeps §3's "port the regexes verbatim first, hand-optimize later, with the
suite as the guard" strategy intact, which is the whole reason §3 chose regexes.

Hand-writing 16 scanners up front is the alternative, and it inverts §3's
sequencing: it makes the highest-fidelity-risk component a from-scratch
reimplementation on day one. Reject it for M1. Individual scanners can replace
individual regexes later, one at a time, once the suite is green — exactly as
§3 prescribes.

*Caveat to check in S1:* `fancy-regex` is a backtracking engine, so the
ReDoS-class patterns `rules.ts` disables lint rules for (`no-super-linear-
backtracking` appears 7 times) are genuinely super-linear here too. Input is
the user's own block text, not network data, so this is a latency question and
not a security one — but it is what the M1 fuzzing gate should be pointed at
first. `fancy-regex` has a backtrack limit; set it explicitly and decide what
exceeding it means (recommend: treat as "rule did not match", never panic).

**Decided in S1: 1,000,000 steps, and exceeding it means the rule did not
match.** The value is `fancy-regex`'s own default, adopted deliberately rather
than inherited silently, so that changing it is a reviewable diff rather than a
dependency bump; it is per rule *attempt*, not per document. Written into
`rules::BACKTRACK_LIMIT` with the three reasons no-match beats a panic, of
which the first is that the M1 exit gate is panic-freedom and a resource limit
that panics *is* the panic the gate forbids. The other two: a rule that does
not match leaves its characters to accumulate as text, which is what a reader
sees for any construct that fails to parse and leaves the tiling invariant
untouched; and every alternative treatment (skip the character, truncate the
input) makes the tokenizer non-total.

The cost, stated so it is not discovered later: tokenization becomes
input-length dependent at the extreme, so a differential disagreement is
*possible* on an input pathological enough to reach the limit. Nothing in
`bench/corpus/` or `spec/fixtures/` comes close. If one ever does, it is a
`spec/divergences.json` entry like any other deliberate difference.

### C2 — JavaScript and Rust regex classes are not the same **← actioned in S1**

Faithful-port traps that will not show up as compile errors:

| Class | JavaScript | Rust `regex`/`fancy-regex` | Fix |
|---|---|---|---|
| `\w` | ASCII `[A-Za-z0-9_]` | Unicode-aware | write `(?-u:\w)` or the literal class |
| `\s` | includes U+FEFF, excludes U+0085 | `\p{White_Space}`: excludes U+FEFF, includes U+0085 | define the class explicitly |
| `.` | excludes `\n \r \u2028 \u2029` | excludes `\n` only | use an explicit negated class |
| `(?i)` | simple folding | full Unicode folding | only `auto_link` and `html_tag` use it; verify |

`\w` matters immediately: it is the emoji word-boundary check (`lexer.ts:206`),
and under Rust's default a Cyrillic or CJK character before a `:` would suppress
an emoji that muya emits. `\s` matters because `UNICODE_WHITESPACE_REG` drives
the entire emphasis-flanking decision, and the corpus has a BOM case.

Two amendments from writing the table out, both in `crates/mt-inline/src/rules.rs`
and both checked by `every_character_class_matches_what_javascript_matches`:

- **`\d` belongs in the table.** JavaScript's is ASCII `[0-9]`; Rust's is
  `\p{Nd}`, every decimal-digit script. `emoji`, `auto_link` and
  `auto_link_extension` all use it, so Rust's default would admit Devanagari
  digits into an emoji shortcode and into a port number. Written as `0-9`.
- **A third rule uses `(?i)`:** `html_escape`, which `rules.ts:45` builds with
  the `i` flag. The three are handled differently, and none keeps a bare `(?i)`
  over a letter class. `auto_link` has no backreference, so the flag is
  *removed* and the classes written out (`[a-z]` → `[a-zA-Z]`) — which is
  exactly what JavaScript's Canonicalize does to an ASCII class, and unlike a
  Rust `(?i)` it cannot admit U+017F (ſ) or U+212A (K). `html_tag` needs the
  flag, because its `\3` must close a `<DIV>` with a `</div>`, so it keeps
  `(?i)` and wraps the tag-name class in `(?-i:…)`. `html_escape` is an
  alternation *of* letters, so neither trick applies; `(?i-u:…)` would be the
  answer but `fancy-regex` rejects it ("changing Unicode mode inline is not
  supported"), so the fold is expanded a letter at a time — `&amp;` becomes
  `&[aA][mM][pP];`.

One class is left verbatim, deliberately: `[\s\S]`, which is the union of a
shorthand and its own complement and so total in either engine. The test proves
that rather than assuming it.

### C3 — the tiling invariant holds *per level*, not globally

§3 rule 1 says concatenating every token's `raw` reproduces the source. True,
but only within one `tokenizerFac` call. Children are tokenized from a
**substring** with an absolute base offset, so:

- concatenating a level's tokens reproduces that level's input exactly;
- a child level's concatenation reproduces the parent's capture group, which is
  a sub-slice of the parent's `raw`.

Assert both, and assert that every child range is contained in its parent's
range. State the invariant that way in the debug assertion, or it will fire
spuriously on the first nested `**bold**`.

Three handlers need care because their `raw` is not their consumed length:

- `tryBacklash` — `raw` is only the `\`; the escaped character is pushed into
  `pending` and surfaces in the *next* text token. Consumed length is 2.
- `tryTailHeader` — `raw` and consumption are both `tailTo[1]`, not `tailTo[0]`;
  the trailing whitespace group is left in the input.
- `tryAutoLinkExtension` — `raw` is the *trimmed* extent; consumption matches
  the trim, so the trimmed tail re-enters the loop as text.

## 5. Decisions to make before writing code

### D1 — offset units: UTF-16 or UTF-8 bytes? **← decided**

**Decided in S0: UTF-8 byte offsets internally**, with the UTF-16 conversion
confined to the boundary where a token is serialized for comparison against
TypeScript. Written into `crates/mt-inline/src/lib.rs`, `token.rs` and the
header of `tests/inline_renderer_specs.rs`, per the gate.

Reading `lexer.ts` in full settles this rather than merely recommending it, and
the argument is stronger than the one below. Offsets are *pure bookkeeping*
inside the tokenizer: `state.pos` is only ever incremented by a match length,
stored into a token's `range`, and compared against **zero**. It is never used
to index anything — with exactly one exception, `state.originSrc[state.pos - 1]`
at `lexer.ts:206` and `:578`, which is D3 site 1 and which the port fixes by
indexing relative to the current level anyway. So the unit of measurement
cannot change any tokenization decision, and byte offsets cost nothing.

The transcribed specs assert on token *shape* and on field values read through
`Span::of`, never on numeric offsets — so the convention is applied rather than
restated, and an offset in the wrong unit fails by construction. The original
reasoning follows.


muya's `range.start`/`range.end` are JavaScript string indices, i.e. **UTF-16
code units**. §3 says "byte offsets into the block's text". These differ for
every non-ASCII character, and the corpus deliberately contains CJK, emoji
(including ZWJ sequences and regional-indicator flags), and RTL files.

This is not cosmetic. Ranges are what §3.1's marker-reveal predicate compares
the caret against, what `highlights` intersect with, and what M2's differential
harness would compare if ranges ever reach the state dump.

**Recommendation:** store UTF-8 byte offsets internally — anything else fights
`&str` — and put the UTF-16 conversion in *one* place, at the boundary where a
token is serialized for comparison against TypeScript. Transcribed tests that
assert a numeric range must then either assert byte offsets (recompute by hand,
document the input's encoding) or go through the converter. Pick one convention
in S0 and write it into the test module header; mixing them silently is the
failure mode.

Note this also *removes* code: `lastCodePointChar` and `codePointCharAt`
(`utils.ts:104-130`) exist purely to reassemble surrogate pairs that JavaScript
splits. Rust's `char` iteration gives that for free. Port their *callers*
faithfully; do not port the functions.

### D2 — `getAttributes` needs an HTML parser **← decided in S4**

`getAttributes` (`utils.ts:172`) calls `DOMParser` — which is why every one of
the seven spec files carries `// @vitest-environment happy-dom`. `mt-inline`
cannot have a DOM.

It parses the full match, takes `body.firstElementChild`, keeps only the
whitelisted attribute names, seeds `{title, src, alt}` to `''` for `IMG`, and
coerces `width`/`height` through a digits-only check. Returning `null` (no
element) makes `tryHtmlTag` fail; returning `{}` does **not** — an empty object
is truthy in JavaScript. Get that distinction right: `None` fails, `Some(empty)`
passes.

**Decided in S4: hand-write it, no `html5ever`, and take exactly as much of
tree construction as `body.firstElementChild` actually needs — no more.** The
recommendation below said "a hand-written scanner implementing the HTML5
attribute-tokenization states, with `html5ever` as the escape hatch", and
flagged that it predates knowing what the corpus contains. Both halves were
aimed at the wrong problem. The full reasoning is on
`crates/mt-inline/src/html.rs`; the four findings that changed the decision:

- **The reference is not an HTML5 tokenizer.** happy-dom parses a start tag's
  attributes with *one regular expression* — four alternatives over the text
  between the tag name and the tag's end. It is not the spec's state machine
  and it disagrees with it (`<div class=a/>` is `class="a"` there and
  `class="a/"` under the spec). So the port ports *that regex*, not the HTML5
  states.
- **`html5ever` would not have helped.** Its whole value would be agreeing
  with the reference, and it cannot: it is spec-conformant and happy-dom is
  not. Measured, happy-dom keeps a `<colgroup>` and a `<frame>` the spec's "in
  body" insertion mode discards. The escape hatch buys a large dependency and a
  *different* disagreement, so it is rejected rather than deferred.
- **Attribute tokenization was never the hard part.** Over 14,035 cases — all
  1199 distinct `html_tag` matches in `bench/corpus/` and `spec/fixtures/`,
  plus a sweep of every HTML element name against 46 attribute shapes and 14
  content shapes — the attribute scanner disagreed with happy-dom **zero**
  times. Every disagreement was *which element* `body.firstElementChild` is.
- **So the port models the element, not just the string.** Three mechanisms,
  each measured rather than recalled: eleven tag names happy-dom will not
  append under `<body>` (`<td>`, `<tr>`, `<html>`, …), `<head>` additionally
  swallowing its content, and an unterminated quoted value discarding the
  element with a retry at the next terminator. With those three, the port
  agrees with happy-dom on **every one of the 1199**.

The one mechanism deliberately **not** modelled is foster parenting inside
`<table>`/`<colgroup>`, where happy-dom moves a forbidden descendant to before
the table so that `getAttributes` returns *a different element's* attributes.
Modelling it means porting happy-dom's per-element `permittedDescendants` /
`moveForbiddenDescendant` tables — a test-only DOM's non-conformant table
handling, which the shipped Electron/Chromium build does differently again.
Registered as `html-tag-attrs-from-a-foster-parented-element`, per D3's rule;
it does not occur anywhere in the corpus or the fixtures.

Two things the decision corrected — one in this document, one in the token
types — both settled against the running module rather than by reading:

- **26 whitelisted names, not 25.** The extra one is `data-align`, marktext's
  own addition rather than part of the MDN list the comment cites —
  `utils/__tests__/dompurifyXss.spec.ts` explains why it survives sanitisation.
  `WHITELIST_ATTRIBUTES.length` is 26.
- **`getAttribute` can never return `null` in that loop**, so the attribute
  value is not optional. It iterates `getAttributeNames()`, so the name is
  present, and a valueless attribute has the value `""`; `null` means *absent*.
  `HtmlTag::attrs` was `Vec<(String, Option<String>)>` on the opposite reading,
  with a test asserting the distinction. Both were wrong and both are gone.

One thing the port needed that the paragraph above does not imply: attribute
values have their **character references resolved** by the HTML parser, so
`<a href="&ouml;&ouml;.html">` gives `href` the value `öö.html`. That is the
HTML5 named-reference table, not marktext's own `escapeCharacter.ts` list — a
different table with non-distinct keys, since it is a rule alternation rather
than a decode map. `crates/mt-inline/src/entities.rs` is the HTML5 one, 2125
names, generated and then verified entry by entry against the engine that
happy-dom actually calls.

*The original recommendation, kept because the decision is a departure from it:*
hand-write a scanner over the open tag implementing the
HTML5 attribute-tokenization states. It is a small, well-specified state
machine, and it keeps `mt-inline` dependency-free. The risk is malformed input,
where DOMParser does error recovery — so pair it with a differential check
against happy-dom via the existing harness. `html5ever` is the fallback if the
scanner diverges on real corpus content; it is pure (no I/O) and so permitted by
§1, but it is a large dependency for one function.

### D3 — muya's bugs: fixed in place, divergence registered **← decided**

`tryChunks` tests `state.originSrc[state.pos - 1]` for the emoji word boundary.
In a nested call `originSrc` is the **child** substring while `pos` is an
**absolute** offset, so the check reads the wrong character — or off the end.

Verified against the running engine:

```
":smile:"            → emoji: [":smile:"]     top level, correct
"lunch :100: today"  → emoji: [":100:"]       top level, correct
"**a :smile:**"      → emoji: []              nested — emoji swallowed
"**:smile:**"        → emoji: []              nested — emoji swallowed
"*x :smile:*"        → emoji: [":smile:"]     nested — survives by luck
"[a :smile:](u)"     → emoji: [":smile:"]     nested — survives by luck
```

Whether an emoji inside emphasis survives depends on what character happens to
sit at the absolute offset within the child string. `tryAutoLinkExtension` reads
`originSrc` the same way but is gated on `state.top`, so it is safe.

**Decided: fix them as they are reached, not bug-for-bug.** The port carries the
fixes; muya's behaviour is not reproduced.

The cost is real and has to be paid explicitly. M1's verification strategy is
agreement with the TypeScript engine, and every fix is a disagreement. Without
somewhere to record it, a fixed bug and a botched port look identical — so the
fixes are only safe if each one is *registered* before it is made.

#### The divergence register

`spec/divergences.json`, one entry per intentional difference:

```json
{
  "id": "emoji-nested-boundary",
  "site": "lexer.ts:206 tryChunks",
  "muya": "child substring indexed at an absolute offset",
  "ours": "index relative to the current tokenizer level",
  "inputs": ["**a :smile:**", "**:smile:**"],
  "upstream": null
}
```

Rules, which are what make this stronger than bug-for-bug rather than weaker:

1. A differential disagreement on a registered input is expected. A
   disagreement on **any other** input is a failure, exactly as before.
2. Every entry names concrete inputs, and those inputs become Rust tests
   asserting the **fixed** behaviour.
3. An entry with no failing differential case is stale — the fix is either
   unimplemented or the divergence was imaginary. The harness should say so.
4. `upstream` holds the marktext issue URL once filed. **File them.**

This is the same shape as `spec/expected-failures.json`, deliberately: M2's
conformance ratchet will need the identical mechanism, and one register serving
both harnesses is one thing to keep honest.

#### The three sites

| # | Site | Fix | Register? | |
|---|---|---|---|---|
| 1 | `tryChunks` emoji boundary, `lexer.ts:206` | Index relative to the current level, not absolutely | **Yes** | done, S2; entry widened S3 and S5 |
| 2 | `disallowedHtmlTag`, `lexer.ts:21` | Exact tag-name match, not substring | **Yes** | done, S4 |
| 3 | `pending` doubling, `lexer.ts:135` | Plain assignment | No — inert | done, S1 |
| — | `tryFootnote`'s `pos === 0`, `lexer.ts:290` | *none* — reproduced | No — not a bug | examined, S2 |

**1 — emoji boundary. Done in S2.** Track each level's base offset and read the
preceding character at `pos - base - 1`. When `pos == base` there is no
preceding character *at this level*: treat that as a boundary and allow the
emoji. That is correct for every call site — a child level is only ever entered
after `*`, `_`, `~`, `[` or a `>`-terminated open tag, none of which are word
characters — and it is what the top level already does at `pos == 0`.

In Rust this falls out of passing level-relative slices and keeping `base`
separate, so it is one line rather than a special case. It also makes
`tryAutoLinkExtension`'s identical read (`lexer.ts:578`) safe *by construction*
instead of by the `state.top` gate that currently saves it by accident.

**Checked at S5, which is where that second site was finally written.** muya is
right there and the port registers nothing: `state.top` really does guarantee
that `originSrc` is the string `pos` indexes. What S5 confirms is the *by
construction* half — `LexState::preceding_char` cannot read a different string
from the one `pos` indexes whether or not `top` holds, so the gate is
reproduced because it is muya's behaviour and not because the port needs it to
be safe. That was the last place D4's claim had left to be checked.

D4 went one step further than that paragraph anticipated, and the step matters
here: because a level is `(origin, level: Span)` rather than a substring plus a
base, `LexState::preceding_char` is the whole fix and there is no second string
for `pos` to disagree with. The bug is **unrepresentable**, not merely absent.

The divergence turned out to be wider than the entry that registered it,
**three times** — see "S2's verification", "S3's verification" and "S5's
verification" in §6. Two inputs became seven, then twelve, then sixteen; one
fix throughout. The second widening is the *opposite direction* of the first
(muya keeping an emoji it should suppress, rather than losing one it should
keep), and the third is at `html_tag`, the container S4 added. Register rule 1
is what forces all of them: an unregistered disagreement is a failure, so a
class wider than its entry must widen the entry.

The third widening is worth separating from the other two, because it is a
**correction** rather than an extension. S4 checked this exact class at
`html_tag` with two inputs, found both agreeing, and recorded in §6 that the
entry did not need to widen. One of the two agrees for a reason that does not
generalise, and 96 of 228 swept inputs disagree. A hand-run can return a false
negative and be written down as a result; that is the argument for S7's
comparator, stated by an actual miss rather than in the abstract.

**A fourth site was considered and rejected.** `tryFootnote` returns false when
`state.pos === 0` (`lexer.ts:290`), and `pos` is absolute, so a footnote cannot
open at offset 0 of a block while in a nested level it can. That is the same
*shape* as site 1 — an absolute offset where a relative one might be meant — so
it was worked out rather than waved past. It is **reproduced**, for two
reasons, the first decisive: the comparison has only one operand and reads no
string, so unlike site 1 there is nothing for the absolute offset to be
inconsistent *with*; and "the beginning of the block" is the right thing to
test, because a `[^…]` there is the label of a footnote *definition* line and
belongs to the block layer. No register entry — nothing diverges. Recorded on
`try_footnote`, where the next reader of that line will be.

**2 — disallowed HTML tags. Done in S4.** GFM §6.11 names exactly nine tag
names: `title` `textarea` `style` `xmp` `iframe` `noembed` `noframes` `script`
`plaintext`. muya's regex is unanchored, so `<subtitle>` and `<scripty>` are
rejected too. Match the name exactly, case-insensitively.

The Unicode half of that is already closed upstream of the fix, which is why
`eq_ignore_ascii_case` against nine literals is exact rather than a narrowing:
S1 wrapped `html_tag`'s tag-name class in `(?-i:…)` precisely so Rust's full
folding could not admit U+017F or U+212A, so capture 3 is ASCII by
construction.

**The entry widened, for the third time in this register and the first on this
entry** — two inputs to seven, from the S4 differential. Reading the regex
gives `<subtitle>` and `<scripty>`; running it gives three things reading did
not. The class contains **real HTML elements** — `<noscript>` is rejected for
containing `script`, and `<subscript>`/`<superscript>` are used in the wild. It
is case-insensitive on the *containing* name too, so `<SubTitle>` is rejected.
And it reaches **hyphenated custom-element names**, which GFM's own tag-name
production explicitly allows, so `<iframe-x>` is rejected. Fifty-eight of the
4172 differential inputs are this class; seven representatives are registered,
because rule 2 asks for concrete inputs that become tests rather than an
enumeration.

**3 — `pending` doubling. Done in S1.** `state.pending += state.pending +
backTo[2]` reads as a doubling bug, but `pushPending` clears `pending` on the
line above, so it is always `'' + '' + x`. Write the plain assignment and leave
a comment saying why it is not a behavioural change. No register entry —
nothing diverges.

Worth one more sentence than it looked like it needed, because the port does
not carry a `pending` string at all: it carries the offset the run starts at,
with the end implied by `pos`. That is sound only because pending text is
always a contiguous slice of the source — which is true *given* this fix, and
would not be if the doubling were live. The reasoning is recorded on
`LexState::pending`, not only at the assignment.

#### What this does not disturb

None of the 49 transcribed specs assert any of these behaviours: the four
`emojiWordBoundary` cases are all top-level, and the one `commonmarkExamples`
case that reaches `html_tag` uses `<bar attr="…">`, not a disallowed name. So
the fixes add tests and change none. Checked, not assumed.

### D4 — `state.src.substring(n)` is O(n²) **← actioned in S1**

The TypeScript loop reslices the remaining input on every token *and every
unmatched character*. Rust should advance an index into the original `&str` and
match anchored at that index. This is a pure win — same semantics, no allocation
— but it changes what "the input to a rule" means, so decide it before writing
the loop rather than retrofitting.

Done, and it took one more step than the paragraph above describes. A level is
represented as `(origin: &str, level: Span)` rather than as a substring plus a
base offset, so a rule matches against `&origin[pos..level.end]`. That is what
makes D3 site 1 unrepresentable rather than merely fixed: muya's bug is that
`originSrc` is the child string while `pos` indexes the parent, and here there
is only one string. `tryAutoLinkExtension`'s identical read is safe by
construction too, instead of by the `state.top` gate that saves it by accident.

Anchoring: every rule is `^`-anchored and JavaScript `exec` is called on a fresh
substring. In Rust, match against `&src[pos..]` with the same `^` anchor, or use
an explicitly anchored search. Do not use an unanchored search and check the
match start — that silently changes `lowerPriority`'s meaning.

### D5 — where `lowerPriority` gets its rule set

Two different sets are passed, and the difference is load-bearing (there is a
14-line comment in `rules.ts:118-125` explaining why, referencing issue #4671):

- `validateRules` — all rules except `em`, `strong`, `tail_header`, `backlash`,
  `superscript`, `subscript`, `footnote_identifier` — used by emphasis
  validation and the emoji check.
- `linkValidateRules` — only `inline_code`, `html_tag`, `auto_link` — used by
  `tryLink` and `tryReferenceLink`.

Model these as two explicit const slices. Do not derive one from the other at
runtime; the exclusion list is a `const` in TypeScript for the same reason.

Note `lowerPriority` iterates every position up to `offset` and runs every rule
in the set at each one. It is O(offset × |rules|) regex executions. Correct
first, per §3; but it is the obvious hot spot and worth a benchmark before M1
closes so M3 is not surprised.

**Done in S3**, and widened on the way: S2's measurement showed the rule table
costs more than `lowerPriority` does, so `crates/mt-inline/benches/tokenizer.rs`
benchmarks the whole tokenizer over `bench/corpus/` and keeps a
`lowerPriority`-shaped input set as one section of it. Numbers per stage in §6.

### D6 — fuzzing on Windows **← implemented in S7**

The exit gate is 24 hours without a panic. `cargo-fuzz`/libFuzzer support on
Windows MSVC is thin. **Recommendation:** run the 24 h libFuzzer soak on Linux
in CI, and run `proptest` on all three platforms in the normal test job. The
corpus already contains the awkward inputs to seed from. Panic-freedom is a
property of the code, not the platform — but the *platform-specific* risk here
is UTF-8 boundary slicing, so make sure the proptest generator produces
multi-byte and lone-surrogate-adjacent input.

**Built in S7, and the recommendation held in full — with one thing it did not
anticipate and one it got exactly right.**

`crates/mt-inline/tests/properties.rs` runs in the normal test job on all three
platforms: 512 cases over each of three distributions, plus the `highlights`
post-pass and `marker_state` over arbitrary cursors, in 5.5 s. `fuzz/` carries
three cargo-fuzz targets and `.github/workflows/soak.yml` runs them nightly on
Linux.

**"Lone-surrogate-adjacent" needed reading twice.** Rust's `str` cannot hold a
lone surrogate — that is what `char` *is* — so the phrase cannot mean what it
says literally, and a generator built to the letter of it would produce nothing.
What it means is the three places the surrogate block makes the two languages
disagree about what one character is, and the generator produces all three:
U+D7FF and U+E000, the scalars either side of the block, where a hand-decoded
`\uD800`-`\uDFFF` escape is off by one and `emphasis.rs`'s non-BMP punctuation
table is forty such escapes; **astral** characters, one `char` here and two
UTF-16 code units there, which is D1's entire subject; and multi-character
grapheme clusters — ZWJ, variation selectors, skin-tone modifiers, combining
marks. `the_generator_produces_multi_byte_and_surrogate_adjacent_input` asserts
the distribution contains them, because a generator that silently degenerates to
ASCII makes every property above it vacuous and nothing in a green run would
say so.

**The gate does not fit in a GitHub job, and 24 hours is not 24 hours of wall
clock.** A GitHub-hosted runner is killed at **6 hours**. So `soak.yml` runs a
3 targets × 2 shards matrix at 4 h each: 24 CPU-hours in 4 hours of wall clock,
every shard under the limit with room. The shards of one target differ only in
their libFuzzer `-seed` and share a cached corpus, so they explore different
mutation sequences from the same frontier instead of repeating each other.

**Three targets rather than one**, because "point the fuzzer at it" is a
statement about the input distribution and a general target satisfies it only by
accident:

| Target | Pointed at | Why separate |
|---|---|---|
| `tokenize` | everything | The gate itself. |
| `autolink` | `trim_auto_link_extent` | **The one thing `BACKTRACK_LIMIT` does not bound** — hand-written Rust, quadratic in the extent (S5). Every input starts at an opener, so the budget goes on the extent. |
| `backtracking` | the seven ReDoS-class rules | §4 C1: *"what the M1 fuzzing gate should be pointed at first."* Every input opens a quantifier that must scan to the end of the level before it can fail. |

**And one thing D6 does not cover, which §9 makes matter.** libFuzzer on Linux
leaves the gate met on the platform whose failures block *least* — §9 says
**Windows ships first**. So `properties.rs` also carries an `#[ignore]`d `soak`
test: the same properties over the same generators, driven for a wall-clock
duration on any platform and any toolchain, coverage-**blind** where libFuzzer
is coverage-guided and structure-**aware** where libFuzzer starts from bytes.
`soak.yml` runs it for an hour on all three. It also reports its slowest inputs
per byte, which is libFuzzer's `-report_slow_units` for the platforms libFuzzer
does not run on — and that is what turns a soak into a benchmark row rather than
only a pass/fail.

**Assertions are the point, and a plain `--release` run loses them.** The four
proved-unreachable branches are `debug_assert!`s as of S7, so both
`fuzz/Cargo.toml`'s release profile and the soak's invocation set
`debug-assertions = true`. A soak with them compiled out runs faster and checks
strictly less — and "less" is precisely the four claims nobody has broken by
hand.

### D7 — what `highlights` costs **← implemented in S6**

`tokenizer()` takes `highlights` and runs a post-pass intersecting every token
range with every highlight. §3 puts `highlights: SmallVec<[Highlight; 2]>` on
every token. The TypeScript makes it optional and only allocates on
intersection. Keep it optional/empty-by-default; a `SmallVec` inline capacity of
2 on every token in a 5 MB document is a measurable memory cost for a field
that is empty except during a search.

**Built in S6, and the decision needed no revision — but it has two
consequences the paragraph above does not spell out.**

- **`lexer.ts:890` guards the whole walk**, not just the allocation:
  `if (highlights.length) postTokenizer(tokens)`. So the empty case costs one
  branch per *call*, not one per token, and the port reproduces the guard as
  behaviour rather than adopting it as an optimisation. Measured: at 1 to 64
  highlights the post-pass is **below this benchmark's noise floor** against
  the tokenize it follows, and it only becomes visible at 1024 — about
  **0.5–0.8 ns per `union`**, which is two integer comparisons and a `max`/
  `min`. See "S6's cost".
- **Empty-by-default is a wire difference, and S7's comparator needs to know.**
  muya creates `token.highlights` on the *first* push, so a token that
  intersects nothing has **no `highlights` key at all**; the port gives every
  token a `Vec` that is merely empty. That is this decision working as
  intended — the field is not an `Option` here — but it is a per-field
  `undefined`/`[]` normalisation exactly like the `|| ''` sites S3 found, and
  it is recorded beside them in `xtask/src/divergences.rs` rather than only
  here.

### D8 — marker reveal: §3.1 is a sketch and two of its three clauses are false **← decided in S6**

§3.1 states the predicate as:

> A token's markers reveal when the caret is inside `token.range` (inclusive of
> edges) **or the selection intersects it**. Everything else renders decorated.
> **Ancestor tokens reveal when a descendant reveals.**

The reference is `renderer/index.ts:111`, `_checkConflicted`, reached through
`getClassName` at sixteen call sites:

```js
private _checkConflicted(block, token, cursor = {}) {
    const anchor = cursor.anchor || cursor.start;
    const focus = cursor.focus || cursor.end;
    if (!anchor || !focus || (cursor.block && cursor.block !== block))
        return false;
    const { start, end } = token.range;
    return conflict([start, end], [anchor.offset, anchor.offset])
        || conflict([start, end], [focus.offset, focus.offset]);
}

getClassName(outerClass, block, token, cursor) {
    return outerClass || (this._checkConflicted(block, token, cursor)
        ? CLASS_NAMES.MU_GRAY : CLASS_NAMES.MU_HIDE);
}
```

**Decided: port `_checkConflicted`, not §3.1.** Clause by clause.

**1. "the caret is inside `token.range`, inclusive of edges" — correct.**
`conflict(a, b)` is `!(a[1] < b[0] || b[1] < a[0])`, and both offsets are
passed as the degenerate range `[o, o]`, so the test reduces to
`start <= o && o <= end`. That is `Span::contains_offset`, which S0 wrote for
this and documented as inclusive "because §3.1 says so". It is inclusive
because the engine is.

**2. "or the selection intersects it" — false.** The two endpoints are tested
**separately**, each as its own degenerate range. A selection running from
before a token to after it therefore reveals **nothing**: neither endpoint
lands on the token. Only an endpoint on or inside a token reveals that token.
Select across a whole `**bold**` run and, as far as this predicate is
concerned, its markers stay hidden — that is not a bug, it is this line. (What a
selection *does* light up is a different mechanism: `highlight()` and the
`highlights` field, which is D7.)

**3. "ancestors reveal when a descendant reveals" — false, and there is no
mechanism for it.** This is the clause worth the most words, because the thing
§3.1 describes *nearly* exists.

- The only channel is `getClassName`'s `outerClass`, and it runs **parent →
  child**, the opposite direction.
- It **overrides** rather than combines: `outerClass || (…)`, so a value from
  above replaces the child's own computation instead of being OR-ed with it.
- **Nothing in the pinned revision ever gives it a value.** Every value it
  could carry has to enter through `dispatch`, and all six `dispatch` call
  sites — `output()` and the five child loops in `delEmStrongFactory`,
  `htmlTag`, `link` (twice) and `referenceLink` — construct
  `{ h, cursor, block, token }` with **no `outerClass` key**. The five sites
  that do forward it (`del`/`em`/`strong` → `delEmStrongFac`, `htmlTag` →
  `image` and → `htmlRuby`) forward a parameter their own caller left unset.
  The graph is closed, so `outerClass ≡ undefined`. Measured as well as read:
  `getClassName` was instrumented and seven documents booted against
  happy-dom — nested emphasis, a link inside emphasis, `<ruby>`, an image, a
  reference link, a heading — for **193 calls, every one with
  `outerClass === undefined`**. (One further trap for a reader following the
  name: `backlashInToken`'s third parameter is also called `outerClass`, and it
  is *not* this — it is the already-computed class name, used directly as a CSS
  class rather than passed to `getClassName`.)
- The comments say it was *meant* to work and was broken by a refactor.
  `delEmStrongFactory.ts:33`, `htmlTag.ts:22` and `link.ts:124` each carry a
  note that the original passed a `className` **field** while receivers
  destructure `outerClass`, so it was "silently dropped under the previous
  `as any` cast", and that the TypeScript port preserves that. The legacy
  `packages/muyajs` copy confirms it: there the calls are positional —
  `this[snakeToCamel(to.type)](h, cursor, block, to, className)` — and the
  fifth argument *is* `outerClass`, so propagation was live before the
  options-object refactor. **§3.1 describes muyajs, not muya.** Reproduced as
  it is: §3 rule 3 says behaviour is defined by the engine, and "restore a
  feature the reference lost" is not a port.

One more thing the sketch does not have: the block test. `_checkConflicted`
returns `false` outright when `cursor.block` is set and is not the block being
rendered. `mt-inline` has no blocks (§1), so this becomes the caller's — a
cursor that belongs elsewhere is passed as `None`, which is the same answer.

**So the signature changes, and the per-token shape survives.** §3.1 asks
whether `marker_state` can keep a per-token signature at all given clause 3. It
can, and the reason is stronger than "adequate": with no propagation in either
direction, the decision reads nothing but that token's `range` and the cursor —
no ancestor chain, no descendant scan, no order dependence. What does change is
the arguments. §3.1's
`marker_state(token, caret: Option<usize>, sel: Option<Range<usize>>)` encodes
clause 2 in its own parameter list: a caret and a selection as separate things,
the selection to be intersected. The engine has one pair of offsets, equal when
collapsed. So:

```rust
pub struct Cursor { pub anchor: usize, pub focus: usize }   // Cursor::collapsed(o) is a caret
pub fn marker_state(token: &Token, cursor: Option<Cursor>) -> MarkerState
pub fn marker_state_of_range(range: Span, cursor: Option<Cursor>) -> MarkerState
```

`crates/mt-inline/src/marker.rs` is the module; `MarkerState` is §3.1's enum
unchanged.

**Checked rather than reasoned.** `_checkConflicted` was called on a real
`Renderer` over **2835 combinations** — five token ranges including an inverted
one, nine anchor offsets, nine focus offsets, and seven cursor shapes
(`anchor+focus`, `start+end`, each endpoint alone, same block, another block,
no cursor at all) — and the port's `marker_state` agrees on every one. The two
shapes with a single endpoint and the other-block shape all come back `false`,
which is what makes `Option<Cursor>` the faithful encoding rather than a
convenient one.

**Two renderer behaviours sit on top of the predicate and are deliberately not
in `mt-inline`**, recorded because a renderer that omits them will look correct
and feel wrong. `header.ts:17` calls `getClassName` with a **synthetic token** —
`{ range: { start, end: end - content.length } }` — so a heading's `#`s reveal
for a caret on the `#`s, not for one anywhere in the heading text; and
`htmlTag.ts:121` **bypasses** the predicate for a childless tag
(`children?.length ? getClassName(…) : MU_GRAY`), so a void or empty element is
always revealed. Both are about *which range to test* and *whether to test*;
the predicate itself is unconditional. `marker_state_of_range` exists so the
first is expressible without fabricating a `Token`.

### S3's cost, and why S2's extrapolation was wrong

S2 predicted the two ignored corpus files would go "past ten minutes" by S5.
**S3 halved them instead: ~134 s → ~68 s** in a debug profile, and the covered
run went ~4.2 s → ~3.2 s.

The correction matters more than the number. Cost is not *rules × characters*;
it is *rules × **unmatched** characters*, because a lazy `[\s\S]*?` only scans
to the end of the level when the rule **fails**. `bench/corpus/1mb.md` holds
1586 links, and at S2 each one was ~37 consecutive positions at which six lazy
rules each scanned the rest of a very long paragraph. At S3 one `try_link` call
consumes the construct and those positions stop existing. **A handler that
matches often can pay for itself several times over.**

S4's `html_tag` and S5's autolinks match rarely in this corpus, so they should
add cost rather than remove it — but not by S2's factor.

The benchmark is `crates/mt-inline/benches/tokenizer.rs`, run with `cargo bench
-p mt-inline`. No `criterion`: what is needed is a number per stage comparable
with the previous stage's, not a confidence interval, and the dependency policy
says nothing lands before the milestone that needs it. It carries both profiles
because `round_trip.rs` tracks the debug figure a developer waits for and M3
will want the release one. S3, release: **6.1 s over the whole 6.6 MB corpus,
~1.03 MiB/s, flat across four orders of magnitude of input**. The outlier is
`[` × 4000, at 0.02 MiB/s — fifty times slower per byte than prose, because
every position runs `link`, `reference_link` and the four lazy S2 rules to the
end of the level before failing. It is in the set deliberately: it is the
canary, and a later stage that hurts prose will show up there first, magnified.

### S4's cost — the prediction held, and the shape of the cost is new

**S3's prediction was right: 6.1 s → 14.9 s in release, a 2.4× rise**, the
first stage to make the number worse. The `lowerPriority` set went
200 → 472 ms, the covered `round_trip.rs` run ~3.2 s → ~4.3 s, and the debug
figures rose by a larger 3.4×: the whole-corpus benchmark 71.6 s → 243.4 s and
the two ignored corpus files ~68 s → ~229 s. Debug moves further than release
because `check_tiling` and the extra nesting level `html_tag` introduces exist
only there, so a stage that adds a *container* costs that profile twice.

The factor is not the interesting part; its **uniformity** is. Every row moved
by almost exactly 2.4× — prose 1.03 → 0.42 MiB/s, the `[` × 4000 canary
172 → 412 ms, the `lowerPriority` set 200 → 472 ms. S2's and S3's changes were
*shape-dependent*: they moved the rows with long levels and left short ones
alone, because a lazy `[\s\S]*?` costs in proportion to how far it scans. S4's
is **flat**, and flat means a fixed cost per *attempt* rather than per
character scanned.

That is `html_tag` being the most expensive rule in the table to merely
**fail**. Its `\3` backreference and its `(?i)` flag put it on `fancy-regex`'s
backtracking path instead of the delegated non-backtracking one, so every
unmatched position now pays a VM setup even though both alternatives reject on
the first character. Before S4 the handler returned `false` without running the
rule at all — and its presence in `lowerPriority`'s two sets was not the same
cost, because those only run *inside* a candidate emphasis or link span.

So the model to carry into S5 is now two-part rather than one: a handler's cost
is *(how often it fails) × (its per-attempt cost)* plus *(how far a lazy
quantifier scans when it fails)*, and S2/S3 only exercised the second term. S5's
`auto_link` has no backreference and no `(?i)`, so it should delegate to the
non-backtracking engine and cost far less per attempt than `html_tag` does;
`auto_link_extension` has lookahead and will not.

**The obvious remedy is deliberately not taken.** Both alternatives of
`html_tag` begin with a literal `<`, so skipping the `exec` when the next byte
is not `<` is semantics-preserving and would recover most of the 2.4×. §3
sequences it the other way — port faithfully, hand-optimize later with the
suite as the guard — and a first-byte pre-check is a change to *how rules are
run*, which belongs with the rest of the rule-table work at M3 rather than
inside a handler stage. Recorded on `benches/tokenizer.rs` so M3 finds it as a
measurement rather than a hunch.

The same method again. muya's `tokenizer` was loaded directly and its token

- **S4's check of `emoji-nested-boundary` at `html_tag` was half a check, and

  looked at. This is a class somebody **did** look at, with two inputs, one of

### S5's cost — the prediction was wrong, and wrong in a new way

**Predicted before running:** a rise of 1.4–1.8×, *flat* across rows, on the
S4 model — `auto_link` delegating to the non-backtracking engine and costing
almost nothing, `auto_link_extension` carrying a lookahead and therefore
paying `html_tag`'s flat per-attempt VM setup.

**Measured: 1.20×, and not flat at all.**

Two comparisons, because they do not agree and the difference is the point.
Against S4's recorded 14.9 s, the new number — **16.3 s** — is a 1.09× rise.
But that is across sessions, and this benchmark is a wall clock. So the same
binary was run twice with the two new handlers short-circuited behind a
one-time flag: **13.9 s stubbed against 16.6 s live, a 1.20× rise**, and that
is the number to trust. (Run-to-run noise on the corpus total is ~1.5%, which
is the 16.3/16.6 spread; the 13.9 stubbed figure against S4's recorded 14.9 is
ordinary session variation, and is why the A/B was done at all rather than
trusting the cross-stage subtraction.)

The half of the prediction that held is that `auto_link` costs nothing. The
half that did not is much more interesting, and it needed a new benchmark
section to see — `autolink-shaped inputs`, now in `benches/tokenizer.rs`:

| Input | stubbed | live | |
|---|---:|---:|---|
| one 4000-character word run, no `@` | 9.9 ms | **22.5 ms** | 2.3× |
| the same 4000 characters as 800 short words | 9.7 ms | 11.0 ms | 1.15× |
| the same again, broken by a non-local-part character | 9.8 ms | 10.9 ms | 1.11× |
| 160 bare URLs that match | 9.7 ms | **0.9 ms** | **0.09×** |
| 240 bare emails that match | 10.0 ms | **1.3 ms** | **0.13×** |
| a 2000-character trimmable tail | 5.0 ms | 7.0 ms | 1.44× |
| `[` × 4000 (the S4 canary) | 418.8 ms | 412.4 ms | 1.00× |

Three things follow, and the first is a **third cost shape** for the model:

- **The cost is the email alternative's local part, and it scales with word
  length.** `[\w.!#$%&'*+/=?^`{|}~-]+@` contains every letter, digit and
  underscore, so at every position inside a word the engine scans forward to
  the end of the word run looking for an `@` that is not there. Rows one and
  two are the *same 4000 bytes* and differ by 2×, purely in how long the runs
  are. So the model is now three-termed: *(how far a **lazy** quantifier scans
  when it fails)* — S2 and S3; *(a flat VM setup per attempt)* — S4; and *(how
  far a **greedy** quantifier scans before the character that must follow it
  turns out to be absent)* — S5. The `[` × 4000 canary is unmoved because not
  one of its characters is in that class, which is the cleanest possible
  confirmation.
- **A matching autolink pays for itself an order of magnitude over.** Bare URLs
  went 9.7 ms → 0.9 ms — an **11× speedup** — because one match consumes
  twenty-five characters that would otherwise each have been a position at
  which every rule in the table ran and failed. That is S3's `1mb.md` finding
  again, at a far larger factor, and it is why the corpus rose only 1.20×
  despite row one's 2.3×: prose is short words with occasional URLs.
- **The trim itself is quadratic in the extent**, because the paren rule
  recounts `raw[0..end]` on every pass and `end` moves by one. 1.44× on a
  2000-character tail. muya is quadratic there too, so this is faithfulness
  rather than a regression, but it is the one part of S5 that is *not* bounded
  by the backtrack limit — it is hand-written Rust, not a regex — and S7's
  fuzzer should know that.

Per-file: `1mb.md` is the worst row at 1.41×, `250kb.md` and `10kb.md` are
1.12×, `5mb.md` is 1.17×, and the `lowerPriority` set is 1.06×.

The debug corpus total is **243.4 s → 265.6 s**, and the thing to notice is the
*ratio*: debug has been ~16× release since S4 and it is ~16× again. S4 widened
it from ~12× by adding a container, because `check_tiling` and an extra nesting
level exist only in that profile. Neither autolink handler tokenizes children,
so S5 should not have widened it — and it did not. That is the S4 explanation
confirmed by a stage that predicts the opposite sign, which is the only way a
ratio like that gets checked at all.

**S4's deferred first-byte pre-check is not implemented here**, and S5 adds a
second candidate to it rather than acting on either: `tryAutoLinkExtension`

### S6's verification

The same method again, and this is the first stage where the thing under test

Swept rather than sampled, per the same note. The input set is every
`bench/corpus/` file whole (11) **and every non-empty line of the ones under
300 KB** (2968), every CommonMark and GFM example (1324), every
`marktext-round-trip/` fixture whole and per line (451), 67 targeted inputs
covering all twenty token types the switch names *and* the six in its

**All 5586 agree exactly**, on three things per input: the plain text, the
total token count (a cross-check, so that two engines cannot agree on the text

`start`, `end` and `active`, at every path, for every highlight set.

Three sweeps beside the main one:

- **`union` directly, 7203 rows** — every pair of ranges over seven endpoints
  crossed with the three `active` states. Zero disagreements. This is where the
  degenerate cases live that the post-pass never produces, and one of them
  corrected a claim: *"a zero-length token range never intersects anything"* is
  **false**. The test is `!(tEnd <= lStart || lEnd <= tStart)`, so an empty
  range strictly *inside* the other passes it and yields an empty intersection
  — `[5,5)` against `[0,10)` is `Some([5,5))`. Only a *touching* empty range
  fails. "Touching at a point is not an intersection" is right; "nothing empty
  ever intersects" is the over-reading of it.
- **`_checkConflicted`, 2835 rows** — five token ranges (including an inverted
  one) crossed with nine anchor offsets, nine focus offsets and seven cursor
  shapes, called on the real `Renderer`. Zero disagreements against the port's
  `marker_state`. This is what D8 rests on.
- **The `html_escape` fallback, exhaustively** — see below.

**And a negative control, which is the part S5's lesson demands.** 5586
agreements are only evidence if the harness could have said otherwise, and
nothing in that input set reaches a registered divergence. So all 27
`spec/divergences.json` inputs were run through the same comparator: **16 of 16
`emoji-nested-boundary` disagree, 7 of 7 `disallowed-html-tag-substring-match`

The third entry, `html-tag-attrs-from-a-foster-parented-element`, **agrees on

reads `attrs`. It is invisible to *this* comparator, which is a fact about the
comparator. S7's has to compare fields, not text.

Four things the run established that reading could not:

- **`escapeCharactersMap[…] ?? token.raw`'s fallback is live, and it is the
  common branch.** Three stages running had found a branch that looks
  load-bearing and provably cannot fire — S2's rule-16 guard, S3's `correctUrl`
  group 5, S5's `if (!email)` — so the prior on a fourth was not low. Measured
  instead: the rule is built with the `i` flag (`rules.ts:45`) and the map is a
  JavaScript object, so lookup is case-sensitive. Over **every case spelling of
  every one of the 252 names** — the longest is eight letters, so 6084 distinct
  spellings, exhaustive — all 6084 become an `html_escape` token, **252 hit the
  map** (the canonical spellings, one each) and **5832 miss** and render as
  their own source text. Not a defensive `??`; the branch 96% of reachable
  inputs take.
- **There *is* a fourth dead branch, and it is the next line up.**
  `html_tag`'s `else if (token.content)` cannot fire. `tryHtmlTag` has exactly
  two branches: the comment branch (`lexer.ts:652`) sets neither `content` nor
  `children`, and the element branch (`:686`) sets
  `children: htmlTo[4] ? … : []` — an array either way, and `[]` is truthy — so
  `if (token.children)` always wins there. No producer leaves `children` absent
  while `content` is present. Reproduced with the proof as a test, as the other
  three were.
- **muya's comment on the `backlash` arm is wrong and its code is right.** The
  comment says the escaped character is `raw` minus its leading `\`. §4 C3 says
  `raw` is the `\` **alone** and the escaped character is in the next `text`
  token, and that is what `tryBacklash` does (`lexer.ts:118`). So
  `raw.replace(/^\\/, '')` strips the only character there is and contributes
  the empty string — and the output is still correct, one token later.
  Transcribed as the strip rather than as a `continue`, with the premise pinned
  by a test, because the expression is what muya evaluates.
- **`escape.rs`'s account of its own duplicates was wrong since S1, and
  `entities.rs` had repeated it.** Both said the repeated keys are "mapped to
  different characters at different indices". Enumerated against the running
  module: there are **twelve** repeated keys and not five — `&quot;` `&amp;`
  `&lt;` `&gt;` `&nbsp;` three times each, `&ensp;` `&emsp;` `&copy;` `&reg;`
  `&trade;` `&times;` `&divide;` twice, which is all 17 redundant rows — and
  **every occurrence of a key pairs with the same character**. So `reduce`'s
  last-occurrence-wins is unobservable and the map is well defined either way.
  The part of the argument that survives never needed the values: this list is
  a rule alternation, `entities.rs` is HTML5's, and they are different tables
  for reasons the values had nothing to do with.

### `character_classes.rs`'s fate — **decided: it stays**

`crates/mt-inline/tests/character_classes.rs`'s header has said since S1 that
the file *"becomes redundant and should be deleted in favour of [the
differential harness] when it grows a token-stream mode"*. S7 built that mode,

**Kept.** The sentence was wrong about one thing, and it is the thing that
matters: the two are not the same check, so neither can be redundant with
respect to the other.

- **It runs on a machine with no marktext clone; the harness does not.**
  `cargo xtask divergences` reports `SKIPPED` and exits 0 without the reference
  engine — deliberately, and `--require-ts` is what makes CI demand it. Delete
  this file and the C2 expectations, which §4 C2 calls *"faithful-port traps

  contributor's `cargo test`.
- **A golden and a live comparison fail differently.** The file asserts *what
  muya did*, transcribed by a human; the harness asserts *what muya does*, now.
  A wrong transcription is invisible in the first and caught by the second; an
  absent reference engine is invisible in the second and caught by the first.

So they are wired to complement rather than to overlap, and the wiring is the
part that makes this a decision rather than a deferral. S7 added
`C2_CHARACTERS × C2_CONTEXTS` to the harness's sweep — 35 trap characters in 27

about a thousand inputs go through the live engine on every commit. That set was

makes it able to catch a mis-transcription instead of reproducing one.

The half-decision to avoid is worth naming: moving the golden's inputs into the
sweep and deleting the file would have looked like consolidation and would have
traded an offline check for nothing.

| a trimmable tail | 112.6 ms | 115.0 ms | 1.022× |

Prediction 2 is **half confirmed and stated as such**. The email row is the
largest move and it is the one row with an identified mechanism, which is what
the prediction said. But `bare URLs` moved 1.024× and it should not have — the
URL path reaches no new assertion — and these are single runs, where the release
section above has just demonstrated that one sample carries a systematic
first-run bias. So what is established is a **direction**, not a magnitude, and
the honest summary is that debug is somewhere between unchanged and ~3% slower.

The one number that is not ambiguous is the `lowerPriority` set at **1.000×**,
and it is the control: that section contains no autolink and almost no
completed link, so it reaches none of the five assertions, and it did not move
by a microsecond over four seconds of work.

The debug/release ratio is 261.1 / 16.3 = **16.0×** — the same as S4's, S5's and
S6's. It has moved exactly once in the milestone, at S4, which added a container
and so charged `check_tiling` and an extra nesting level twice. S7 adds no rule
and no level.

**The three-term cost model is unchanged and unextended.** S7 adds no rule, so
there is no fourth shape: *(how far a lazy quantifier scans when it fails)*,
*(a flat VM setup per attempt)*, *(how far a greedy quantifier scans before the
character that must follow it is absent)*.

**A search for slow inputs, rather than a canary someone thought of.** S5's
lesson was that one canary is not enough: `[` × 4000 was blind to the
greedy-quantifier shape S5 itself introduced, and it took a hand-written input
set to see it. A search that *maximises* time per byte is the general version of
that, and it is why the soak reports its slowest inputs per byte at all —
libFuzzer's `-report_slow_units=5` is the coverage-guided form of the same
question, and the soak test is the form that runs where libFuzzer does not.

**And the first version of it was measuring the operating system.** Over
14,657,664 cases it confidently reported eight "slowest" inputs of 10 to 32
bytes at 250,000–939,000 ns/B. Every one worked out to **10–14 ms of wall clock
regardless of length** — a fixed cost, which is a scheduler quantum and not
anything the tokenizer did. At ~2.5 µs/byte a 15-byte input is ~37 µs of work;
the number reported was 380× that.

The fix is in `properties.rs`: the ranking pass is a candidate filter, and what
is printed is the **minimum over 32 re-runs** of inputs of at least 64 bytes.
Minimum rather than mean, because preemption and page faults can only make a
measurement longer, so the smallest observation is the least contaminated one.

It is recorded rather than quietly fixed because of what the unfixed version was
about to do: put a scheduler artefact into `benches/tokenizer.rs` as a cost row.
A benchmark row nobody can reproduce is worse than a missing one, and this
milestone has spent seven stages on the principle that a number without a method
behind it is not evidence. It is also the same shape as the A/B ordering
mistake above and as S4's false negative — a measurement that looked clean,
was internally consistent, and was wrong.

**Fixed, the search found nothing worth a row, and *that* is the result.**
5,897,280 cases over 331 MB, ten minutes, and the eight slowest inputs land
between **2,554 and 3,146 ns/B**. Prose in this corpus runs at ~2,510 ns/B
(0.38 MiB/s), so the worst input a search over nearly six million candidates
could find is **1.25× the average** — against the `[` × 4000 canary already in
`benches/tokenizer.rs`, which is **41×**. The search did not come within a
factor of 33 of the worst input the benchmark already has. No row is added.

The winners say why, and it is a limitation of the *generator* rather than a
fact about the tokenizer: they are 68 to 153 bytes. All three cost terms scale
with how far a quantifier scans, which is bounded by the **level length**, and
`markdownish` concatenates at most 24 pieces — so the longest thing it can
produce is about 460 bytes and no quantifier ever has far to go. A generator
that cannot produce a long level cannot find a slow input, however many short
ones it tries.

That is precisely the gap libFuzzer covers, and it is a better argument for the
Linux soak than "coverage-guided" was: `soak.yml` passes `-max_len=65536`, two
orders of magnitude past anything here, seeded from a corpus whose files are
megabytes. **The slow-input question is open and is the soak's to answer**, with
`-report_slow_units=5`; what this stage establishes is that the *short*-input
space is not where the answer is.

**Neither deferred rule-table optimization is implemented here**, and S7 adds no
third candidate because it adds no rule. `html_tag`'s first-byte pre-check (S4)
and hoisting `tryAutoLinkExtension`'s `state.top` guard above its `exec` (S5)
stay recorded on `benches/tokenizer.rs` as M3's — both are changes to *when* a
rule is run.

### The pending ratchet — added in S0

The stage gates above are written as "N specs pass", which reads as though the
suite is simply red until each stage clears it. Taken literally that leaves
`cargo test --workspace` failing for the whole milestone, and a build that is
red for months is a build nobody reads — by the time a real regression appears
in one of the other thirteen crates the signal is long gone. That is the one
failure mode M1 cannot afford, because §13 R1 (*"lexer port diverges subtly"*)
is the risk the entire verification strategy is built around.

So the 49 are wrapped in the same ratchet the repository already uses twice.
Every case that does not pass yet is listed in `PENDING`
(`crates/mt-inline/tests/inline_renderer_specs.rs`):

| State | Result |
|---|---|
| Listed, still failing | passes — it is on the list |
| Listed, now **passing** | **fails** — delist it |
| Unlisted, passing | passes |
| Unlisted, now failing | **fails**, with the original panic |

Row two is what makes it a ratchet rather than `#[ignore]`: getting better must
also fail the build, so the list is forced down instead of accumulating entries
that later let a fixed case quietly regress. Row four is what gives a delisted
case normal teeth again.

Restated, then: **each stage gate above is "delete that stage's cases from
`PENDING`", and S7's is "`PENDING` is empty."** Its length is the milestone's
progress meter, and shrinking it is a reviewable one-line diff plus the case
removals.

S6's round-trip property is the strongest single check in the milestone and it
is nearly free — `generator` is a concatenation of `raw` fields. Build it as
soon as S1 lands rather than waiting for S6; it will catch tiling errors in
every stage after it.

**Done in S1**, along with the debug tiling assertion S7's row asks for, for
the same reason: an invariant that only starts being checked at the end of the
milestone is an invariant that gets debugged at the end of the milestone.
`crates/mt-inline/tests/round_trip.rs` runs `generator(tokenize(s)) == s` over
`bench/corpus/`, and `tests/inline_renderer_specs.rs` runs it over all 49 spec
inputs, so every handler S2–S5 adds is covered the moment it is written.

## 8. Risks

| Risk | Mitigation |
|---|---|
| `fancy-regex` backtracking blows up on a pathological input | Explicit backtrack limit from S1; treat exceeding it as no-match; point the fuzzer at it first. **Done at S7:** `fuzz/fuzz_targets/backtracking.rs` opens one of the seven lint-silenced quantifiers on every input, and asserts the property C1's decision exists to preserve — a rule that gives up leaves its characters as text, so the round trip holds whether or not the limit was reached |

| The attribute scanner (D2) diverges from DOMParser on malformed HTML | **Retired at S4.** The differential ran: zero disagreements on malformed input across 1199 corpus/fixture matches and a 14,035-case sweep. `html5ever` was rejected rather than held in reserve — it is spec-conformant and the reference is not, so it would disagree too. The residual risk moved to *tree construction*, and the one unmodelled mechanism is registered |
| The register grows an entry nobody decided, quietly widening what the harness tolerates | Every entry names a decision in §5 behind it, asserted by `the_register_holds_d3s_two_entries_and_d2s` |
| The register is never machine-checked, so a reverted fix reads as green | **Closed at S7.** `cargo xtask divergences` compares token streams against the running engine on every commit; all three entries report `ok`, and reverting D3 site 2's fix turns its entry `STALE` and exits 1. | A comparator agrees on everything because nothing it ran could disagree | **Run the register's own inputs as a negative control**, every time. ## 10. Owed forward

Three verifications are owed to milestones that have not started. Recorded here
so they are not lost, because in every case the layer that would check them
does not exist yet — which is exactly how an owed check becomes a forgotten one.

### Owed to the renderer milestone (§9 M3/M4) — autolink href encoding

`autoLinkEncoding.spec.ts` is the only one of the seven inline spec files that
is **not a tokenizer test**: it boots a `Muya` instance against `happy-dom`,
renders, and reads `a.mu-auto-link[href]` out of the DOM. §7 lists it under
`mt-inline`, but the encoding it locks in is the *renderer's*, and `mt-inline`
has no renderer and no DOM — §1 forbids it ever having one.

Split at S0 into the half each layer owns:

- **Done, at S5.** The `auto_link` token's `href` is the literal source
  between the angle brackets — no encoding, no decoding, no normalisation.
  That is the precondition the fix rests on: if the tokenizer mangles the href,
  no renderer can un-mangle it. Both cases are transcribed and both now pass;
  `AutoLink::href` is a `Span`, so the property holds by construction rather
  than by a comparison.
- **Owed.** The anchor's `href` attribute is emitted from that span verbatim
  rather than through an `encodeURI` equivalent. marktext #3548 was a
  double-encoding bug — `%20` became `%2520` — so the regression it guards
  against is silent and user-visible: the link opens the wrong URL.

**S5 made this more fragile, not less.** Before it, the two transcribed cases
sat in `PENDING` and were visibly unfinished business. Now they pass, `PENDING`
is empty, and nothing anywhere is red on account of #3548 — which is precisely
the state in which an owed check becomes a forgotten one. A green tokenizer
test is not evidence about a renderer that does not exist. It is recorded here,
on `AutoLink` in `token.rs`, and in the `auto_link_encoding` module of
`tests/inline_renderer_specs.rs`; the milestone that lands the renderer owes
the other half.

### Owed to the renderer milestone — the two overrides above `marker_state`

Added at S6, when D8 settled what the reveal predicate is. `mt-inline` now ships
the predicate, and it is exact: 2835 swept `(range, anchor, focus, shape)`
combinations agree with `_checkConflicted` on the running `Renderer`. But two
call sites do not use it as written, and both are invisible from here because
§1 forbids this crate a renderer.

- **`header.ts:17` tests a synthetic range.** It builds
  `{ range: { start, end: end - content.length } }` and passes *that* to
  `getClassName`, so an ATX heading's `#`s reveal for a caret on the `#`s and
  not for one anywhere in the heading text. `mt_inline::marker_state_of_range`
  takes a bare `Span` precisely so a renderer can express this without
  fabricating a `Token`; whether it *does* is what is owed.
- **`htmlTag.ts:121` bypasses the predicate.**
  `children?.length ? getClassName(…) : MU_GRAY` — a void or empty element is
  revealed unconditionally, cursor or no cursor.

Neither is a tokenizer behaviour and neither can be red here. They are recorded
on `crates/mt-inline/src/marker.rs` as well as in this section.

### Owed to M2 — `normalizeHtml`

Carried from M0. `normalizeHtml` was ported to Rust in M0 and has never been
checked end-to-end, because nothing produces HTML yet. When
`render_to_static_html` returns `Ok`, feed the same HTML through the Rust and
TypeScript versions and assert agreement. Noted in `xtask/src/html.rs` and
`tools/diff/README.md`.
